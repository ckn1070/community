# 도메인별 개선 검토 관점

이 문서는 `improvement`가 현재 artifact를 도메인 전문성에 맞게 검토하기 위한 선택형 질문을 제공한다. 모든 항목을 형식적으로 적용하지 말고, 결론과 검증 범위를 바꿀 수 있는 관점만 개선 판단에 연결한다.

여러 도메인이 관련되면 사용자가 개선하려는 결과를 직접 소유하는 primary domain을 먼저 정하고, 그 결과의 정확성·안전성·실행 가능성을 좌우하는 도메인만 supporting domain으로 포함한다.

## 문서

- 대상 독자와 문서만으로 답해야 할 질문이 명확한가?
- 현재 사실, 결정, 작업 상태, 운영 절차와 과거 증거의 canonical owner가 분리됐는가?
- 문서의 주장이 실제 코드, 설정, schema, 운영 상태와 일치하는가?
- 제목과 첫 화면에서 목적, 책임과 다음 탐색 경로를 복원할 수 있는가?
- 정보가 일반 개념에서 구체 조건과 절차로 자연스럽게 이어지는가?
- 중복, 장황함, 폐기된 결론, 설명 없는 용어와 원문 오염이 남아 있는가?
- router, 링크, 번호, 보존 등급과 영구 SOT 승격이 현재 구조와 일치하는가?
- 절차라면 시작 조건, 정상 흐름, 중단 조건, 검증과 복구를 독자가 실행할 수 있는가?
- 구조 verifier뿐 아니라 독자 관점의 전체 읽기와 source 의미 동기화가 가능한가?

문서 개선은 문장을 다듬는 데서 끝내지 않는다. 내용의 소유 위치, 최신성, 탐색성, 필요한 분량과 실제 source와의 의미 일치를 함께 검토한다.

## 코드와 테스트

- 외부에서 관찰되는 동작과 반드시 보존할 호환성은 무엇인가?
- 도메인 불변식, validation, 권한, 데이터 무결성과 transaction 경계가 어디에 있는가?
- 동시성, idempotency, retry, rollback과 부분 실패가 개선으로 달라지는가?
- 책임, 응집도, 결합도, 의존 방향과 abstraction 수준이 현재 문제에 적합한가?
- naming, 제어 흐름, 중복과 복잡성이 독자의 정확한 이해와 변경을 방해하는가?
- 오류 처리와 예외 변환이 원인을 보존하고 호출 계약에 맞는가?
- 성능, 자원 사용과 확장 비용을 뒷받침하는 측정이나 구조적 근거가 있는가?
- test가 구현 세부가 아니라 사용자 동작과 위험 경계를 증명하는가?
- fixture, mock과 test seam이 결정적이고 유지 가능한가?
- 비자명한 정책·위험·변경 조건에 정확한 코드·설정 주석과 문서가 필요한가?

코드 개선을 미관이나 line 수 감소로 판정하지 않는다. 실제 변경 용이성, 정확성, 안전성, 검증 가능성과 기존 보장의 유지로 판단한다.

## 시스템과 운영

시스템에는 build, runtime 설정, CI/CD, infrastructure, deployment, 외부 연동, 자동화, 관측성과 운영 절차를 포함한다.

- 구성요소, interface, dependency, 실행 주체와 신뢰 경계가 명확한가?
- 정상 흐름 외에 timeout, 부분 실패, 재시도, 중복, 장애 전파와 복구 경로가 있는가?
- 권한, secret, 개인정보, 공급망과 외부 입력의 검증 경계가 충분한가?
- 데이터 생성·변경·보존·삭제와 rollback에서 무결성이 유지되는가?
- 배포, migration, 점진 전환, 호환성과 안전한 rollback이 가능한가?
- 로그, metric, trace, health signal과 경보가 실패를 영향 범위까지 진단하게 하는가?
- 성능, 용량, 비용, rate limit과 자원 한도가 실제 운영 조건에 맞는가?
- 설치와 실행이 재현 가능하고 manual step, drift와 환경별 차이가 통제되는가?
- 운영자, 소유권, runbook, 장애 대응과 제거·갱신 조건이 명확한가?
- test, static validation, policy, staging과 실제 환경 검증이 위험을 비례적으로 닫는가?

작은 diff를 낮은 시스템 위험으로 간주하지 않는다. 권한 기본값, schema constraint, CI gate와 배포 설정 한 줄도 영향과 가역성으로 평가한다.

## Workflow와 skill

- trigger가 사용해야 할 요청을 놓치거나 관련 없는 요청에 발동할 가능성이 있는가?
- 본문이 해당 domain의 고유 판단만 소유하고 canonical workflow의 공통 lifecycle을 복제하지 않는가?
- handoff가 specialist에게 필요한 입력·산출물 경계를 보존하는가?
- 자동화 후보가 독립 oracle을 가지며 새 실패 표면과 유지 비용보다 순효과가 큰가?
- metadata가 discovery에 필요한 trigger와 제외 상황만 설명하고 본문 절차나 권한을 대신하지 않는가?
- SKILL 본문, bundled resource와 `agents/openai.yaml`이 같은 사용 범위를 표현하는가?
- 복잡하거나 재량이 큰 변경을 오염되지 않은 forward-test나 cold-reader로 검증할 수 있는가?

workflow와 skill 개선은 규칙 문장을 늘리는 것으로 끝내지 않는다. trigger, owner 경계,
전문 판단, resource와 검증 가능성 중 실제로 품질을 제한하는 계층을 고친다.

## 제품, 도메인과 데이터

- 개선이 해결하려는 사용자 결과와 업무 의미가 명확한가?
- 정상 흐름, 경계 조건, 오류, 권한 거부와 상태 전이가 정의됐는가?
- 도메인 불변식과 데이터 소유권을 올바른 모델과 계층이 책임지는가?
- 개인정보, 접근성, 공정성, 감사와 규제 조건에 영향이 있는가?
- 기존 사용자, API와 데이터의 호환성·migration·복구 경로가 있는가?
- 성공을 사용자 동작, 업무 상태와 측정 가능한 수용 기준으로 확인할 수 있는가?

새 사용자 가치나 정책 결정이 필요하면 개선이라는 이름으로 암묵적으로 확정하지 않는다. feature·design·planning 경로에서 선택지와 영향을 닫은 뒤 실행한다.
