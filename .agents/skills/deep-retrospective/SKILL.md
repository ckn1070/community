# 심화 회고

동일한 보호 범위에서 실패가 재발했을 때 새 규칙을 덧붙이지 않고, 이전 원인 분석과
방어의 생애주기 자체가 왜 실패했는지 조사합니다.

## 1. 적용 조건

다음을 실제 source와 Git에서 모두 확인합니다.

- 서로 독립된 두 사건이 있습니다.
- 이전 회고의 보호 불변식과 유효 범위를 복원할 수 있습니다.
- 이전 조치가 구현·적용·검증 완료로 보고됐습니다.
- 후속 사건이 같은 불변식 또는 포괄한다고 선언한 실패 계열을 위반했습니다.
- 이후 사용자 요구나 상위 SOT가 그 contract를 폐기하지 않았습니다.

하나라도 없으면 일반 회고나 별도 결함 조사로 돌립니다. 제품명이나 마지막 문장이
비슷하다는 이유로 재발로 묶지 않습니다. 적용 여부, 읽기 전용·실행 권한과 복귀점은
[100 작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)가
판정합니다.

이전 완료·검증 증거는 verifier가 본 control content, 적용된 Git blob과 실제 actor가
호출한 content identity가 일치할 때만 인정합니다. 기록 digest가 실제 blob과 다르거나,
검증 뒤 control이 바뀌면 영향받은 verdict와 그 의존 완료를 무효화합니다. Isolated runner만
통과하고 live invocation 증거가 없으면
[100 작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)의
증거 등급에 따라 모델링된 통제 효과의 직접 증명 범위는 유지하되, 미관찰 invocation과 그
효과에 의존한 완료만 `검증 불가`로 낮춥니다. 일부 control·전이만 불일치하면 일치한
control과 직접 관찰한 전이의 증거까지 함께 폐기하지 않습니다.

일반 회고가 사용자 원문의 `회고해`, `회고하라` 같은 명령에서 실행 mode를 확정했다면
심화 routing은 그 권한을 줄이지 않습니다. 이 skill 이름이 새로 선택됐다는 이유나 원인·
이유 질문이 함께 있다는 이유로 읽기 전용으로 다시 판정하지 않습니다. 사용자가 원인·
판단·상태만 질문했거나 skill을 언급하기만 한 경우에는 상태 변경 권한을 만들지 않습니다.

## 2. 두 사건과 이전 방어

각 사건은 `$retrospective`의 수평·수직 분석으로 별도 폐쇄합니다. 그다음 다음을
연결합니다.

- 사건별 기대·실제·영향과 최초 단절
- 공통 보호 불변식과 서로 다른 경로
- 이전 root와 선택한 통제
- 통제의 실제 owner·배치·호출 시점
- 이전 oracle이 증명한 범위와 증명하지 않은 범위
- 후속 사건이 통제를 우회하거나 통과한 exact 경로

이전 보고와 self-authored 검증을 사실로 재사용하지 않고 실제 artifact·호출·결과를
대조합니다.

## 3. 방어 생애주기의 2차 원인

이전 방어를 다음 전이로 분해합니다.

```text
원인 분석 → 통제 설계 → owner·배치 → invocation → oracle
→ 검증 → 갱신·제거·drift 관리
```

각 전이에서 실제 증거로 다음을 조사합니다.

- 직접 원인에서 멈추거나 서로 다른 사건을 과도하게 합쳤는가
- root와 다른 계층 또는 중복 owner에 통제를 배치했는가
- 영향 뒤에 호출되거나 실제 경로에서 호출되지 않았는가
- 작성자가 만든 contract·fixture만으로 성공을 선언했는가
- 구현 존재를 실제 사용·효과로 오인했는가
- 검증한 exact content와 적용·호출된 Git blob이 일치했는가
- 새 메시지나 phase handoff 뒤에도 같은 live actor가 통제를 실제 호출했는가
- 제거·갱신 조건이 없어 stale 통제가 남았는가

각 실패 전이에 최소 5회의 인과 질문과 root 제거 반사실을 적용합니다. 사건의
제품명·확장자·option을 형제 사례로 바꿔도 원인과 불변식이 유지되는지 확인합니다.

## 4. 공통 통제 lifecycle에 인계

다음을 작업 실행 workflow의 통제 변경 생애주기에 전달합니다.

```text
두 사건과 공통 불변식
+ 사건별 최초 단절
+ 이전 방어 lifecycle의 실패 전이와 2차 root
+ 이전 완료·검증 범위
+ root 제거·renamed transfer 반사실
+ 원래 작업 복귀점
```

기존 완료 무효화, work item 재개, 통제별 유지·강화·교체·병합·제거와 새 통제
admission은 공통 workflow가 단독으로 판정합니다. 이 skill은 그 상태 전이를 다시
소유하지 않습니다.

## 5. 반영·검증·보고

실행 권한이 있으면 선택된 canonical owner와 중복 통제를 같은 결과 단위에서
정리합니다. 사건 대상 artifact 복구와 push는 별도 권한입니다.

명령형 실행 회고에서 전환됐다면 `$retrospective`의 실행 회고 closure 계약을 그대로
적용합니다. 이전 방어 생애주기 분석이나 통제 처분 판정만으로 완료하지 않으며, 선택한
통제의 실제 적용·행동 검증·필요한 local commit 또는 공통 실제 차단 gate의 `Blocked`
전환이 없으면 심화 회고를 `진행 중`으로 유지합니다.

행동 검증의 raw source pool에는 두 사건, 이전 방어의 우회 경로와 root 제거 반사실을
포함합니다. 통제 작성자가 최종 사례·oracle·합격을 함께 소유하지 않도록 case contract
동결, fresh runner·독립 evaluator 분리와 실패 뒤 보완 lifecycle은 작업 실행 workflow에
위임하며, 이 skill에서 별도 판정 규칙을 만들지 않습니다. one-shot runner의 PASS를
다중 턴 actor나 다른 phase의 invocation 증거로 대체하지 않고, 동결한 content identity와
최종 적용 blob이 달라지면 그 행동 검증을 다시 수행합니다.

다음을 연결해 보고합니다.

```text
두 사건과 공통 불변식
→ 이전 방어 생애주기의 2차 시스템 원인
→ 공통 lifecycle의 통제 처분과 실제 적용
→ 행동 검증과 남은 위험
→ 원래 작업의 상태와 복귀 행동
```

필요할 때만 `$report-task`로 상태 projection을 보충하며, 짧은 상태 요약으로 심화
회고의 인과 결과를 대체하지 않습니다.
