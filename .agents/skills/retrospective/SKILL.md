# 회고

한 사건의 사용자 영향에서 출발해 최초로 끊어진 전이와 시스템 원인을 찾습니다. 사건에
등장한 명사별 규칙을 만들지 않고 [작업 실행 워크플로우의 통제 변경
생애주기](../../../docs/workflow/100-work-execution-workflow.md#4-통제-변경-생애주기)에
증거를 전달합니다.

## 1. 적용과 routing

원래 요청·직접 선행 문맥, 사건 artifact·diff·log와 현재 통제 source를 읽습니다.
작업 실행 workflow에서 exact 회고 대상, 문장 기능, 권한과 복귀점을 먼저 확정합니다.

[작업 실행 workflow의 분류와 routing](../../../docs/workflow/100-work-execution-workflow.md#분류와-routing)을
그대로 사용하며 이 skill에서 같은 분류를 다시 정의하지 않습니다. 그 결과 일반 회고로
routing된 사건만 아래 절차로 조사하고, 심화 회고나 다른 owner로 향한 사건은 해당
입력과 복귀점을 그대로 인계합니다.

어떤 사건이 회고 대상인지, 기존 회고가 이 skill의 인과·통제 lifecycle·보고 계약을
충족했는지 묻는 요청도 retrospective domain으로 routing합니다. 질문형 문장은 상태 변경
권한을 닫을 뿐, 이 skill과 현재 통제 source를 읽는 read-only 조사를 생략하는 근거가
아닙니다.

skill 호출 자체는 상태 변경 권한이 아닙니다. 읽기 전용·실행 범위와 local commit
예외는 작업 실행 workflow의 판정을 따릅니다.

skill 이름·tag와 사용자의 회고 동사를 분리합니다. 사용자가 현재 실패를 재발하지 않게
`회고해`, `회고하라`처럼 명령하면 원인·이유를 함께 요구해도 통제 반영·검증을 포함하는
실행 회고입니다. 파일명, `반영`이나 `commit`을 따로 말하지 않았다는 이유로 읽기 전용
질문으로 낮추지 않습니다. 반대로 회고 대상 여부·원인·판단·상태·보고 형식만 질문했거나
skill을 언급하기만 했다면 상태를 변경하지 않습니다. 이 mode를 고정한 뒤 일반·심화
routing을 수행하며, 심화 회고로 인계할 때도 원문에서 확정한 mode를 다시 해석하지
않습니다.

실행 mode를 확정할 때 작업 실행 workflow의 회고 상시 예외를 같은 원자의 operation
map에 즉시 결속합니다. 이 map은 `통제 owner의 exact-path local commit`을 포함하고 사건
artifact 복구와 push를 제외하며, 통제 적용 뒤 Git 단계에서 새로 만들거나 다시 승인받지
않습니다. Git adapter와 sandbox·tool approval을 호출할 때도 원문 원자와 이 예외를 함께
전달해, 외부 gate가 skill의 전체 결과 계약을 추론하도록 두지 않습니다.

## 2. 사건 계약

다음을 source에 연결합니다.

- 사용자가 요구한 결과와 실제 결과
- exact 사건 대상과 관찰 가능한 영향
- 위반한 불변식과 증거
- 사건까지 이어진 actor·입력·결정·행동·검증·보고
- 관련 기존 통제의 owner·도입 시점·호출 여부
- 원래 작업의 현재 상태와 복귀점

대화 요약이나 Agent의 사과를 증거로 사용하지 않습니다. 여러 영향 경로가 있으면
공통 단어로 합치지 않고 각 경로를 독립적으로 닫습니다.

사용자가 번호·block별로 회고를 따로 명령하면 각 명령에서 별도 사건 계약을 만듭니다.
공통 source discovery는 재사용할 수 있지만 사건별 사용자 영향·최초 단절·routing·통제
처분·행동 검증 verdict와 복귀점은 합치지 않습니다. 조사 뒤 공통 root가 확인되더라도
그 관계는 개별 회고를 대체하지 않으며, 여러 사건을 비교하는 심화 회고도 사용자가 요구한
개별 회고의 누락 근거가 될 수 없습니다. 사용자가 하나의 상위 회고로 직접 묶었을 때만
통합 결과를 만들고 그 안에서도 하위 사건 identity와 verdict를 유지합니다. 이 명시적
grouping은 source discovery 전에 첫 projection에서 수락하며, 허용 여부를 다시 질문하거나
판정 대상으로 열지 않습니다.

일반·심화 subtype은 사건 당시의 통제 도입 시점과 영향 전 실제 invocation을 source·Git
timeline으로 확인한 뒤에만 확정합니다. 사건 뒤 작성한 현재 workflow·skill 후보의 존재나
반복·공통 주제는 이전 방어가 실패했다는 증거가 아닙니다. timeline이 없으면 실행 mode는
그대로 유지하고 subtype만 미확정으로 둔 채 이 skill이 증거를 복원하며, 현재 후보를 근거로
심화 회고를 먼저 호출하지 않습니다.

구체적인 답변·변경 실패와 모든 미래 경로에서 그 실패를 강제로 막는 보장은 별도 사건
계약으로 둡니다. 사용자가 현재 실패의 회고·수정을 요구했다면 미요청 보장이나 platform
구축을 상위 결과로 올리지 말고, 현재 Agent가 만들 수 있는 exact 결과와 복귀점을 먼저
보존합니다.

## 3. 수평 경로

각 사건을 시간 순서로 분해합니다.

```text
source·입력 → 의미 해석 → 판단·계획 → 실행 → 직접 검증 → 사용자 결과
```

기대와 실제가 처음 달라진 전이를 최초 단절로 고정합니다. 잘못된 마지막 문장,
제품명·option·파일명, 사용자의 기대 상태와 `주의 부족`은 최초 단절이 아닙니다.

하나의 경로를 고쳤을 때 같은 입력 전달을 공유하는 형제 실패가 남는지 확인합니다.
명사를 바꿔도 같은 경로가 끊기면 domain 사례가 아니라 공통 전이 문제입니다.

## 4. 수직 원인

각 최초 단절에서 최소 5회의 인과 질문을 사용하고 증거가 요구하면 더 확장합니다.

```text
직접 단절
→ 왜 허용됐는가
→ 어떤 owner·interface·invocation·oracle이 비었거나 잘못됐는가
→ 시스템 root
→ 기존 방어가 있었다면 왜 영향 전에 작동하지 않았는가
→ root 제거 반사실
```

원인은 관찰 가능한 전이와 책임 관계를 설명해야 합니다. 기존 규칙의 문구를 다시
말하거나 결과를 개인 주의로 돌리지 않습니다. root를 제거해도 같은 증거 경로에서
영향이 발생하면 더 위의 전이를 추적합니다.

누락된 외부 owner·interface·runtime을 root나 blocker로 지목하기 전에, 사건 당시 현재
Agent가 가진 source·권한만으로 기대 결과를 만들 수 있었는지와 그 외부 요소가 영향 전의
실제 인과 경로에 있었는지를 확인합니다. 기대 결과를 만들 수 있었고 외부 요소가 실제
경로에 없었다면 외부 강제력의 부재는 root가 아닙니다. 현재 대상을 더 큰 보장 문제로
바꾼 의미 해석·판단 전이부터 계속 추적하며, 미래 보장의 한계를 현재 실행 능력의 한계나
사용자의 구현 책임으로 바꾸지 않습니다.

사용자가 원인이나 통제가 증상 처방이라고 지적하면 그 결론에서 파생한 해결책을
폐기하고 최초 단절부터 다시 조사합니다.

## 5. 공통 통제 lifecycle에 인계

인과가 닫히기 전에는 해결책을 선택하지 않습니다. 닫힌 뒤 작업 실행 workflow에
다음을 전달합니다.

```text
관찰 영향 + 최초 단절 + 보호 불변식 + 시스템 root
+ 기존 통제 timeline·owner·invocation·oracle
+ root 제거 반사실 + 형제 경로 + 복귀점
```

통제의 유지·강화·교체·병합·제거, 새 통제 admission, work item 재개와 행동 검증은
공통 workflow가 판정합니다. 이 skill은 같은 상태 전이나 Git 권한을 다시 정의하지
않습니다.

## 6. 반영·검증·보고

실행 권한이 있으면 공통 lifecycle이 선택한 canonical owner만 수정합니다. skill이나
Markdown을 바꾸면 해당 전문 skill을 함께 적용합니다. 사건 대상 artifact의 복구는
별도 권한이 있을 때만 수행합니다.

명령형 실행 회고에서는 `원인 분석 완료`, `통제 처분 결정`, `통제 적용`, `행동 검증`과
`Git 마무리`를 서로 다른 상태로 유지합니다. 분석·제안·review 판정이나 변경할 필요가
없다는 설명은 뒤 상태를 대신하지 않습니다. 영향받은 기존 통제를 `유지`하려면 작업 실행
workflow의 유지 조건을 사건 영향과 다시 대조하며, 보호 범위 안에서 사용자 영향이 이미
발생한 통제를 근거 없이 그대로 두는 처분은 적용 완료가 아닙니다.

실행 회고는 다음 중 하나가 실제로 성립할 때만 닫습니다.

- 선택한 통제 처분을 canonical owner에 반영하고 행동 검증을 통과했으며, worktree 변경이
  있으면 허용된 exact path의 local commit까지 완료했습니다.
- 작업 실행 workflow의 실제 차단 gate를 통과해 `Blocked`로 전환하고, 남은 owner·필요
  입력·재개 조건을 확정했습니다.

어느 쪽도 아니면 회고는 `진행 중`입니다. 통제 미적용 상태를 `변경 없음`, `분석 완료`나
`회고 완료`로 보고하지 않으며, local 변경이 없다는 이유로 빈 commit을 만들지도 않습니다.

행동 검증의 raw source pool에는 실제 사건, 최초 단절과 root 제거 반사실을 포함합니다.
통제 작성자가 최종 사례·oracle·합격을 함께 소유하지 않도록 case contract 동결, fresh
runner·독립 evaluator 분리, regression·transfer·false-block·실제 routing 판정과 보완
lifecycle은 작업 실행 workflow에 위임합니다. 문구 존재나 자기작성 fixture를 별도 성공
기준으로 만들지 않습니다.

결과는 다음 인과 순서로 보고합니다.

```text
최초 단절과 시스템 원인
→ 기존 방어가 실패한 이유
→ 공통 lifecycle의 통제 처분과 실제 반영 상태
→ 검증 결과와 남은 위험
→ 원래 작업의 현재 상태와 복귀 행동
```

분석·제안·적용·검증을 구분합니다. 상태 projection이 별도로 필요할 때만
`$report-task`를 보조로 사용하고, 상태 요약으로 인과 결과를 대체하지 않습니다.
