# 개발 계획

구현자가 중대한 제품·기술 선택을 다시 하지 않고 실행할 수 있는 계획 artifact를 만든다.
요청 해석, 권한, 공통 단위 상태, 병렬화, 실제 차단 판정과 final discovery·closure는
[작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)가 소유한다.
이 skill은 계획이 결과인 작업의 설계 판단과 문서 checkpoint만 소유한다.

## 1. 계획 경계와 source

작업 실행 workflow가 계획을 현재 결과로 routing했을 때 primary로 사용한다. 구현 요청 중
계획 보완이 필요한 경우에는 workflow가 인계한 영향 범위의 설계 결정만 닫고 `$develop`의
복귀점을 유지한다.

계획을 작성하기 전에 다음을 실제 디스크에서 읽는다.

1. 저장소 `AGENTS.md`, 문서 router와 관련 workflow
2. 현재 work item, 같은 번호의 `-design`과 직접 연결된 결정 문서
3. 관련 code, test, 설정, schema, migration, 배포·운영 source
4. 현재 사실을 소유하는 domain·architecture·project·tech-stack SOT

계획 문서에는 [`$documentation`](../documentation/SKILL.md)을 적용한다. 이 저장소에서는
`docs/work-items/000-index.md`와 `docs/work-items/100-work-item-lifecycle.md`를 기준으로 기존
문서를 우선 갱신한다. 미확정 계획을 현재 사실 SOT로 승격하거나 Plan mode의 대화 목록을
최종 산출물로 대신하지 않는다.

## 2. 계획 입력과 현재 상태 조사

작업 실행 workflow가 잠근 목표·제약·범위·수용 기준을 계획 입력으로 받고 다음을 연결한다.

- 계획의 독자와 구현 후 관찰할 제품·기술 결과
- 현재 동작, 목표 동작, 확인된 간극과 authoritative source
- 요구사항별 수용 기준과 이를 입증할 구현·검증·문서 책임
- 사용자가 고정한 방법과 검토 가능한 구현 후보의 구분
- 외부 공식 계약, 저장소 규칙, 가정과 미확정의 구분

일부 snippet, 이름, 계획 문장이나 일반 Best Practice만으로 현재 상태를 추정하지 않는다.
현재성이 중요한 지원 상태·보안·비용·호환성은 최신 공식 1차 근거를 확인한다. 사용자가
제안한 방법보다 목표를 더 잘 달성하는 실행 가능한 대안이 있으면 비교와 추천에 포함한다.

## 3. 설계 표면을 포화하기

결과를 바꿀 수 있는 관련 표면을 세션 inventory에 `미조사`, `분석 중`, `확정`, `열린
사용자 결정`, `해당 없음`으로 표시하고 근거·다음 판단을 연결한다. 전체 표를 repository에
보존하지 않고 consequential decision과 계획 결과만 문서화한다.

- 제품 동작, 사용자 흐름, 오류와 경계 조건
- API, event, file, CLI와 외부 계약
- 도메인 규칙, 상태 전이, 권한과 불변식
- data model, schema, constraint, migration과 보존
- transaction, 동시성, idempotency, retry, 보상과 rollback
- module, package, 계층, port/adapter와 의존 방향
- 기술, library, 외부 서비스와 공급자
- 인증·인가, secret, 개인정보, 위협과 감사
- 성능, 용량, 확장, cache와 자원 한도
- 배포, 설정, 관측성, 장애 대응과 복구
- test 전략, fixture, 검증 환경과 품질 gate
- 호환성, 전환, 점진 배포, 되돌리기와 제거
- 문서, 운영 책임, 소유권과 영구 SOT

하위 계획 다수를 무효화할 수 있는 공통 전제는 downstream 상세화 전에 가장 작은 실제
source·공식 근거·대표 정상 경로·대표 반례로 확인한다. 전제가 성립하지 않으면 그 전제에서
파생한 파일별 계획을 만들지 않고 설계 표면과 대안으로 돌아간다. 판정에 외부 입력이
필요하면 그 사실과 영향은 계획 결과에 제공하되, 실제 차단 여부는 작업 실행 workflow에
인계한다.

## 4. 결정 소유권과 결정 카드

결과에 의미 있는 차이를 만드는 결론은 다음 권위 중 하나로 분류한다.

- **사용자 확정 요구**: 이미 정한 목표·제약·제외·수용 기준이므로 다시 선택지로 만들지 않는다.
- **외부·저장소 불변식의 파생 결론**: 공식 규격, 현재 source나 확정 상위 결정이 선택을
  하나로 제한하므로 근거와 파생 관계를 기록한다.
- **Agent 소유 기술 추천**: 현재 목표와 근거로 최적안을 책임 있게 정할 수 있으므로
  대안·추천·trade-off를 문서화하고 결론을 떠넘기지 않는다.
- **사용자 소유 결정**: 실행 가능한 대안이 둘 이상이고 제품 정책, 예산, 위험 허용도,
  운영 책임, 조직 역량이나 외부 입력이 선택 기준일 때만 사용자에게 결정받는다.

중요하거나 복잡하다는 이유만으로 사용자 소유 결정으로 만들지 않는다. 국소적이고 쉽게
되돌릴 수 있으며 결과 차이가 작은 기술 세부는 저장소 관례로 닫는다.

사용자 소유 결정은 상세 설계를 읽지 않아도 답할 수 있는 카드로 준비한다.

1. 결정할 질문
2. 사용자 소유 근거
3. 배경과 제약
4. 실제 채택 가능한 2~3개 대안
5. 결과를 바꾸는 비교 축과 차이
6. 추천안과 이유
7. 영향·위험·재검토 조건
8. 한 줄로 답할 수 있는 exact 응답 형식

비교 축은 정확성, data·security, 안정성·복구, 유지보수성, 성능·자원, 호환성·migration,
test·관측성, 비용·소유권과 사용자 경험 중 결론을 바꾸는 것만 사용한다. 결정 카드의
제시 시점과 묶음이 공통 차단 gate를 충족하는지는 작업 실행 workflow가 판정한다.

후속 피드백은 [설계 피드백 워크플로우](../../../docs/workflow/120-design-feedback-workflow.md)로
정규화한다. 직접 취소·대체되지 않은 사용자 확정 요구와 결정은 같은 값·권위로 유지한다.
변경 후보에서 확정 결정이 삭제·강등·재전환되면 이를 허용하는 더 최신 사용자 결정이나
독립 authoritative source를 요구한다.

## 5. 구현 가능한 계획 artifact

설계 표면과 선행 결정이 닫힌 범위에서 작업을 파일 목록이 아니라 독립적으로 검증 가능한
결과 단위로 작성한다. 각 작업은 다음을 포함한다.

1. 제목, 목표와 연결된 요구사항·결정
2. 선행 조건과 의존 결과
3. 수행 내용과 영향받는 경계
4. 오류·보안·data·운영 고려사항
5. test·검증 명령과 통과 기준
6. 문서와 영구 SOT 반영
7. 완료 뒤 관찰 가능한 결과
8. rollout, rollback 또는 복구 방법

계획 전체에는 요구사항·수용 기준, 확정 결정 색인, 작업 의존 관계, negative·회귀 test,
migration·호환성, 운영 검증과 범위 밖 항목의 재검토 조건을 연결한다. TDD 대상은 실패
test, 최소 구현, refactor와 회귀 검증 순서를 반영한다. 근거 없는 일정 숫자는 작성하지 않는다.

work item 본문은 현재 계획 결과와 확정 결정 색인을, `-design`은 장기 복원이 필요한 대안
비교와 구현 계약을 소유한다. 대화 원문, 승인 표현, 내부 사고, 임시 inventory, dirty 상태와
반복 검증 기록은 저장하지 않는다. 상세 판단이 커도 사용자가 결정할 질문·대안·추천을 첫
화면에서 복원할 수 있게 한다.

## 6. 계획 문서 checkpoint

계획 문서가 요청 결과이면 작업 실행 workflow가 허용한 상시 예외로 검증된 현재
checkpoint를 local commit한다.

1. 현재 계획 상태를 work item·`-design`과 필수 router에 동기화한다. 미확정 계획을
   `Planned`나 완료로 승격하지 않는다.
2. `$documentation`으로 source·owner·링크·번호와 결정 delta를 검증한다.
3. 이번 checkpoint의 exact path·hunk만
   [커밋 워크플로우](../../../docs/workflow/300-commit-workflow.md)로 stage·commit한다.
4. 다른 작업의 dirty hunk와 안전하게 분리할 수 없으면 checkpoint를 만들지 않는다.
5. commit object와 잔여 dirty를 확인한다. push는 별도 명시 권한이 있을 때만 수행한다.

최초 안정된 `Proposed`, 사용자 결정 반영과 최종 `Planned` 후보처럼 다음 작업자가 복원할
필요가 있는 상태만 checkpoint로 남긴다. 최종 후보는 아래 독립 검증을 통과한 뒤에만
`Planned`로 전환하고 다시 checkpoint한다.

## 7. 계획 검증과 산출물

자체 검토에서는 다음 반례를 찾는다.

- 구현자가 중대한 제품·기술 선택을 새로 해야 하는가
- 정상 흐름뿐 아니라 잘못된 입력, 권한 거부, 중복, 동시성, 부분 실패와 복구가 빠졌는가
- 기존 data·API·설정·배포에서 목표 상태로의 전환과 rollback이 빠졌는가
- 모든 요구가 구현 작업·검증·문서에 연결되고 각 작업의 결과를 관찰할 수 있는가
- test 불가능한 주장, owner 없는 운영·migration·보안 책임이나 중복 SOT가 남았는가
- 사용자 결정으로 표시한 항목이 실제 사용자 소유 기준에 의존하는가
- 결정 카드가 상세 절 없이 질문·대안 차이·추천·응답 형식을 전달하는가

완성 후보는 [`$verify-plan`](../verify-plan/SKILL.md)에 원래 목적, 확정 결정, 계획 artifact와
관련 source를 제공해 독립 감사한다. audit phase, 후보 동결, 보완·closure 횟수, 실패 뒤
상태 전이와 구현 인계는 작업 실행 workflow가 소유하며 이 skill에서 다시 정의하지 않는다.

계획 결과에는 다음이 포함돼야 한다.

- 계획 문서 경로와 구현 가능 판정
- 닫힌 설계 표면·주요 결정과 남은 사용자 소유 결정
- 작업·검증·전환·문서 책임의 연결
- `$verify-plan` 판정과 계획 checkpoint 상태

채팅 projection은 [완료 및 작업 보고 워크플로우](../../../docs/workflow/140-completion-reporting-workflow.md)에
맡기고 계획 결과와 구현 결과를 구분한다.
