# 개발 계획

사용자가 선택해야 할 내용을 근거·대안·추천과 함께 검토할 수 있는 계획 artifact를 만든다.
사용자가 필요한 제품·운영 결정을 직접 선택한 뒤에는 그 결정, 독립 source의 제약과
검증된 Agent 기술 결정을 연결해 구현자가 중대한 선택을 다시 하지 않고 실행할 수 있는
계획까지 구체화한다.
요청 해석, 권한, 공통 단위 상태, 병렬화, 실제 차단 판정과 final discovery·closure는
[작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)가 소유한다.
이 skill은 계획이 결과인 작업의 설계 판단과 문서 checkpoint만 소유한다.
계획 단계, 단계별 artifact와 closure·rollback은
[작업 문서 생명주기](../../../docs/work-items/100-work-item-lifecycle.md#계획-단계와-최소-artifact)를
소비하며 이 skill에서 다시 정의하지 않는다.

## 1. 계획 경계와 source

작업 실행 workflow가 계획을 현재 결과로 routing했을 때 primary로 사용한다. 구현 요청 중
계획 보완이 필요한 경우에는 workflow가 인계한 영향 범위의 설계 결정만 닫고 `$develop`의
복귀점을 유지한다.

계획을 작성하기 전에 다음을 실제 디스크에서 읽는다.

1. 저장소 `AGENTS.md`, 문서 router와 관련 workflow
2. 현재 work item, 같은 번호의 `-design`과 직접 연결된 결정 문서
3. 관련 code, test, 설정, schema, migration, 배포·운영 source
4. 현재 사실을 소유하는 domain·architecture·project·tech-stack SOT

계획 문서에는 [`$documentation`](../documentation/SKILL.md)을 적용한다. 이 저장소에서는
`docs/work-items/000-index.md`와 `docs/work-items/100-work-item-lifecycle.md`를 기준으로 기존
문서를 우선 갱신한다. 미확정 계획을 현재 사실 SOT로 승격하거나 Plan mode의 대화 목록을
최종 산출물로 대신하지 않는다.

## 2. 계획 입력과 현재 상태 조사

작업 실행 workflow가 잠근 목표·제약·범위·수용 기준을 계획 입력으로 받고 다음을 연결한다.

- 계획의 독자와 구현 후 관찰할 제품·기술 결과
- 현재 동작, 목표 동작, 확인된 간극과 authoritative source
- 요구사항별 수용 기준과 이를 입증할 구현·검증·문서 책임
- 사용자가 고정한 방법과 검토 가능한 구현 후보의 구분
- 외부 공식 계약, 저장소 규칙, 가정과 미확정의 구분

일부 snippet, 이름, 계획 문장이나 일반 Best Practice만으로 현재 상태를 추정하지 않는다.
현재성이 중요한 지원 상태·보안·비용·호환성은 최신 공식 1차 근거를 확인한다. 사용자가
제안한 방법보다 목표를 더 잘 달성하는 실행 가능한 대안이 있으면 비교와 추천에 포함한다.

## 3. 설계 표면을 포화하기

결과를 바꿀 수 있는 관련 표면을 세션 inventory에 `미조사`, `분석 중`, `사용자 선택됨`,
`source 제약`, `Agent 기술 결정 후보`, `Agent 기술 결정 검증됨`, `열린 사용자 결정`,
`해당 없음`으로 표시하고 근거·다음 판단을 연결한다. 전체 표를 repository에
보존하지 않고 consequential decision과 계획 결과만 문서화한다.

- 제품 동작, 사용자 흐름, 오류와 경계 조건
- API, event, file, CLI와 외부 계약
- 도메인 규칙, 상태 전이, 권한과 불변식
- data model, schema, constraint, migration과 보존
- transaction, 동시성, idempotency, retry, 보상과 rollback
- module, package, 계층, port/adapter와 의존 방향
- 기술, library, 외부 서비스와 공급자
- 인증·인가, secret, 개인정보, 위협과 감사
- 성능, 용량, 확장, cache와 자원 한도
- 배포, 설정, 관측성, 장애 대응과 복구
- test 전략, fixture, 검증 환경과 품질 gate
- 호환성, 전환, 점진 배포, 되돌리기와 제거
- 문서, 운영 책임, 소유권과 영구 SOT

하위 계획 다수를 무효화할 수 있는 공통 전제는 downstream 상세화 전에 가장 작은 실제
source·공식 근거·대표 정상 경로·대표 반례로 확인한다. 전제가 성립하지 않으면 그 전제에서
파생한 파일별 계획을 만들지 않고 설계 표면과 대안으로 돌아간다. 판정에 외부 입력이
필요하면 그 사실과 영향은 계획 결과에 제공하되, 실제 차단 여부는 작업 실행 workflow에
인계한다.

## 4. 결정 소유권과 결정 카드

결과에 의미 있는 차이를 만드는 값은 다음 권위 중 하나로 분류한다. 계획 문서 작성 요청,
상세화 요청, 검증·commit·push 요청, 계획을 잘 작성해 달라는 평가와 `계획을 확정해` 같은
artifact 상태 지시는 그 안에 포함된 사용자 소유 추천값의 선택을 뜻하지 않는다.

- **사용자 확정 요구**: 이미 정한 목표·제약·제외·수용 기준이므로 다시 선택지로 만들지 않는다.
- **외부·저장소 제약과 사실**: 공식 규격, 현재 source나 사용자 확정 상위 결정이 허용 범위를
  제한하면 근거와 파생 관계를 기록한다. 이는 Agent나 사용자가 새로 선택한 결정이 아니다.
- **Agent 기술 결정**: API·schema·module·test처럼 specialist가 Agent 책임으로 분류한 기술
  선택은 현재 목표와 source에서 대안·trade-off를 비교해 추천하고 계획의 기술 결정으로
  닫을 수 있다. 사용자 선택으로 귀속하거나 승인 질문으로 넘기지 않으며 독립 검증과 재검토
  조건을 연결한다.
- **열린 사용자 결정**: 제품 동작·범위·UX 우선순위, 법·개인정보 감수 수준, 예산·외부 계약·
  운영 책임, 출시 범위·일정처럼 프로젝트 외부 판단이 필요하고 source가 exact 값을 고정하지
  못한 경우에만 사용자가 선택할 수 있는 형태로 제공한다.

기술 선택의 변경 비용이 크다는 사실만으로 사용자 결정을 만들지 않는다. 기술안이 제품 범위,
외부 계약이나 운영 책임을 함께 선택해야만 닫히면 그 외부 판단만 사용자 결정으로 분리하고,
답을 받은 뒤 Agent가 기술안을 닫는다. 사용자가 구현 자체를 명시적으로 요청한 별도
generation에서는 작업 실행 workflow가 `$develop`로 routing하며, 그때 닫은 기술 결론도
사용자가 선택한 결정으로 기록하지 않는다.

열린 사용자 결정은 상세 설계를 읽지 않아도 답할 수 있는 카드로 준비한다.

1. 결정할 질문
2. 사용자 소유 근거
3. 배경과 제약
4. 실제 채택 가능한 2~3개 대안
5. 결과를 바꾸는 비교 축과 차이
6. 추천안과 이유
7. 영향·위험·재검토 조건
8. 한 줄로 답할 수 있는 exact 응답 형식

사용자 결정으로 기록하려면 현재 또는 직접 선행 원문에서 `결정 차원 → 선택한 exact 값 →
긍정 선택 표현`을 모두 복원할 수 있어야 한다. 사용자가 여러 추천을 하나의 exact 묶음으로
승인하면 그 묶음만 선택된 것으로 기록하고 인접 추천으로 전파하지 않는다. 원문 일부인
`확정해도 된다`, `그 계획을 확정해` 같은 상태 표현만 떼거나 Agent가 작성한 계획·요약·검증
결과를 승인 source로 사용하지 않는다. 추천 묶음 전체를 그대로 선택한다는 명시 표현은 그
묶음의 exact 범위만 승인 source로 사용할 수 있다. 승인되지 않은 추천은 결정 차원별 권위를
다시 분류하며, API·schema·module 같은 Agent 기술 결정을 열린 사용자 결정으로 바꾸지 않는다.

비교 축은 정확성, data·security, 안정성·복구, 유지보수성, 성능·자원, 호환성·migration,
test·관측성, 비용·소유권과 사용자 경험 중 결론을 바꾸는 것만 사용한다. 결정 카드의
제시 시점과 묶음이 공통 차단 gate를 충족하는지는 작업 실행 workflow가 판정한다.
첫 결정 카드를 제시하기 전에 현재 단계 closure에 필요한 사용자 소유 결정을 모두 찾는다.
현재 source와 닫힌 선행 결과만으로 선택지·차이·추천을 만들 수 있는 결정은 작업 문서
생명주기의 현재-stage 결정 블록 하나에 전부 넣는다. 앞 블록의 exact 선택 없이는 질문이나
실제 대안을 만들 수 없는 결정만 다음 의존 블록으로 보류한다. 단계별 진행 지시를 같은
단계의 카드 `0..1` 지시로 바꾸지 않는다. 현재 단계 안의 서로 독립적인 결정도 한 번에
하나씩 묻도록 사용자가 exact 범위를 명시한 경우에만 작업 실행 workflow의 예외 cadence를
적용한다. 블록의 답은 현재 단계 결과에 한 번에 반영하고 source-first로 대조한 뒤 다음
의존 블록이나 다음 단계를 연다.

후속 피드백은 [설계 피드백 워크플로우](../../../docs/workflow/120-design-feedback-workflow.md)로
정규화한다. 직접 취소·대체되지 않은 사용자 확정 요구와 결정은 같은 값·권위로 유지한다.
변경 후보에서 확정 결정이 삭제·강등·재전환되면 이를 허용하는 더 최신 사용자 결정이나
독립 authoritative source를 요구한다.

## 5. 현재 단계 계획 artifact

작성 전에 본문의 `상태`와 `계획 단계`를 읽고 작업 문서 생명주기가 허용한 artifact와
section만 갱신한다. 선행 단계가 닫히기 전에는 다음 단계 문서·heading·해결 후보·task를
미리 만들지 않는다.

- `결과 정의`에서는 work item 본문 하나에 유형별 제품·문제·조사 결과, 범위, 요구사항·
  수용 기준과 현재 사용자 결정만 쓴다. API·schema·module·transaction, 해결 대안·기술
  계약, 구현·수정·실험 방법, task와 test 상세는 session inventory에만 두고 저장하지 않는다.
- `해결 설계`에서는 결과 정의 closure를 다시 확인한 뒤 설계 표면을 닫는다. 별도
  `-design`은 작업 문서 생명주기의 조건을 모두 만족할 때만 만들고, task·순서·test 실행을
  넣지 않는다.
- `실행 계획`에서는 해결 설계 closure를 확인한 뒤 새 문서를 만들지 않고 본문에만 검증
  가능한 결과 단위와 실행 책임을 추가한다.
- `계획 완료`는 실행 계획 검증과 상태 전이 권한이 모두 닫힌 결과만 투영한다.

사용자 결정의 추천을 선택했다고 가정한 다음 단계 상세를 작성하지 않으며, `확정 결정`,
`남은 결정 없음`이나 동등한 구현 지시로 승격하지 않는다. Agent 기술 결정은 해결 설계가
활성화된 뒤 근거·대안·trade-off·재검토 조건으로 닫고 사용자 결정으로 표시하지 않는다.

설계 준비도와 구현 인계는 작업 실행 workflow의 `설계 준비도와 구현 입장`을 소비한다.
실행 계획 단계에서 구현 task 사이의 선행 관계는 task 번호나 producer 역할명이 아니라
`앞 task의 exact 결과 → 처음 그 결과를 소비하는 뒤 task의 exact 단계`로 연결하며, 이
관계가 없으면 독립·합류 시 필요·권장 순서를 구분한다.

실행 계획은 사용자가 선택한 결정, 외부·저장소 제약과 검증된 Agent 기술 결정으로 설계
표면이 닫힌 범위에서만 작업을 파일 목록이 아니라 독립적으로 검증 가능한 결과 단위로
작성한다. 각 작업은
다음을 포함한다.

1. 제목, 목표와 연결된 요구사항·결정
2. 선행 조건과 의존 결과
3. 수행 내용과 영향받는 경계
4. 오류·보안·data·운영 고려사항
5. test·검증 명령과 통과 기준
6. 문서와 영구 SOT 반영
7. 완료 뒤 관찰 가능한 결과
8. rollout, rollback 또는 복구 방법

계획 전체에는 요구사항·수용 기준, 권위 source가 연결된 사용자 결정 색인, 작업 의존 관계,
negative·회귀 test,
migration·호환성, 운영 검증과 범위 밖 항목의 재검토 조건을 연결한다. TDD 대상은 실패
test, 최소 구현, refactor와 회귀 검증 순서를 반영한다. 근거 없는 일정 숫자는 작성하지 않는다.

work item 본문과 조건부 `-design`의 정확한 책임은 작업 문서 생명주기를 따른다. 대화 원문,
승인 표현, 내부 사고, 임시 inventory, dirty 상태와 반복 검증 기록은 저장하지 않는다. 상세
판단이 커도 현재 결과 정의에서 사용자가 결정할 질문·대안·추천을 첫 화면에서 복원할 수
있게 한다.

사용자 검토용 첫 화면, heading과 결정 카드는 사용자가 무엇을 선택하고 어떤 결과가
달라지는지를 일상어로 먼저 쓴다. 직접 선행 문맥에서 이해가 확인되지 않은 기술 명사는
최초 사용 문장 안에서 concrete 대상·행동으로 설명하거나 쉬운 표현으로 바꾸고, 사용자
판단에 필요하지 않으면 기술 상세로 옮긴다. 뒤쪽 용어집, 다른 미정의 영어 이름이나 API·DB
목록은 첫 설명을 대신하지 않는다. Exact API path·field·enum 같은 구현 계약 literal은
보존하되 그 역할이 사용자 판단에 필요하면 같은 단위에서 쉬운 뜻을 붙인다.

## 6. 계획 문서 checkpoint

계획 문서가 요청 결과이면 작업 실행 workflow가 허용한 상시 예외로 검증된 현재
checkpoint를 local commit한다.

1. 현재 계획 상태를 work item, 현재 단계에서 허용된 `-design`과 필수 router에 동기화한다.
   미확정 계획을 `Planned`나 완료로 승격하지 않는다.
2. `$documentation`으로 source·owner·링크·번호와 결정 delta를 검증한다.
3. 이번 checkpoint의 exact path·hunk만
   [커밋 워크플로우](../../../docs/workflow/300-commit-workflow.md)로 stage·commit한다.
4. 다른 작업의 dirty hunk와 안전하게 분리할 수 없으면 checkpoint를 만들지 않는다.
5. commit object와 잔여 dirty를 확인한다. push는 별도 명시 권한이 있을 때만 수행한다.

최초 안정된 `Proposed`, 사용자 결정 반영과 최종 `Planned` 후보처럼 다음 작업자가 복원할
필요가 있는 상태만 checkpoint로 남긴다. `Planned` 후보는 모든 사용자 소유 값이 사용자
선택 또는 독립 source 제약으로 닫히고, Agent 소유 기술 결정은 source·대안·trade-off와 함께
독립 검증을 통과해야 한다. 독립 검증은 사용자 선택을 대신하거나 새 사용자 권위를 만들지
않는다.

## 7. 계획 검증과 산출물

자체 검토에서는 현재 계획 단계에 허용된 축만 열고 다음 반례를 찾는다. 구현·검증·전환
항목은 실행 계획 단계에서만 필수이며 앞 단계에서는 다음 단계 상세가 생겼는지를 대조한다.

- 구현자가 중대한 제품·기술 선택을 새로 해야 하는가
- 현재 계획 단계에서 허용되지 않은 다음 단계 artifact·section·후보 상세가 생겼는가
- 정상 흐름뿐 아니라 잘못된 입력, 권한 거부, 중복, 동시성, 부분 실패와 복구가 빠졌는가
- 기존 data·API·설정·배포에서 목표 상태로의 전환과 rollback이 빠졌는가
- 모든 요구가 구현 작업·검증·문서에 연결되고 각 작업의 결과를 관찰할 수 있는가
- 구현 후보가 설계 closure보다 현재·다음 실행 단위로 승격되지 않았고, 각 필수 선행 edge가
  producer의 exact 결과와 최초 exact consumer 단계에 연결되는가
- test 불가능한 주장, owner 없는 운영·migration·보안 책임이나 중복 SOT가 남았는가
- 사용자 결정으로 표시한 항목이 실제 사용자 소유 기준에 의존하는가
- 각 사용자 결정의 exact 값과 긍정 선택 표현이 계획 후보가 아닌 원문 source에 연결되는가
- 열린 사용자 결정의 Agent 추천이나 verifier 결론이 사용자 선택·`남은 결정 없음`으로
  승격되지 않았고, Agent 기술 결정은 사용자 선택으로 잘못 귀속되지 않았는가
- 결정 카드가 상세 절 없이 질문·대안 차이·추천·응답 형식을 전달하는가
- 첫 화면·heading·결정 카드의 새 용어가 `선행 이해 확인 / 최초 문장에서 일상어로 설명 /
  쉬운 표현으로 교체·기술 상세로 이동` 중 하나이며, exact 계약 literal을 불필요하게
  번역·삭제하지 않았는가

완성 후보는 [`$verify-plan`](../verify-plan/SKILL.md)에 원래 목적, 확정 결정, 계획 artifact와
관련 source를 제공해 독립 감사한다. audit phase, 후보 동결, 보완·closure 횟수, 실패 뒤
상태 전이와 구현 인계는 작업 실행 workflow가 소유하며 이 skill에서 다시 정의하지 않는다.

계획 결과에는 다음이 포함돼야 한다.

- 계획 문서 경로, 현재 계획 단계와 해당 단계 closure 상태
- 현재 단계까지 닫힌 표면·주요 결정과 남은 사용자 소유 결정
- 실행 계획 단계이면 작업·검증·전환·문서 책임의 연결과 구현 가능 판정
- 적용한 검증 판정과 계획 checkpoint 상태

채팅 projection은 [완료 및 작업 보고 워크플로우](../../../docs/workflow/140-completion-reporting-workflow.md)에
맡기고 계획 결과와 구현 결과를 구분한다.
