# 개발 계획

사용자가 선택해야 할 내용을 근거·대안·추천과 함께 검토할 수 있는 계획 artifact를 만든다.
사용자가 필요한 제품·운영 값을 직접 선택하고 Agent가 명확한 기술값을 선택한 뒤에는 그
선택, 독립 source의 제약과 검증을 현재 단계 결과 후보에 연결한다. 어느 선택도 사용자
확정으로 대신하지 않으며, 사용자가 exact 현재 단계 결과를 확정한 뒤에만 다음 단계가
소비할 계획으로 동결한다. 값 확정과 단계 확정은 다른 의미 상태지만 별도 왕복을 강제하지
않는다. 마지막 열린 값을 반영하라는 원문이 무모호한 현재 단계 후보까지 닫으면 같은
원문으로 단계를 전환하고, 실제로 애매한 차원이 있을 때만 한 블록으로 묻는다.
요청 해석, 권한, 공통 단위 상태, 병렬화, 실제 차단 판정과 final discovery·closure는
[작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)가 소유한다.
이 skill은 계획이 결과인 작업의 설계 판단과 문서 checkpoint만 소유한다.
계획 단계, 단계별 artifact와 closure·rollback은
[작업 문서 생명주기](../../../docs/work-items/100-work-item-lifecycle.md#계획-단계와-최소-artifact)를
소비하며 이 skill에서 다시 정의하지 않는다.

## 1. 계획 경계와 source

작업 실행 workflow가 계획을 현재 결과로 routing했을 때 primary로 사용한다. 구현 요청 중
계획 보완이 필요한 경우에는 workflow가 인계한 영향 범위의 설계 결정만 닫고 `$develop`의
복귀점을 유지한다.

계획을 작성하기 전에 다음을 실제 디스크에서 읽는다.

1. 저장소 `AGENTS.md`, 문서 router와 관련 workflow
2. 현재 work item, 같은 번호의 `-design`과 직접 연결된 결정 문서
3. 관련 code, test, 설정, schema, migration, 배포·운영 source
4. 현재 사실을 소유하는 domain·architecture·project·tech-stack SOT

계획 문서에는 [`$documentation`](../documentation/SKILL.md)을 적용한다. 이 저장소에서는
`docs/work-items/000-index.md`와 `docs/work-items/100-work-item-lifecycle.md`를 기준으로 기존
문서를 우선 갱신한다. 미확정 계획을 현재 사실 SOT로 승격하거나 Plan mode의 대화 목록을
최종 산출물로 대신하지 않는다.

## 2. 계획 입력과 현재 상태 조사

작업 실행 workflow가 잠근 목표·제약·범위·수용 기준을 계획 입력으로 받고 다음을 연결한다.

- 계획의 독자와 구현 후 관찰할 제품·기술 결과
- 현재 동작, 목표 동작, 확인된 간극과 authoritative source
- 요구사항별 수용 기준과 이를 입증할 구현·검증·문서 책임
- 사용자 목표·성공 조건별로 선택한 기술 결정이 충족·영향 없음임을 보이는 목표 보존 identity
- 사용자가 고정한 방법과 검토 가능한 구현 후보의 구분
- 외부 공식 계약, 저장소 규칙, 가정과 미확정의 구분

일부 snippet, 이름, 계획 문장이나 일반 Best Practice만으로 현재 상태를 추정하지 않는다.
현재성이 중요한 지원 상태·보안·비용·호환성은 최신 공식 1차 근거를 확인한다. 사용자가
제안한 방법보다 목표를 더 잘 달성하는 실행 가능한 대안이 있으면 비교와 추천에 포함한다.
변경량·migration 비용·현재 구조 보존은 목표를 충족한 대안 사이에서만 비교한다. 모든 안이
목표를 일부 약화하면 Agent 기술 결정으로 닫지 않고 약화되는 성공 조건·영향·대안·추천을
사용자 결정 카드로 먼저 반환한다.

## 3. 설계 표면을 포화하기

결과를 바꿀 수 있는 관련 표면을 세션 inventory에 `미조사`, `분석 중`, `Agent 추천`,
`사용자 선택`, `사용자 값 확정`, `Agent 기술 선택`, `source 제약`, `검증됨`, `사용자 단계 확정`,
`열린 사용자 결정`, `해당 없음`으로 표시하고 추천 주체, 선택 주체·값, 확정 범위·source와
다음 판단을 각각 연결한다. 전체 표를 repository에
보존하지 않고 consequential decision과 계획 결과만 문서화한다.

- 제품 동작, 사용자 흐름, 오류와 경계 조건
- API, event, file, CLI와 외부 계약
- 도메인 규칙, 상태 전이, 권한과 불변식
- data model, schema, constraint, migration과 보존
- transaction, 동시성, idempotency, retry, 보상과 rollback
- module, package, 계층, port/adapter와 의존 방향
- 기술, library, 외부 서비스와 공급자
- 인증·인가, secret, 개인정보, 위협과 감사
- 성능, 용량, 확장, cache와 자원 한도
- 배포, 설정, 관측성, 장애 대응과 복구
- test 전략, fixture, 검증 환경과 품질 gate
- 호환성, 전환, 점진 배포, 되돌리기와 제거
- 목표 구조와 독립적으로 선택 가능한 전환 방식. 후보별 임시 trigger·function·column·
  compatibility adapter·routing·dual write·backfill, 추가 migration·release·관찰·contract 제거,
  data 폐기와 rollback 책임
- 문서, 운영 책임, 소유권과 영구 SOT

하위 계획 다수를 무효화할 수 있는 공통 전제는 downstream 상세화 전에 가장 작은 실제
source·공식 근거·대표 정상 경로·대표 반례로 확인한다. 전제가 성립하지 않으면 그 전제에서
파생한 파일별 계획을 만들지 않고 설계 표면과 대안으로 돌아간다. 판정에 외부 입력이
필요하면 그 사실과 영향은 계획 결과에 제공하되, 실제 차단 여부는 작업 실행 workflow에
인계한다.

## 4. 결정 소유권과 결정 카드

결정 ID나 기능명을 원자 단위로 먼저 만들지 않는다. 최초 사용자 요구, authoritative source,
실제 후보와 추천 결과에 등장하는 결과값·default·owner·경계·표현·저장 위치·version·운영
수단을 inventory하고 다음 분리 질문을 각 값에 적용한다.

> 다른 값을 모두 고정한 채 이 값만 바꿔도 유효한 후보가 되거나, 다른 consumer·영향·재검토
> 조건이 생기는가?

하나라도 성립하면 별도 결정 축과 별도 ID다. 같은 기능·계층·구현 단위에 있고 한 번에 답할
수 있다는 사실은 결합 근거가 아니다. 열린 사용자 결정만 활성 카드, Agent 기술 선택은 비교
결정 block, 사용자 확정 요구는 고정 입력·닫힌 결과, source 파생은 source 파생 block, 입력
부재는 gate block으로 표현한다. 여러 열린 사용자 축은 하나의 활성 결정 block과 결합 응답
형식에 함께 둘 수 있지만, 각 축은 질문·대안·권위·선택·영향을 소유하는 별도 카드여야 한다.
둘 이상의 값을 하나로 유지하려면 한 값만 바꾼 조합이 source나 논리상 성립하지 않는다는
불가분 근거를 structure map에 기록한다. 비교 결정·활성 카드는 하나의 공통 질문·option set·
owner·consumer·재검토 조건, 사용자 확정 요구·고정 입력은 하나의 authoritative 요구·적용
범위·consumer·재검토 조건, source 파생은 하나의 source·파생 규칙·consumer·재검토 조건,
입력 부재 gate는 하나의 부족 입력·입력 owner·획득/재개 조건·처음 막는 consumer를 가져야 한다.

결과에 의미 있는 차이를 만드는 값은 다음 권위 중 하나로 분류한다. 계획 문서 작성 요청,
상세화 요청, 검증·commit·push 요청, 계획을 잘 작성해 달라는 평가와 `계획을 확정해` 같은
artifact 상태 지시는 그 안에 포함된 사용자 소유 추천값의 선택을 뜻하지 않는다.

- **사용자 확정 요구**: 이미 정한 목표·제약·제외·수용 기준이므로 다시 선택지로 만들지 않는다.
- **외부·저장소 제약과 사실**: 공식 규격, 현재 source나 사용자 확정 상위 결정이 허용 범위를
  제한하면 근거와 파생 관계를 기록한다. 이는 Agent나 사용자가 새로 선택한 결정이 아니다.
- **Agent 기술 선택**: API·schema·module·test처럼 specialist가 Agent 책임으로 분류한 기술
  값은 현재 목표와 source에서 대안·trade-off를 비교한다. 유지보수성·완결성·확장성 등
  관련 축에서 한 값이 명확하면 Agent가 추천하고 선택하며, 사용자 선택으로 귀속하거나
  선택 질문으로 넘기지 않는다. 독립 검증과 재검토 조건을 연결하되 이 선택을 사용자 확정이나
  단계 closure로 기록하지 않는다.
- **열린 사용자 결정**: 제품 동작·범위·UX 우선순위, 법·개인정보 감수 수준, 예산·외부 계약·
  운영 책임, 출시 범위·일정처럼 프로젝트 외부 판단이 필요하고 source가 exact 값을 고정하지
  못한 경우에만 사용자가 선택할 수 있는 형태로 제공한다.

기술 선택의 변경 비용이 크다는 사실만으로 사용자 결정을 만들지 않는다. 기술안이 제품 범위,
외부 계약이나 운영 책임을 함께 선택해야만 닫히면 그 외부 판단만 사용자 결정으로 분리하고,
답을 받은 뒤 Agent가 기술안을 선택한다. 사용자가 구현 자체를 명시적으로 요청한 별도
generation에서는 작업 실행 workflow가 `$develop`로 routing하며, 그때 닫은 기술 결론도
사용자가 선택한 결정으로 기록하지 않는다.

열린 사용자 결정은 상세 설계를 읽지 않아도 답할 수 있는 카드로 준비한다.

1. 결정할 질문
2. 사용자 소유 근거
3. 배경과 제약
4. 실제 채택 가능한 2~3개 대안
5. 결과를 바꾸는 비교 축과 차이
6. 추천안과 이유
7. 영향·위험·재검토 조건
8. 한 줄로 답할 수 있는 exact 응답 형식

사용자 결정으로 기록하려면 현재 또는 직접 선행 원문에서 `결정 차원 → 선택한 exact 값 →
긍정 선택 표현`을 모두 복원할 수 있어야 한다. 사용자가 여러 추천을 하나의 exact 묶음으로
승인하면 그 묶음만 선택된 것으로 기록하고 인접 추천으로 전파하지 않는다. 원문 일부인
`확정해도 된다`, `그 계획을 확정해` 같은 상태 표현만 떼거나 Agent가 작성한 계획·요약·검증
결과를 승인 source로 사용하지 않는다. 추천 묶음 전체를 그대로 선택한다는 명시 표현은 그
묶음의 exact 범위만 승인 source로 사용할 수 있다. 승인되지 않은 추천은 결정 차원별 권위를
다시 분류하며, API·schema·module 같은 Agent 기술 선택을 열린 사용자 결정으로 바꾸지 않는다.

값 선택·값 확정과 단계 확정은 권위 범위를 분리해 복원하되 별도 source·메시지를 기계적으로
강제하지 않는다. 사용자가 exact 값이나 결정 블록을 채택·반영하도록 승인하면 그 범위를
사용자 값 확정으로 동결한다. 그 값이 마지막 열린 결정이고 현재 단계 후보가 앞서 제시한
결정 결과와 닫힌 source에서 하나로 복원되며, 반영 중 새 사용자 소유 결과·선택지가 생기지
않으면 같은 원문을 단계 확정으로도 인계하고 다음 단계를 연다. 미답 결정, 모호한 대상이나
새 사용자 판단이 있으면 단계 전체로 전파하지 않고 그 항목을 한 블록으로 묻는다. 값만 고른
응답·Agent 기술 선택·source 제약·verifier 판정은 단계 확정이 아니다. `이대로 확정`,
`그대로 반영`, `다음 단계 진행`처럼 exact 후보의 채택과 소비를 긍정한 원문에는 추가
재확인을 요구하지 않는다.

비교 축은 정확성, data·security, 안정성·복구, 유지보수성, 성능·자원, 호환성·migration,
test·관측성, 비용·소유권과 사용자 경험 중 결론을 바꾸는 것만 사용한다. 결정 카드의
제시 시점과 묶음이 공통 차단 gate를 충족하는지는 작업 실행 workflow가 판정한다.
첫 결정 카드를 제시하기 전에 현재 단계 closure에 필요한 사용자 소유 결정을 모두 찾는다.
현재 source와 닫힌 선행 결과만으로 선택지·차이·추천을 만들 수 있는 결정은 작업 문서
생명주기의 현재-stage 결정 블록 하나에 전부 넣는다. 앞 블록의 exact 선택 없이는 질문이나
실제 대안을 만들 수 없는 결정만 다음 의존 블록으로 보류한다. 단계별 진행 지시를 같은
단계의 카드 `0..1` 지시로 바꾸지 않는다. 현재 단계 안의 서로 독립적인 결정도 한 번에
하나씩 묻도록 사용자가 exact 범위를 명시한 경우에만 작업 실행 workflow의 예외 cadence를
적용한다. 값만 선택하고 artifact 반영을 요청하지 않은 답은 세션 후보만 갱신하며 writer를 호출하지
않고, 이미 답한 값은 제외한 남은 결정을 한 블록으로 제시한다. 값의 채택·반영 요청이 있는
경우에만 artifact 후보를 한 번에 반영해 source-first로 대조한다. 대조 뒤 남은 결정이나 새
사용자 소유 결과가 있으면 exact 범위로 한 번에 제시해 묻는다. 없고 마지막 답변이 값의
채택·반영을 긍정했다면 같은 원문으로 현재 단계를 닫고 다음 의존 블록이나 다음 단계를 연다.

같은 목표 상태에 도달하는 직접 전환·호환 전환·환경 초기화 전환이 둘 이상이면 전환 방식을
목표 구조와 별도 결정 축으로 만든다. 후보에만 필요한 임시 DB 객체·dual write·backfill,
compatibility adapter·routing, 추가 release·migration·관찰·제거 작업은 조건부 후손으로
숨기지 않고 선택 전 비교표의 실제 비용과 실패 표면으로 공개한다. 일회성 초기화 조건은 공용
운영 절차로 일반화하지 않는다.

후속 피드백은 [설계 피드백 워크플로우](../../../docs/workflow/120-design-feedback-workflow.md)로
정규화한다. 직접 취소·대체되지 않은 사용자 확정 요구와 결정은 같은 값·권위로 유지한다.
변경 후보에서 확정 결정이 삭제·강등·재전환되면 이를 허용하는 더 최신 사용자 결정이나
독립 authoritative source를 요구한다.

## 5. 현재 단계 계획 artifact

작성 전에 본문의 `상태`와 `계획 단계`를 읽고 작업 문서 생명주기가 허용한 artifact와
section만 갱신한다. 선행 단계가 닫히기 전에는 다음 단계 문서·heading·해결 후보·task를
미리 만들지 않는다.

- `결과 정의`에서는 work item 본문 하나에 유형별 제품·문제·조사 결과, 범위, 요구사항·
  수용 기준과 현재 사용자 결정만 쓴다. API·schema·module·transaction, 해결 대안·기술
  계약, 구현·수정·실험 방법, task와 test 상세는 session inventory에만 두고 저장하지 않는다.
- `해결 설계`에서는 결과 정의 closure를 다시 확인한 뒤 설계 표면을 닫는다. 별도
  `-design`은 작업 문서 생명주기의 조건을 모두 만족할 때만 만들고, task·순서·test 실행을
  넣지 않는다.
- `실행 계획`에서는 해결 설계 closure를 확인한 뒤 새 문서를 만들지 않고 본문에만 검증
  가능한 결과 단위와 실행 책임을 추가한다.
- `계획 완료`는 실행 계획 검증과 상태 전이 권한이 모두 닫힌 결과만 투영한다.

사용자 결정의 추천을 선택했다고 가정한 다음 단계 상세를 작성하지 않으며, `확정 결정`,
`남은 결정 없음`이나 동등한 구현 지시로 승격하지 않는다. Agent 기술 선택은 해결 설계가
활성화된 뒤 근거·대안·trade-off·재검토 조건으로 선택하고 사용자 결정으로 표시하지 않는다.
사용자 선택과 Agent 기술 선택을 모두 반영해도 현재 단계 결과에 대한 사용자 확정 전에는
다음 단계 artifact를 만들거나 상태를 전환하지 않는다. 다만 작업 실행 workflow의 무모호
closure 조건을 충족한 마지막 값의 반영 요청은 그 단계 확정을 함께 제공하므로 별도 확인을
기다리지 않는다.

설계 준비도와 구현 인계는 작업 실행 workflow의 `설계 준비도와 구현 입장`을 소비한다.
실행 계획 단계에서 구현 task 사이의 선행 관계는 task 번호나 producer 역할명이 아니라
`앞 task의 exact 결과 → 처음 그 결과를 소비하는 뒤 task의 exact 단계`로 연결하며, 이
관계가 없으면 독립·합류 시 필요·권장 순서를 구분한다.

실행 계획은 사용자가 확정한 해결 설계 결과 안의 사용자 선택, 외부·저장소 제약과 검증된
Agent 기술 선택으로 설계 표면이 닫힌 범위에서만 작업을 파일 목록이 아니라 독립적으로
검증 가능한 결과 단위로
작성한다. 각 작업은
다음을 포함한다.

1. 제목, 목표와 연결된 요구사항·결정
2. 선행 조건과 의존 결과
3. 수행 내용과 영향받는 경계
4. 오류·보안·data·운영 고려사항
5. test·검증 명령과 통과 기준
6. 문서와 영구 SOT 반영
7. 완료 뒤 관찰 가능한 결과
8. rollout, rollback 또는 복구 방법

계획 전체에는 요구사항·수용 기준, 권위 source가 연결된 사용자 결정 색인, 작업 의존 관계,
negative·회귀 test,
migration·호환성, 운영 검증과 범위 밖 항목의 재검토 조건을 연결한다. TDD 대상은 실패
test, 최소 구현, refactor와 회귀 검증 순서를 반영한다. 근거 없는 일정 숫자는 작성하지 않는다.

work item 첫 화면에는 현재 사용자와 다음 작업자가 전체 흐름, 현재 인계와 각자의 책임을
복원할 수 있는 단계 지도를 반드시 둔다. 이 지도는 공통 workflow 이름을 옮기는 checklist가
아니라 현재 작업에서 실제 결과가 만들어지는 순서를 보여 준다.

1. 최초 범위·결정부터 설계, 구현 가능한 계획, 계획 검증, 개발, 결과 검증, 영구 SOT와 Git
   마무리까지 현재 작업에 적용되는 전체 단계
2. 각 단계의 `완료`, `현재`, `다음`, `후속`, `조건부`, `해당 없음` 상태와 판정 근거
3. 현재 단계의 입력·산출물·완료 조건과 현재 완성 여부
4. 현재 단계 안에서 아직 남은 즉시 다음 작업, 그 작업의 실행자, 그 결과를 처음 소비하는
   대상과 완료 뒤
   관찰 가능한 결과
5. 사용자가 지금 제공해야 할 결정·입력·외부 행동 또는 `사용자 작업 없음`, 후자인 경우
   Agent가 질문 없이 이어서 수행할 exact 작업
6. 현재 단계가 모두 끝난 뒤 넘어갈 다음 단계와 전환 조건
7. 제품 기능·정책, 도메인, module, API, schema·migration, 보안, infrastructure, data 운영,
   test·복구와 문서 표면의 현재 위치 또는 재검토 조건

표면 이름을 자동으로 직렬 phase로 만들지 않는다. 선행 결과 없이 시작할 수 있는 표면은
독립 트랙으로, 서로의 결과가 적용·연동·통합 검증에서 처음 필요한 지점은 합류점으로 쓴다.
구현 방식에 따라 달라지는 표면은 조건부로 남기며, 언급되지 않은 표면을 해당 없음으로
간주하지 않는다. `Proposed`는 열린 결정과 후보를 포함한 저상세 전체 지도를, `Planned`는
확정된 결과 단위·검증·전환 조건을 보여 준다. 결정이나 상태를 갱신할 때 현재 단계와 다음
단계를 같은 변경에서 갱신한다.

section과 표를 쓰기 전에 독자가 그 단위에서 답할 질문 하나와 분류 축 하나를 고정한다.
제목이 현재 상태를 묻는다면 완료·진행·미착수와 다음 작업만 답하고, 무엇을 만들지 설명하는
기능·범위, 왜 선택했는지 설명하는 결정·원칙과 재검토 조건을 같은 상태 값으로 섞지 않는다.
`상태` 열은 선언한 하나의 상태 집합만 사용한다. 설계 성숙도, 정보 종류, 재검토 시점처럼
다른 차원이 필요하면 이름이 맞는 별도 열이나 section으로 분리한다.

현재 단계에 미완료 결과가 있으면 이후 lifecycle 단계를 `다음 작업`으로 쓰지 않는다. 현재
단계 안에서 바로 만들 exact 결과와 그 완료 조건을 먼저 쓰고, 현재 단계가 모두 닫힌 뒤의
다음 단계는 별도로 표시한다. 기능 요약·결정 근거·공통 workflow 원칙은 각 canonical owner에
두고 진행 지도에는 현재 작업에 적용된 결과·상태·전환만 투영한다.

`남은 사용자 결정 없음`을 사용자가 할 일을 추론하게 하는 간접 표현으로 사용하지 않는다.
현재 단계의 완성 여부, 즉시 다음 작업의 실행자와 사용자 행동 유무를 같은 진행 단위에
직접 표시한다. 사용자 행동이 없고 현재 계획 결과가 미완료이면 문서 checkpoint·검증·보고를
종료 지점으로 쓰지 않고, 작업 실행 workflow의 operation map에 남은 즉시 다음 설계 결과로
복귀한다.

work item 본문은 현재 계획 결과와 확정 결정 색인을, `-design`은 장기 복원이 필요한 대안
비교와 구현 계약을 소유한다. 대화 원문, 승인 표현, 내부 사고, 임시 inventory, dirty 상태와
반복 검증 기록은 저장하지 않는다. 상세 판단이 커도 사용자가 결정할 질문·대안·추천을 첫
화면에서 복원할 수 있게 한다.

파일명, 접미사, 본문·companion 구분이나 활성 사용자 값 결정의 유무와 관계없이 모든 계획
목적 artifact의 첫 화면에서 현재 결론과 다음 행동을 복원할 수 있어야 한다. 제목과 상태·계획
단계 바로 다음, 첫 배경·문서 경계·상세 결정 전에 다음 source-backed 현재 상태를 보여 준다.

- 현재 단계·결론, 닫힌 결과와 남은 gate
- 다음 안정 handoff에 남을 gate identity·terminal 상태와 모든 선행 gate·checkpoint 뒤 처음
  행동할 안정 actor·exact 행동
- 그 안정 actor가 사용자이면 exact 질문, 선택지·결과 차이, 추천·근거와 응답 형식
- 현재 행동 뒤 결과와 다음 단계 전환 조건

상세 결정과 근거는 해당 section으로 연결하되 현재 행동을 알기 위해 하단이나 다른 문서를
먼저 읽게 하지 않는다. 모든 gate가 닫혔으면 완료 결론과 다음 허용 행동만 표시하고 새
선택지·응답 형식·중복 확정을 만들지 않는다. 검증·checkpoint가 닫힌 exact candidate의
결론·gate·안정 actor·다음 행동이 바뀌면 다음 actor 인계 전에 첫 화면을 갱신한다. 진행 중
writer·reviewer·Git actor와 phase는 작업 실행 receipt에만 둔다.

사용자 검토용 첫 화면, heading과 결정 카드는 사용자가 무엇을 선택하고 어떤 결과가
달라지는지를 일상어로 먼저 쓴다. 직접 선행 문맥에서 이해가 확인되지 않은 기술 명사는
최초 사용 문장 안에서 concrete 대상·행동으로 설명하거나 쉬운 표현으로 바꾸고, 사용자
판단에 필요하지 않으면 기술 상세로 옮긴다. 뒤쪽 용어집, 다른 미정의 영어 이름이나 API·DB
목록은 첫 설명을 대신하지 않는다. Exact API path·field·enum 같은 구현 계약 literal은
보존하되 그 역할이 사용자 판단에 필요하면 같은 단위에서 쉬운 뜻을 붙인다.

### 구조를 먼저 닫는 작성 순서

현재 단계 work item과 허용된 `-design`을 실질 변경해 사용자의 값 선택이나 단계 확정에
인계할 때에는 상세 내용을 쓰기 전에 문서화 workflow의 session structure map을 만들고
작업 실행 workflow의 `plan-structure` round를 닫는다. `$verify-plan structure`를 항상
호출하며 중대한 구조이면 같은 round의 별도 identity로 `$verify-documentation proposal`도
호출한다. Discovery 전체 finding을 한 번 처분한 뒤 계획 의미·결정 권위·단계는 이 skill이,
hierarchy·first-screen·owner·보존 map은 `$documentation`이 그 순서로 한 correction batch에서
고친다. 새 map·digest를 하나의 Frozen candidate로 만든 뒤 closure를 한 번 수행한다.

Structure map은 `원문·source·후보의 독립 변경값 → 결정 축 ID → 권위·상태 → 권위별 표현·owner·
consumer·재검토 조건`을 빠짐없이 연결한다. 역방향으로도 추천·선택·목표 계약과 prose에
들어갈 모든 세부값이 축 ID 또는 고정 입력·source 파생 계약 하나에 연결되어야 한다. 이
양방향 대조가 닫히기 전에는 heading이나 카드 수를 동결하지 않는다.

Structure closure receipt와 exact map·digest가 없거나 stale이면 content writer를 호출하지
않는다. Closure 뒤 단일 `$documentation` writer는 동결된 heading, 두 열 first-screen field,
활성 결정 block, 결정 권위·상태와 보존 관계를 추가·삭제·재배치하지 않고 값과 설명만 채운다.
그 뒤 `$verify-plan content`로 final content round를 한 번 닫고, 중대한 final 또는 중대한
구조이면 `$verify-documentation final`을 같은 round의 별도 identity로 호출한다. Content가
골격이나 권위 상태를 바꾸면 structure verdict는 `Invalidated`이며 새 structure round로
돌아간다.

첫 화면에는 review 중 실제 writer·reviewer·Git actor가 아니라 모든 필수 gate와 checkpoint가
닫힌 뒤 문서를 처음 소비할 안정 actor·상태를 투영한다. Live phase는 작업 실행 receipt만
소유한다. 이미 확정된 결정은 결정 색인과 닫힌 결과에 남기고 활성 결정으로 다시 열지 않는다.
검증된 안정 candidate가 복구 지점이면 사용자에게 제시하기 전에 아래 checkpoint를 닫는다.

최초의 명시적 계획 artifact 작성 요청은 위 구조·내용 검증과 필수 checkpoint까지 허용한다.
반대로 사용자가 값만 선택하고 artifact 반영을 요청하지 않은 메시지는 문서 mutation 권한을
만들지 않는다.

## 6. 계획 문서 checkpoint

계획 문서가 요청 결과이거나 승인된 구현의 첫 mutation 전에 설계 closure를 제공하는
불가피한 선행 dependency이면, 작업 실행 workflow가 허용한 상시 예외로 검증된 현재
checkpoint를 local commit한다. 이 예외는 후속 production mutation이나 push 권한을 만들지
않는다.

1. 현재 계획 상태를 work item, 현재 단계에서 허용된 `-design`과 필수 router에 동기화한다.
   미확정 계획을 `Planned`나 완료로 승격하지 않는다.
2. `$documentation`으로 source·owner·링크·번호와 결정 delta를 검증한다.
3. 검증된 안정 상태가 다음 actor의 복구 지점이면 같은 후보 digest, 계획 lifecycle 상태,
   fixed-base `HEAD`, exact path·hunk, 제외 dirty와 `push 없음` 경계를 결속해 checkpoint를
   `Required-Pending`으로 만든다.
4. `Required-Pending`을 즉시 `$git-finalize`에 전달하고 이번 checkpoint의 exact path·hunk만
   [커밋 워크플로우](../../../docs/workflow/300-commit-workflow.md)로 stage·commit한다. 별도
   `commit` 요청이나 사용자 재확인을 기다리지 않는다.
5. 다른 작업의 dirty hunk와 안전하게 분리할 수 없으면 공통 blocker gate의 직접 증거로
   `Blocked`를 반환하고 다른 Git 효과로 우회하지 않는다.
6. commit object, parent, tree, full patch와 잔여 dirty를 확인한 뒤에만 `Committed`로
   바꾼다. push는 별도 명시 권한이 있을 때만 수행한다.

Checkpoint commit은 계획 작업의 복구 지점이지 완료 판정이 아니다. Commit 뒤에는 원래 계획
결과의 완료 oracle, 현재 단계의 남은 결과, 사용자 행동 유무를 operation map에서 다시 읽고,
사용자 행동이 없으면 다음 안전한 설계 단위를 계속 수행한다.

`Required-Pending`에서는 `$git-finalize` handoff만 수행하고 사용자 대기, 다른 phase handoff,
다음 rewrite와 terminal 보고를 하지 않는다. 실제 Git 차단만 `Blocked`를 만들 수 있으며,
`commit 요청 없음`이나 검증 완료 보고는 정상 종료 사유가 아니다.

최초 안정된 `Proposed`, 사용자 결정 반영과 최종 `Planned` 후보처럼 다음 작업자가 복원할
필요가 있는 상태만 checkpoint로 남긴다. `Planned` 후보는 모든 사용자 소유 값이 사용자
선택 또는 독립 source 제약으로 정해지고, Agent 소유 기술 선택은 source·대안·trade-off와
함께 독립 검증을 통과하며, 이 모두를 반영한 실행 계획 후보의 exact 범위를 사용자가
확정해야 한다. 독립 검증은 사용자 선택이나 단계 확정을 대신하거나 새 사용자 권위를
만들지 않는다.

## 7. 계획 검증과 산출물

자체 검토에서는 현재 계획 단계에 허용된 축만 열고 다음 반례를 찾는다. 구현·검증·전환
항목은 실행 계획 단계에서만 필수이며 앞 단계에서는 다음 단계 상세가 생겼는지를 대조한다.

- 계획 첫 화면만 보고 전체 단계, 현재 단계, 정확한 다음 단계와 전환 조건을 답할 수 없는가
- 계획의 목적, 현재 완성 여부, 즉시 다음 작업의 실행자와 사용자가 지금 해야 할 일 또는
  `없음`을 첫 화면만 보고 답할 수 없는가
- 현재 단계 안의 즉시 다음 작업과 현재 단계가 끝난 뒤의 다음 단계를 구분할 수 없는가
- section 제목의 질문과 본문·표의 정보 역할이 다르거나 한 `상태` 열에 상태·정보 종류·
  성숙도·재검토 시점을 섞었는가
- 작업별 진행 지도에 기능 요약·결정 원칙이나 공통 workflow 설명을 복제했는가
- 독립 설계 표면을 근거 없이 직렬화하거나 조건부·해당 없음 판정을 생략했는가
- 구현자가 중대한 제품·기술 선택을 새로 해야 하는가
- 현재 계획 단계에서 허용되지 않은 다음 단계 artifact·section·후보 상세가 생겼는가
- 정상 흐름뿐 아니라 잘못된 입력, 권한 거부, 중복, 동시성, 부분 실패와 복구가 빠졌는가
- 기존 data·API·설정·배포에서 목표 상태로의 전환과 rollback이 빠졌는가
- 모든 요구가 구현 작업·검증·문서에 연결되고 각 작업의 결과를 관찰할 수 있는가
- 구현 후보가 설계 closure보다 현재·다음 실행 단위로 승격되지 않았고, 각 필수 선행 edge가
  producer의 exact 결과와 최초 exact consumer 단계에 연결되는가
- test 불가능한 주장, owner 없는 운영·migration·보안 책임이나 중복 SOT가 남았는가
- 사용자 결정으로 표시한 항목이 실제 사용자 소유 기준에 의존하는가
- 각 사용자 결정의 exact 값과 긍정 선택 표현이 계획 후보가 아닌 원문 source에 연결되는가
- 열린 사용자 결정의 Agent 추천이나 verifier 결론이 사용자 선택·`남은 결정 없음`으로
  승격되지 않았고, Agent 기술 선택은 사용자 선택으로 잘못 귀속되지 않았는가
- 사용자 선택, Agent 기술 선택과 source 제약이 사용자 단계 확정으로 잘못 승격되지 않았고,
  각 단계 전환의 exact 사용자 확정 source를 복원할 수 있는가. 동시에 마지막 값의 무모호한
  채택·반영까지 별도 확인으로 쪼개 정상 진행을 막지 않았는가
- 값 선택만 있는 읽기 전용 논의에서 artifact writer를 호출하거나 mutation 권한을 만들지
  않았는가
- 결정 카드가 상세 절 없이 질문·대안 차이·추천·응답 형식을 전달하는가
- 하나의 카드·비교표·요약 문장이 `그리고`, `/`, 복합 명사로 독립 변경값을 함께 선택하거나,
  카드 prose가 axis inventory에 없는 default·owner·경계·표현·위치·version·운영 수단을
  은근히 확정하지 않았는가
- 모든 추천·선택·세부값이 정확히 하나의 축 ID 또는 고정 입력·source 파생 계약으로 역추적되고,
  한 값을 단독 변경할 수 있는데도 같은 카드에 남은 예가 없는가
- work item 본문과 `-design`을 포함한 모든 계획 목적 artifact의 첫 화면에서 현재 결론,
  닫힌 결과, 다음 안정 handoff의 남은 gate terminal 상태, 안정 actor·exact 행동, 사용자
  차례의 조건·응답 방식과 다음 전환을 복원할 수 있는가. 선행 검증의 live 행동을 첫 화면에
  섞거나, 활성 사용자 값 결정이 없다는 이유로 단계 확정 행동을 하단으로 미루거나, 닫힌
  계획에 새 질문·재확인을 만들지 않았는가
- 사용자 행동이 없고 계획이 미완료인데 checkpoint·검증·보고 뒤 안전한 다음 설계 단위로
  복귀하지 않고 종료했는가
- 검증된 안정 상태가 `Required-Pending`인데 `$git-finalize` 호출과 commit object 확인보다
  사용자 대기·다른 phase handoff·다음 rewrite·terminal 보고를 먼저 했는가
- 첫 화면·heading·결정 카드의 새 용어가 `선행 이해 확인 / 최초 문장에서 일상어로 설명 /
  쉬운 표현으로 교체·기술 상세로 이동` 중 하나이며, exact 계약 literal을 불필요하게
  번역·삭제하지 않았는가

완성 후보는 [`$verify-plan`](../verify-plan/SKILL.md)에 원래 목적, 확정 결정, 계획 artifact와
관련 source를 제공해 독립 감사한다. audit phase, 후보 동결, 보완·closure 횟수, 실패 뒤
상태 전이와 구현 인계는 작업 실행 workflow가 소유하며 이 skill에서 다시 정의하지 않는다.

계획 결과에는 다음이 포함돼야 한다.

- 계획 문서 경로, 현재 계획 단계와 해당 단계 closure 상태
- 현재 단계까지 선택·검증·확정된 표면, 주요 결정과 남은 사용자 소유 결정 또는 단계 확정
- 실행 계획 단계이면 작업·검증·전환·문서 책임의 연결과 구현 가능 판정
- 적용한 검증 판정과 계획 checkpoint 상태. `Committed`이면 SHA·parent·exact path·잔여
  dirty 확인을, `Blocked`이면 실제 blocker와 재개 조건을 함께 연결한다.

채팅 projection은 [완료 및 작업 보고 워크플로우](../../../docs/workflow/140-completion-reporting-workflow.md)에
맡기고 계획 결과와 구현 결과를 구분한다.
