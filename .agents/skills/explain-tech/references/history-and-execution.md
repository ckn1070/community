연결합니다.

## 시간축

질문에 필요한 축을 먼저 고정합니다.

```text
목표·최종 흐름 | exact commit·파일 snapshot | 현재 구현·caller
```

commit hash, 과거 diff, 선택 line과 `이 commit을 설명해`라는 요청은 snapshot의 초점을
지정할 뿐 `과거만`이라는 범위가 아닙니다. 현재 시간축은 사용자가 `그 당시 코드만`,
`현재와 비교하지 말고`처럼 명시적으로 제외했을 때만 닫습니다. Agent가 질문의 상세도나
선택한 snapshot에서 제외를 추론하지 않습니다.

현재 축이 열려 있으면 상세 초안 전에 다음 대응을 닫습니다.

```text
현재 판정·수정 필요성 | 현재 구현·caller
| snapshot이 추가한 책임·지속 기여
| 당시 한계별 현재 처분과 후속 commit·source
```

이 대응의 현재 판정·지속 기여·handoff를 첫 문단이나 바로 이어지는 작은 표에 먼저
노출합니다. 이 첫 화면만 남겨도 `지금 고칠 문제인가`, `snapshot에서 무엇이 현재까지
남았는가`, `무엇이 언제 바뀌었는가`를 답할 수 있어야 합니다. commit 당시 함수의 존재·
line·명칭을 바로잡는 것은 snapshot 정확성이지 현재 판정이 아니므로 이 admission을
대신하지 않습니다. 통과 전에는 과거 code와 당시 한계의 line-by-line을 시작하지 않습니다.

그다음 다음 순서로 설명합니다.

1. 현재 사용 여부와 지금 수정이 필요한지
2. 현재 end-to-end 흐름과 대상의 역할
3. 선택한 snapshot이 추가한 책임과 현재 남은 기여
4. 당시 한계와 인접 변경의 handoff
5. 요청한 line-by-line

과거 snapshot에 caller가 없었다는 사실을 현재 사용 여부로 확대하지 않고, 현재
caller를 과거에도 존재한 것처럼 쓰지 않습니다.
snapshot의 한계·취약점·미완성을 설명하면 같은 답변에서 현재 상태를 다음 중 하나로
판정합니다.

```text
현재도 유지 | 후속 수정됨 | 다른 구현으로 교체됨 | 제거됨 | 현재 source로 확인 불가
```

후속 질문에서 `이게 지금도 문제인가`가 나오면 그 질문만 보충해 끝내지 않습니다. 앞선
commit 설명이 현재 축을 누락한 것이므로 현재 판정, 지속 기여, 당시 한계와 후속 handoff를
한 연결로 복구합니다.

## 과거 판단의 근거와 원인

이전 답변·판단·행동이 왜 나왔는지 설명할 때에는 현재 source의 내용이 그럴듯하다는 이유로
과거 actor의 입력으로 소급하지 않습니다. [작업 실행 workflow](../../../../docs/workflow/100-work-execution-workflow.md)의
시간 방향을 적용해 다음을 먼저 닫습니다.

```text
설명할 결과와 발생 시각
→ 후보 source의 생성·유효·접근 가능 시각
→ 당시 actor가 실제 읽거나 호출한 trace
→ causal input / 후발 관찰·정정 source / 미증명
```

- 결과 뒤에 생성된 source는 앞선 결과의 원인 후보에서 제외합니다.
- 현재 문서가 앞선 판단과 같은 내용을 담아도, 당시 actor가 읽었다는 trace가 없으면 인과
  근거가 아닙니다.
- 후발 source는 앞선 답변을 반박·정정하거나 현재 상태를 설명할 수 있지만, 그 답변이 왜
  나왔는지를 증명하지 않습니다.
- 당시 trace를 전부 확인하지 못하면 확인한 직접 원인과 미증명 경계를 분리합니다. 현재
  artifact로 빈 구간을 채우거나 원인 하나를 추측하지 않습니다.

첫 문장은 시간 순서가 성립하는 원인만 쓰거나, 성립하는 원인을 확인하지 못했다고
판정합니다. 상세한 현재 상태와 후속 정정은 그 뒤에 분리합니다.

## 실행 인과

환경 이름과 파일 목록이 아니라 actor나 행위가 바뀌는 지점마다 사건을 나눕니다.

```text
시작 조건·event
→ 새 run·process
→ 그 실행의 설정·policy 판정
→ 전달되는 값·credential·artifact
→ consumer의 실제 명령·API 호출
→ 외부 상태와 관찰 결과
```

시작 조건은 다음 실행을 여는 조건일 뿐, source가 직접 증명하지 않으면 이전 실행의
권한·값·성공을 자동 상속시키는 행위자가 아닙니다. `가능함`, `설정됨`, `전달됨`,
`실제로 사용함`과 `성공함`을 서로 다른 상태로 둡니다.

여러 보안·권한 체계가 있으면 강함·약함으로 합치지 않습니다. 질문의 결론에 필요한
각 체계에서 다음만 연결합니다.

```text
설정 owner → 판정 policy → effective capability
→ 발급·주입되는 값 → 실제 consumer와 허용 행위
```

CI/CD, local·test·staging·production도 같은 모델을 사용합니다. test, runtime smoke,
artifact publish, 배포·reconcile과 배포된 process의 runtime 행위는 서로 다른
consumer 사건이며 하나의 성공으로 다른 사건을 증명하지 않습니다.

## 값과 상태의 출처

비슷한 이름의 값이 둘 이상이면 값마다 다음을 분리합니다.

```text
어느 event·process 문맥인가
→ 누가 언제 기록·생산하는가
→ 무엇을 가리키는가
→ concrete 상황의 실제 값
→ 어느 consumer가 왜 읽는가
```

평소 값이 같다는 사실은 의미가 같다는 증거가 아닙니다. 값이 달라지는 대표 상황과
잘못 선택했을 때 어느 후속 행위가 잘못된 대상을 처리하는지 보여줍니다.

## 실행 상태 근거

source가 증명하는 범위만 말합니다.

| 확인한 source | 말할 수 있는 범위 |
| --- | --- |
| 파일·함수·설정 존재 | 구현 또는 entrypoint가 존재함 |
| workflow·code의 직접 caller | 명시 조건에서 caller가 호출함 |
| runbook·development 문서 | 문서가 actor에게 실행을 지시함 |
| 현재 run·log·live readback | 관찰한 시점·대상에서 결과가 확인됨 |

`항상`, `보장`은 조건부 실행, disable, skip과 fallback까지 fail-closed로 막는 근거가
있을 때만 사용합니다. 그렇지 않으면 조건과 확인 공백을 함께 밝힙니다.
