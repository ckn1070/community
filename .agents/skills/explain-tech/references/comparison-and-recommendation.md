# 비교·대안·추천 설명

후보 이름부터 나열하지 말고 무엇을 같은 단위에서 비교하는지 고정한다.

구조의 존재 여부, 특정 topology가 필수인지와 현재 실행 절차는 상위 판정에서 먼저
확정합니다. 이 문서는 그 결론을 현재 directory나 기존 artifact로 다시 정당화하지 않고,
완전한 후보들의 trade-off와 추천 근거만 소유합니다.

## 비교 단위

```text
비교 질문 | 공통 시작 상태 | 공통 종료 상태
| 후보 단위 | 비교 축
```

- 전체 구조의 대안에는 같은 시작에서 같은 결과를 만드는 완전한 경로만 둔다.
- 제품, 역할, protocol 계층, 실행 위치와 연결 방식처럼 다른 분류 축을 동등한 후보로
  놓지 않는다.
- 함께 사용할 수 있는 구성요소를 배타적인 선택지로 만들지 않는다.
- 각 후보가 무엇을 대체하고 무엇과 결합하며 값·상태를 다음 단계로 어떻게 넘기는지
  밝힌다.

사용자가 실행 구조나 반복 운영 방식을 비교하면 후보별로 다음 실행 계약을 채웁니다.
현재 후보와 제안 후보를 구분하되, 제안이라는 이유로 후보 이름만 쓰거나 현재 후보보다
얕게 비교하지 않습니다.

```text
초기·반복·변경·삭제 구간 | 현재 존재 / 제안 / 미확정 | actor
| trigger·대상 상태 | 실행 위치
→ 기존 executable·새 executable·표준 명령 중 실제 수단 또는 결정되지 않은 exact 값
→ 입력 interface | 직접 변경 대상 | postcondition
```

- 사용자가 script를 비교 단위로 지정하면 각 후보가 어느 기존 script를 유지·개편하거나
  어느 책임의 새 script로 분리하는지 답합니다. 실행 수단을 정하지 않은 채 `일반 변경`,
  `operations`, `수렴 도구` 같은 분류만 붙인 후보는 완전한 경로가 아닙니다.
- 현재 source와 사용자 요구로 exact 수단을 고를 수 없으면 그 빈 결정을 명시하고 추천을
  조건부로 제한합니다. 설명을 위해 존재하지 않는 도구를 이미 있는 것처럼 쓰거나 임의의
  미래 파일명을 현재 interface로 만들지 않습니다.
- 한 후보의 핵심 action field가 미확정이면 그 exact 결정을 표시하고 조건부 후보로
  비교합니다. 미확정 field를 현재 구현처럼 쓰지 않으며, 다른 완전한 후보가 있는데도
  이름뿐인 후보로 선택 공간을 채우지 않습니다.
- 후보의 절차를 `목록에 추가`, `배포`, `script 실행`, `검증` 같은 단계명으로만 채우지
  않습니다. 각 단계는 행동 reference의 admission을 만족해야 하며, 개념 예시와 선택된
  artifact·interface를 구분합니다.
- 추천을 고른 뒤 실제 현재 절차나 채택된 제안을 두 단계 이상 펼칠 때만 행동 reference의
  user-facing 표를 사용합니다. 비교 중인 모든 후보를 현재 실행 절차처럼 쓰지 않습니다.

사용자가 선택지를 직접 요구하지 않아도 답변이 source나 사용자에게 아직 확정되지 않은
actor, 실행 위치, 상태 기준, artifact 형식, 전달·연결 방식이나 반복 운영 주체 중 하나를
고르면 비교가 발생한 것이다. 이를 이미 정해진 절차의 설명으로 바꾸지 말고, 같은 시작·
종료 상태의 실질 후보군을 먼저 닫는다. 후보군은 의사결정을 바꾸는 구조 차이까지만
제시하며 같은 구조의 제품 목록을 전체 선택지처럼 늘리지 않는다.

한 답변에 배포 주체·artifact 형식처럼 서로 독립된 선택 축이 있으면 한 축의 추천으로
다른 축을 자동 확정하지 않는다. 현재 다음 행동을 바꾸는 축은 후보와 추천 근거를 닫고,
아직 결정할 필요가 없는 축은 후보 이름 하나를 기본값처럼 사용하지 말고 보류 범위를
밝힌다. 추천에 필요한 network·권한·실행 주체 같은 전제가 현재 확인되지 않았으면 해당
전제가 충족될 때의 조건부 추천으로 제한한다.

## 적용 시간축

초기 1회 검증, 반복 운영과 목표 상태를 구분한다. 한 구간에서 단순하거나 안전한 경로를
다른 구간의 표준·최종 추천으로 확대하지 않는다. 구간마다 추천이 다르면 다음처럼 한
계약으로 연결한다.

```text
현재 구간과 목적 → 현재 추천 → 목표 구간과 추천
→ 전환 조건·유지되는 artifact·바뀌는 actor
```

`Best Practice`는 검증 가능한 원칙·운영 속성에 붙이고, 제품은 그 원칙을 구현하는 후보로
분리한다. 제품을 추천하려면 같은 원칙을 구현하는 주요 후보와 해당 환경의 선택 근거를
별도로 닫는다.

## 현재 상태와 목표 상태

다음 mode를 사용자 원문에서 선택한다.

- **목표 상태 최적화**: 현재 구현과 독립적으로 요구 결과를 가장 잘 만족하는 구조를
  먼저 찾는다.
- **점진적 전환**: 사용자가 기존 요소 유지, 최소 변경이나 호환을 명시한 경우 현재
  상태를 공통 시작점으로 둔다.

두 관점이 모두 필요하면 목표 구조를 먼저 확정한 뒤 `현재 → 목표`의 차이, 전환 비용과
위험을 별도로 설명한다. `현재 사용 중`이라는 사실만으로 목표 구조에 요소를 남기지
않는다.

## 추천 근거

저장소에 적용할 추천은 다음 근거를 닫은 뒤에만 확정한다.

```text
사용자 요구·제약 | 현재 SOT·활성 design | 실제 consumer
| 같은 결과를 만드는 후보 | consumer의 허용 조건·실패·비용
| 외부 공식 source | 대표 반례 | 재검토 조건
```

현재 구현은 적용 범위와 전환 비용의 근거다. 일반적인 업계 장점을 저장소의 실제 선택
이유로 만들지 않는다. 외부 provider·platform·protocol의 현재 계약이 결론을 바꾸면
공식 1차 자료로 확인한다.

근거가 닫히지 않으면 `최선`, `추천`, `Best Practice`로 승격하지 않고 조건부 후보와
확인할 공백을 밝힌다. 추천할 수 있는 근거가 이미 있으면 사용자가 말하지 않은 선호를
되묻지 않는다.

## 다음 행동의 의존 경계

다음 작업이나 구축 순서를 묻는 질문에는 마지막으로 본 화면이나 방금 만든 리소스만
이어 붙이지 않는다. 사용자 원문의 상위 결과와 현재 확정 상태에서 출발해, 그 결과에
필요한 능력·의존성 전체의 저상세 경계를 실제 consumer와 authoritative source에서 먼저
찾는다. 한 runbook이나 현재 화면은 그 안의 순서를 증명할 수 있지만 상위 결과의 전체
의존성 coverage를 대신하지 않는다.

각 의존성은 다음 중 하나로 판정한다.

| 상태 | 판정 기준 |
| --- | --- |
| 지금 필요 | 선택한 다음 행동의 진입·검증을 위해 먼저 닫혀야 한다. |
| 나중에 필요 | 상위 결과에는 필요하지만 현재 행동의 완료를 막지 않는다. |
| 조건부 | 구현 방식·소유자·운영 조건에 따라 필요 여부나 순서가 바뀐다. |
| 해당 없음 | 현재 목표와 source에서 결과에 관여하지 않는 근거가 있다. |
| 미확정 | source나 사용자 결정이 없어 현재 판정할 수 없다. |

상위 결과에 필요한 능력마다 위 상태를 판정하며, 다음 행동 하나를 찾았다는 이유로 발견을
중단하지 않는다. 언급되지 않은 의존성을 `해당 없음`으로 바꾸지 않는다. 조건부 의존성은
한 구현 방식이나 소유자를 암묵적으로 고르지 말고, 같은 결과를 만드는 완전한 경로와 순서
차이를 비교한다. 모든 미래 작업을 상세 설계할 필요는 없지만 이 저상세 경계가 닫히기
전에는 단일 항목을 최종 추천하지 않는다.

`한 단계씩`은 실행·답변의 노출 단위를 제한하며 의존성 발견 범위를 줄이지 않는다.
답변에는 상위 결과의 필수 능력과 각 상태를 짧은 지도로 보여 주고, 추천한 다음 한 단계만
상세화한다. 조건부 항목은 현재 선택이 필요한지와 구현 방식별 순서 차이를 함께 밝힌다.

### 선행조건, 독립 트랙과 합류점

남은 항목을 하나의 번호 순서로 쓰기 전에 각 연결을 실제 소비 관계로 판정한다. `A가 B보다
먼저다`라고 말할 수 있는 경우는 B의 특정 단계가 A의 결과를 입력으로 소비해, A 없이는 그
단계를 시작하거나 완료할 수 없을 때뿐이다. 이때 `A의 어떤 결과 → B의 어느 단계`인지
명시한다. 적용·실행·통합 검증에만 필요한 결과를 설계·작성·제작 단계의 선행조건으로
소급하지 않는다.

관계는 다음처럼 구분한다.

| 관계 | 판정과 표현 |
| --- | --- |
| 필수 선행 | exact consumer 단계가 producer 결과 없이는 진행할 수 없다. 처음 막히는 단계를 밝힌다. |
| 독립 | 현재 상태에서 서로의 결과 없이 시작·완료할 수 있다. 병렬 가능한 별도 트랙으로 보인다. |
| 합류 시 필요 | 각 트랙은 독립적으로 진행할 수 있고 적용·연동·통합 검증 같은 최초 합류점부터 상대 결과가 필요하다. |
| 권장 순서 | 비용·피드백·위험 때문에 먼저 하기를 추천하지만 다른 작업의 진입조건은 아니다. 추천이라고 표시한다. |
| 리마인더 | 지금 할 필요는 없지만 특정 consumer 전까지 완료해야 한다. `지금 먼저`가 아니라 `늦어도 언제까지`로 표현한다. |

각 남은 트랙에는 `지금 시작 가능한가`, `처음 막히는 consumer 단계`, `늦어도 필요한 시점`을
판정한다. 둘 이상의 독립 트랙이 있으면 하나의 직렬 목록으로 합치지 않고 트랙과 최초
합류점을 짧게 보여 준다. 저장소에서 설계·작성할 수 있는 결과를 외부 환경의 미실행만으로
차단하지 않는다. 다음 행동은 준비도·학습 가치·비용을 근거로 추천할 수 있지만, 그 추천을
다른 트랙의 필수 선행조건으로 바꾸지 않는다.

## 누락 지적 뒤 재구성

Agent가 추천한 뒤 사용자가 반복 수동 작업인지, 원래 방식인지, 다른 선택지가 없는지,
왜 그것이 최선인지 되묻는 것은 직전 후보의 상세 질문으로만 처리하지 않는다. 원래 비교
단위나 후보군이 보이지 않았다는 증거이면 이전 추천을 무효화하고 최초 질문으로 돌아간다.

사용자가 `왜 A를 먼저 해야 하나`, `A를 하지 않으면 B를 못 하나`, `둘이 정말 연결되는가`를
묻는 경우도 직전 순서 문장만 완화하지 않는다. 이전 의존 지도를 무효화하고 각 edge의 실제
consumer, 독립 트랙과 최초 합류점을 다시 판정한다.

다시 답할 때는 `같은 시작·종료 상태의 후보군 → 현재 조건의 추천 → 선택 이유·trade-off
→ 재검토 조건`을 한 번에 제시한다. 직전 후보의 제품군만 추가하거나 `방식은 표준이고
제품은 후보`처럼 계층을 바꾸어 기존 결론을 보존하지 않는다. 사용자가 단순히 이미 닫힌
후보 하나의 세부 동작만 묻는 경우에는 이 재구성을 강제하지 않는다.

## 사용자 지정 평가축 폐쇄

사용자가 비용·보안·운영처럼 추천에 적용할 조건을 직접 지정했다면 조건 목록 전체를
하나의 추천 계약으로 사용한다. `가정하지 않기`, 특정 source 제외와 현재 항목 한정처럼
후보가 타협할 수 없는 제약은 평가축과 분리해 먼저 적용하고, 하나라도 위반하는 후보는
종합 점수와 무관하게 제외한다. 인접한 저장소 값이나 일반적인 미래 가능성을 사용자가
확정한 현재 요구로 바꾸지 않는다.

답변 전에 각 평가축을 다음 중 하나로 닫는다.

| 상태 | 답변에서 할 일 |
| --- | --- |
| 평가됨 | 확인한 사실과 추천에 미치는 영향을 연결한다. |
| 해당 없음 | 왜 현재 후보의 결론을 바꾸지 않는지 설명한다. |
| 미확정 | 값을 가정하지 않고 조건부 판정과 확인·재검토 조건을 제시한다. |

모든 축이 이 셋 중 하나가 되기 전에는 종합 추천과 Best Practice 판정을 확정하지 않는다.
한 축의 새 정보가 들어와도 그 축만 최적화해 결론을 뒤집지 않고 전체 축에 미치는 영향을
다시 대조한다. 이전 추천이 바뀐다면 새 사실, 영향받은 평가축과 변경 이유를 같은 답변에
밝힌다.

요구가 언급되지 않았다는 사실을 `필요 없음`이나 `미래 선택권 선호`라는 사용자 결정으로
바꾸지 않는다. 미확정 요구에 따라 결론이 달라지면 확인된 범위에서 운영 표면을 늘리지
않는 조건부 기본값과 그 결정 원칙을 밝히고, 반대 조건에서 추천이 어떻게 바뀌는지 함께
제시한다. 미래 유연성만을 근거로 기능을 미리 활성화하려면 그 유연성이 사용자 요구로
확정돼 있어야 한다.
