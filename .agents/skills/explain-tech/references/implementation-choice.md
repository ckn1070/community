# 구현 선택 판정

현재 코드가 특정 기능을 직접 수행하는 이유, 플랫폼 기본 기능 대신 현재 방식을 택한
필요성과 합리성, 구현 topology와 실행 절차를 설명할 때 답의 종류를 분리합니다. 현재
구현의 작동 원인을 설명하는 것으로 그 선택이 옳은지 판정했다고 계산하지 않습니다.

## 1. 선택 질문 admission

다음 질문은 사용자가 `대안`, `추천`이나 `Best Practice`라는 말을 쓰지 않아도 구현 선택
질문입니다.

- `플랫폼도 해주는데 왜 우리가 직접 하는가`, `왜 굳이 이 방식인가`
- `현재 방식이 꼭 필요한가`, `합리적인가`, `다른 방법은 무엇인가`
- 현재 구현을 설명하려면 source나 사용자가 확정하지 않은 actor·실행 위치·artifact 형식·
  전달 방식·반복 운영 주체 중 하나를 골라야 하는 질문

이 reference가 해당 선택의 첫 화면 판정과 최소 대안 비교를 단독 소유합니다. 일반적인
추천 taxonomy나 script lifecycle workflow를 먼저 읽지 말고 현재 code·design·caller에서
아래 값을 닫습니다. 현재 코드가 존재하거나 복잡한 인과로 작동한다는 사실은 선택 근거가
아닙니다.

## 2. 첫 화면 판정

상세 작동 원리, 기술 근거와 source link보다 먼저 다음 네 값을 한 단위에서 닫습니다.

1. **현재 방식**: 누가 어떤 변환·상태 변경을 직접 수행하는가
2. **필수성**: 플랫폼·표준 계약상 본래 필수인지, 현재 설계 선택 때문에 필요한지
3. **실제 선택 근거**: 설계·사용자 결정에 명시됐는지, 코드에서만 추론되는지, 확인할 수
   없는지
4. **현재 합리성**: 현재 요구·변경 주체·운영 조건에서 합리적, 조건부, 과도함, 판정 불가
   중 무엇인지와 그 이유

첫 두 문장 안에 네 값을 모두 명시합니다. `현재는 A이며, A 자체는 필수가 아니고, C를
얻기 위해 선택됐지만 그 이유는 source에서 확인되지 않으며, 현재 조건에서는 과도합니다`처럼
사용자가 판단할 값을 직접 말합니다. 네 값 중 하나가 없으면 뒤의 작동 원리·장점·대안으로
진행하지 않고 source를 더 확인하거나 `판정 불가`라고 씁니다.

하위 방식이 이미 선택된 상위 설계와 호환되거나 그 설계 안에서 필요하다는 사실은 현재
합리성의 근거가 아닙니다. 상위 설계의 필요성·결정 근거를 별도로 확인하고, 확인되지 않으면
`상위 설계를 유지할 때만 조건부로 필요하지만 현재 요구에서 그 선택은 입증되지 않았다`고
판정합니다. 전환 비용·호환성만으로 현재 방식을 합리적이라고 승격하지 않습니다.

새 기술 용어가 이 판정에 필요하면 최초 사용과 같은 문장에서 `무엇을 기록·비교하는가 →
다음 변경에서 무엇이 허용·거부·삭제되는가`처럼 관찰 가능한 차이까지 일상어로 닫습니다.
이 차이를 한 문장으로 닫지 못하면 용어를 첫 결론에서 제거하고 concrete 동작만 씁니다.
용어의 인과 chain을 먼저 나열하고 마지막에 필요성·합리성을 붙이지 않습니다.
관리 주체별 field 추적을 선택 근거로 쓰면 다른 주체가 그 field를 바꿀 때의 충돌과 같은
주체가 다음 요청에서 이전 field를 뺄 때의 유지·삭제 처분을 모두 밝힙니다. 둘 중 하나만
장점으로 나열한 설명은 그 선택의 효과를 닫지 못한 것입니다.

선택 이유는 다음 증거 수준을 섞지 않습니다.

- **명시 근거**: 사용자 결정, design·SOT 또는 commit 설명이 이유를 직접 기록함
- **구조상 추론**: 현재 code·caller·test에서 얻는 속성으로 이유를 추론함
- **일반 장점**: 기술이 보통 제공하는 장점이며 이 저장소의 실제 선택 이유는 아님

테이블·module·file·service처럼 독립 관리 단위를 늘리는 후보는 추천 전에 다음
gate를 통과합니다.

1. 현재 활성 요구와 실제 consumer, 기존 design이 같은 분리안을 검토·배제했는지를
   먼저 복원합니다.
2. 추가하는 각 단위를 다른 단위와 구분하는 현재의 요구·consumer·cardinality·
   lifecycle·무결성·권한·조회 차이 중 하나를 역추적합니다.
3. `NULL` column이 있음, 일반적인 정규화 장점, 미래 속성 확장 가능성만 남으면
   단위를 늘리지 않고 현재 요구를 충족하는 더 단순한 구조를 선택합니다.
4. 활성 design이 이미 검토해 배제한 구조를 다시 추천하려면, 그 결정의 전제를
   무효화한 더 최신의 요구나 authoritative source를 먼저 밝힙니다. 그 근거가 없으면
   폐기한 후보를 새 추천으로 다시 열지 않습니다.

이 gate는 단위 수를 줄이는 것 자체를 목표로 하지 않습니다. 현재 소비하는 책임이 실제로
다르면 분리하고, 그 차이가 없으면 미래 유연성만으로 분리하지 않는 경계입니다.

사용자가 가상·변경된 이름의 계약과 동작을 질문 안에 완결된 source로 제공했는데 저장소에
그 exact artifact가 없으면, 구조가 비슷한 현재 구현의 제품명·파일·line을 그 계약의 근거로
붙이지 않습니다. 제공된 계약만으로 판정하고, 저장소 artifact와의 연결은 확인되지 않았다고
둡니다. 개념 전이 검증에서 원래 사례의 이름이나 source link를 새 사례에 옮기지 않습니다.

## 3. 대안 비교

첫 화면 판정 직후 현재 방식과 실질 대안을 같은 깊이로 비교합니다. 최소 후보는 `현재
방식`과 사용자가 대비한 `플랫폼·표준 기본 방식`이며, 현재 요구를 만족하는 구조적으로 다른
주요 후보가 있으면 함께 둡니다. 이름만 가능한 후보나 같은 구조의 제품 목록으로 수를
채우지 않습니다.

| 후보 | 실제 처리 주체·수단 | 얻는 속성 | 비용·잃는 속성 | 현재 조건의 적합성 |
| --- | --- | --- | --- | --- |
| 현재 방식 | ... | ... | ... | ... |
| 플랫폼·표준 기본 방식 | ... | ... | ... | ... |

비교 뒤에는 현재 권고와 재검토 조건을 명시합니다. 현재 구현이 이미 존재한다는 사실은
전환 비용 근거일 뿐 유지 권고의 근거가 아닙니다. 설계 근거가 없으면 일반 장점으로 현재
선택을 합리화하지 않고 `구조상 추론`과 현재 요구의 적합성만으로 조건부 판정합니다.

실행 entrypoint topology를 비교하는 경우에는 위 공통 계약에 더해 다음 두 후보를 같은
깊이로 포함합니다.

1. 하나의 executable이 명시적인 mode로 최초 구축과 반복 변경을 구분합니다.
2. 얇은 entrypoint를 생애주기별로 두고 검증·render·apply core를 공유합니다.

해당 domain의 표준 desired-state owner가 같은 종료 상태를 만들 수 있으면 세 번째 후보로
포함합니다. 현재 executable을 mode 없이 반복하는 약한 baseline으로 위 두 후보 중 하나를
대체하지 않습니다.

## 4. 존재 여부와 실행 절차

사용자가 물은 능력·interface가 없으면 첫 문장에서 `현재 그 수단은 구현돼 있지 않습니다`라고
답하고, 가상 파일명이나 미래 절차를 현재 artifact처럼 설명하지 않습니다. 값이 없는 field는
`미결정`으로 둡니다.

```text
actor | trigger·대상 상태 | 실행 위치 | executable·API | 입력 interface
| 직접 상태 전이 | 완료 관찰 | 부분 실패 복구
```

실행 절차는 현재 구현됐거나 사용자가 채택한 후보만 펼칩니다. 추천하지 않은 후보의 절차를
모두 나열해 비교를 흐리지 않습니다.

## 5. repair와 false-block

이전 답변이 현재 방식의 작동 원리만 설명했거나, 사용자가 선택 이유·필수성·합리성·대안을
다시 묻는다면 이전 설명 단위를 무효화합니다. 지적받은 질문만 한 문장 보충하지 않고 2절의
첫 화면 판정부터 대안·권고까지 전체 답을 교체합니다.

반대로 선택이 없는 순수 문법·동작 질문, 이미 닫힌 후보 하나의 세부 동작 확인에는 비교를
강제하지 않습니다. 후보가 둘이고 차이가 한 문장으로 닫히면 표를 만들지 않습니다. 단순한
`그 스크립트 안의 값을 바꾼다는 뜻인가`에는 먼저 yes/no를 답하고 바뀌는 대상과 바뀌지
않는 대상만 설명합니다.
