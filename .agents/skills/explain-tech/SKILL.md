# 기술 설명

정확한 사실을 많이 나열하는 것이 아니라, 사용자가 질문의 결론까지 스스로 따라갈 수
있는 가장 짧은 인과 경로를 만듭니다.

## 0. 코드·설정 답변 admission

이 `SKILL.md`는 첫 명령의 고정 line 범위를 읽었다는 이유로 완독했다고 가정하지 않습니다.
초안 전에 전체 line 수와 마지막 line을 확인하고 EOF까지 읽습니다.

플랫폼·framework·표준 도구와 현재 구현이 같은 종료 상태를 만들 수 있는데 현재 구현이
왜 직접 처리하는지 묻는 원자는 다른 reference보다 먼저
[implementation-choice.md](references/implementation-choice.md)만 읽습니다. 현재 code·design·
caller에서 그 reference의 첫 화면 판정과 최소 대안 비교를 닫기 전에는 causal-span,
code-and-config, action, lifecycle, 도구 도입·script engineering reference를 열거나 상세
작동 원리를 초안에 쓰지 않습니다. 이 선택 단위를 닫은 뒤 사용자가 요청한 line-by-line,
lifecycle이나 script 배치 상세에 필요한 reference만 추가합니다.

이 질문의 첫 실질 답변은 첫 두 문장 안에 현재 방식, 본래 필수인지 여부, 실제 선택 근거의
증거 수준과 현재 요구에서의 합리성을 모두 말합니다. 현재 하위 구현이 이미 선택된 상위
설계와 잘 맞는다는 사실만으로 합리성을 닫지 않습니다. 상위 설계가 현재 요구에 필요한
근거가 없으면 `상위 설계를 유지할 때만 조건부로 필요하지만 현재 선택은 입증되지 않았다`고
판정한 뒤 같은 종료 상태의 더 단순한 대안을 비교합니다.

선택한 코드·설정의 정체·목적·앞뒤 흐름을 묻는 원자는 초안 전에
[causal-span.md](references/causal-span.md)와
[code-and-config.md](references/code-and-config.md)를 순서대로 끝까지 읽습니다.
`causal-span`의 producer→선택 span→consumer admission을 내부에서 닫기 전에는 line·option
설명을 시작하지 않습니다. 이 admission의 field와 순서는 source 누락을 막는 조사 도구이지
사용자 답변의 제목·목차·표가 아닙니다. 적용 우선순위는 `선수 개념·causal handoff → 사용자
질문의 최소 완결 단위 → 물리 line coverage → 한 응답 완료`입니다.

## 1. 질문과 근거

초안이나 source 탐색 전에 다음을 고정합니다.

```text
상위 이해 목표 | exact 질문 원자 | 대상·snapshot
| 활성 mode·명시 제약·제외·순서 | source별 허용 역할·권위
| 사용자가 이미 아는 범위 | 결론을 바꿀 직접 근거 | 복귀점
```

한 원자에 여러 질문이 있으면 초안 전에 각 질문을 다음 행으로 분리합니다.

```text
원문 질문 | exact 대상 | 요구한 답의 종류
→ 직접 답할 값 또는 미확정인 exact 값 | 근거 | 답변 문장·위치
```

- `무엇을·무엇으로`는 실제 artifact, executable, API나 명령을 답합니다. 아직 선택되지
  않았거나 존재하지 않으면 그 상태와 결정이 필요한 exact 값을 답하며, 목적·순서·추천
  이름으로 대신하지 않습니다.
- `언제`는 시작 event·대상 상태와 전체 순서의 위치, `어디서`는 실행 환경·process,
  `어떻게`는 caller·입력 interface·직접 행위·변경 대상·관찰 결과를 답합니다.
- `왜·필요한가`는 직접 원인과 제거했을 때 최초로 달라지는 결과를 답합니다.
- 비교·추천은 사용자가 요구한 각 시간 구간에서 위 값이 모두 채워진 후보끼리 판정합니다.
  한 구간의 실행 수단이 비어 있으면 구조 이름이나 lifecycle 분류만으로 완성된 추천으로
  보고하지 않습니다.
- 각 행은 요구한 종류의 값이 들어 있는 문장으로만 닫습니다. 여러 행이 같은 문장을
  사용하려면 각 값이 그 문장에 실제로 있어야 합니다. 공통 설명은 모든 직접 답 뒤에만
  붙입니다.

현재 구현 여부, exact file·test·artifact의 필요성·배치, `어떻게`, 분리 필요성,
Best Practice와 실행 절차가 한 질문이나 연속된 후속 질문에 함께 있거나, 절차 설명이
미확정 actor·실행 위치·상태 기준·artifact 형식·전달 방식·반복 운영 주체를 골라야 하면
[implementation-choice.md](references/implementation-choice.md)를 먼저 읽고 일반 후보 비교가
더 필요할 때만 [comparison-and-recommendation.md](references/comparison-and-recommendation.md)를
읽습니다.

파일이나 artifact의 `정체·어느 영역의 artifact인지`와 현재 실행·배포 경로에서의 역할을
묻거나 둘을 섞을 수 있는 표현을 쓰려면 [code-and-config.md](references/code-and-config.md)의
artifact 분류축을 함께 적용합니다. Path·확장자·현재 caller 중 하나로 내용의 본질과
lifecycle 역할을 한 개의 분류로 합치지 않습니다.

사용자가 행동·절차를 설명해 달라고 했거나, 답변에서 추가·삭제·변경·실행·배포·검증
단계를 하나라도 제시하려면 source 조사와 초안 전에
[action-and-procedure.md](references/action-and-procedure.md)를 끝까지 읽고 그 출력 계약을
적용합니다. 이 reference를 읽기 전에는 행동 이름, 추천 단계나 미래 script를 답변 후보에
쓰지 않습니다.

사용자가 전체 lifecycle, 변경 반영, 기존·새 실행 인스턴스의 차이를
묻거나, 이전 답변의 미답·모순 때문에 같은 결론을 다시 물으면 source 조사와
초안 전에 [lifecycle-and-state.md](references/lifecycle-and-state.md)를 끝까지 읽습니다.
이 계약을 닫기 전에는 phase 목록, 신규 실행 설명이나 추천을 쓰지 않습니다.

- 선택한 이전 문장은 원문과 직접 선행 문맥을 읽고 문자 그대로의 주체·대상·술어·
  범위를 복원합니다. 원문으로도 답을 바꾸는 해석이 둘이면 그 대상만 질문합니다.
- 선택 영역이나 지시어가 있으면 선택한 exact span을 설명 대상으로 고정하고, span을
  포함한 line·block·파일은 문법과 실행을 확인할 context로만 사용합니다. `이게 정확히
  뭐야`처럼 정체를 묻는 질문에는 enclosing context의 요약보다 먼저 span 전체가 명령인지,
  값인지, 어느 parser의 어떤 복합 문법인지를 직접 분류합니다.
- 사용자가 source의 이름을 복사하거나 질문에 사용했다는 사실만으로 그 뜻을 안다고
  판정하지 않습니다. 직접 선행 문맥에서 의미를 설명했거나 사용자가 이해를 드러낸 범위만
  선수 지식으로 두고, 선택 표현의 결론에 필요한 나머지는 첫 인과 사용 전에 닫습니다.
- `무엇`, `왜`, `누가`, `언제`, `어디서`, `어떻게`, `필요한가`, `무엇을 써야 하는가`처럼
  서로 다른 질문은 위 질문 행과 답변 문장으로 각각 닫습니다.
- 한 질문이 조건식의 참·거짓과 대상 상태의 존재·부재를 함께 물으면 문법 판정과 상태
  목표를 별도 원자로 닫습니다. 상태 목표에는 대상의 쉬운 정의, exact 식별자가 구분하는
  역할, 현재 상태, 원하는 최종 상태와 그 상태를 유지했을 때 현재 실행에서 처음 생기는
  concrete 차이를 포함합니다. 문법 결과만 계산한 뒤 정의하지 않은 domain 이름이나
  `제약이므로 제거한다` 같은 순환 설명으로 상태 결론을 압축하지 않습니다.
- 이전 설명이나 선택 문장의 정확성을 묻는다면 첫 문장에서 `맞다/아니다`,
  `쓴다/쓰지 않는다`, `같다/다르다` 중 맞는 판정을 먼저 내립니다.
- 틀린 명제를 넓은 정의로 감싸 보존하지 않습니다. 정정문과 주체·조건·결과 중
  하나라도 다르면 원문을 폐기하고 정확한 문장으로 교체합니다.
- 이전 설명의 `앞의 것`, `parser와 연결`, `설정이 사용한다`처럼 지시 대상이나 관계가
  생략된 표현을 되물으면 주변 코드에 맞는 뜻을 새로 붙이지 않습니다. 원문에서 양 끝의
  exact 대상과 실제 행위를 복원하고, 그런 관계가 없으면 표현 전체를 폐기합니다.
- 화면·첨부·live 출력의 literal을 현재 표면의 문구로 인용하기 전에 다음 gate를 닫습니다.

  ```text
  후보 literal | 최초 출처 | 읽을 수 있는 target 영역·live 표면 증거 | 확정 / 미확정
  ```

  이전 Agent 답변의 문자열을 사용자가 되물어도 최초 출처는 Agent 답변이며 화면 증거로
  승격되지 않습니다. 긴 screenshot은 원본의 target 영역을 읽을 수 있는 크기로 잘라
  확인해야 하며, 전체 image view·원본 pixel 크기·실패한 OCR은 통과 증거가 아닙니다.
  `확정` literal만 현재 화면 문구로 사용합니다. 미확정이면 중립적인 위치 표현을 쓰고
  결론을 바꾸는 literal만 다시 확인합니다. 외부 공식 문서는 동작·계약을 결정하되 화면
  literal을 대신하지 않으며, 용어가 다르면 확인된 `관찰 표현 ↔ 공식 용어` mapping을
  명시합니다.
- 사용자가 추천에 적용할 평가 조건을 둘 이상 지정했다면 각 조건을 독립 평가축으로
  동결합니다. 일부 축만 보고 추천을 먼저 만들거나 후속 질문마다 다른 축으로 추천을
  뒤집지 않습니다. 모든 축의 판정 상태와 결론 영향을 닫는 절차는
  [comparison-and-recommendation.md](references/comparison-and-recommendation.md)를 사용합니다.

질문 유형을 고정한 직후 source를 찾거나 후보를 만들기 전에 적용되는 reference를 모두
끝까지 읽습니다. 하나의 원자가 화면 option의 literal·위치와 추천처럼 여러 유형에
걸치면 한 reference로 다른 유형을 대신하지 않습니다. 설명 도중 대안·Best Practice·
추천으로 질문 기능이 바뀌면 그 시점에 새로 적용되는 reference를 읽고 위 계약을 다시
고정합니다.

- 코드·설정·option·연산자·fixture·line-by-line:
  선택 span의 정체·목적·앞뒤 흐름이면
  [causal-span.md](references/causal-span.md)를 먼저 읽고,
  [code-and-config.md](references/code-and-config.md)를 읽습니다.
- commit·파일 진화·현재 사용 여부·이전 답변·판단의 실제 근거·원인·시간 순서·CI/CD·다중 환경:
  [history-and-execution.md](references/history-and-execution.md)
- 대안 비교·Best Practice·추천·다음 작업 또는 구축 순서:
  [implementation-choice.md](references/implementation-choice.md)를 먼저 읽고,
  [comparison-and-recommendation.md](references/comparison-and-recommendation.md)
- lifecycle·변경 반영·기존 실행 상태와 새 실행 상태 비교·반복 질문 repair:
  구현 여부·선택·절차가 함께 있으면
  [implementation-choice.md](references/implementation-choice.md)를 먼저 읽고,
  [lifecycle-and-state.md](references/lifecycle-and-state.md)

그다음 현재 SOT, 실제 구현·wiring·caller·test를 답을 바꾸는 범위까지 추적합니다.
외부 제품 계약이 필요하면 사용 version의 공식 1차 자료를 사용합니다. 파일 존재,
문서상 의도, 직접 caller와 실제 실행 관찰을 서로 다른 증거로 유지합니다.

사용자가 Agent 추천의 전제·대안·비용·우위나 근거를 문제 삼으면, 직전 추천의 상세 질문이
아니라 추천 결론을 다시 여는 반론으로 처리합니다. 답변 후보를 만들기 전에
[설계 피드백 반영 workflow](../../../docs/workflow/120-design-feedback-workflow.md)와
[implementation-choice.md](references/implementation-choice.md),
[comparison-and-recommendation.md](references/comparison-and-recommendation.md)를 끝까지 읽고,
사용자가 제시한 대안과 직전 추천을 같은 시작·종료 상태와 같은 평가축에서 다시 비교합니다.

직전 추천을 유지하려면 사용자가 지적한 비용을 포함해도 현재 조건에서 우위가 남는다는
직접 source와 trade-off를 제시합니다. 그 우위가 없거나 근거가 닫히지 않으면 추천을
철회·조건부로 낮추고, 일반적 장점이나 downstream 실행 방법으로 기존 결론을 방어하지
않습니다. 같은 근거 공백을 반복해서 묻는 후속 이의는 이전 비교가 성립하지 않았다는
증거이므로, 설명을 덧붙이거나 사용자에게 별도 관리 부담을 넘기지 않고 최초 비교부터
교체합니다.

저장소 문서의 유형·위치·owner·directory topology 또는 여러 실행에서 재사용할 문서 구조를
설명하거나 추천하면, 답변 후보를 만들기 전에 문서 정보 구조 가이드와 문서화 workflow를
끝까지 읽고 관련 router·actual corpus를 직접 수집합니다. 읽기 전용 추천에서도 문서화
workflow의 의미·구조 gate를 적용하며, 실제 Markdown 변경 권한이나 작성 완료로 확대하지
않습니다.

문서 path는 주제 명사나 현재 한 회차의 위치에서 바로 고르지 않고 다음 순서로 판정합니다.

```text
독자가 반복해서 하려는 행동·질문
→ 정보의 수명과 실행마다 바뀌는 상태
→ 환경·topology·lifecycle·복구 등 사용자가 제시한 시나리오 축
→ 공통으로 재사용할 상세 절차와 시나리오마다 달라지는 orchestration
→ 문서 유형·canonical owner·router·directory topology
```

사용자가 여러 현재·미래 시나리오를 제시하면 먼저 시나리오 family와 공통/가변 책임을
모두 보존한 구조 후보를 만듭니다. 현재 시나리오 하나에 맞춘 기존 문서 한 개의 rename·확장과,
시나리오별 상위 절차가 공통 task 문서를 조합하는 구조를 같은 독자 행동·재사용성·추가 비용·
탐색 경로에서 비교합니다. 이 비교 없이 `project`·`operations`, 기존 단일 runbook 또는 새
directory를 결론으로 확정하지 않습니다. 추천이 새 canonical entrypoint·owner·directory·
router·번호 topology를 만들거나 바꾸면 이를 routine 문장 보완이 아닌 문서 구조 proposal로
분류하고, 문서화 workflow가 요구하는 proposal 감사 범위까지 결과에 명시합니다.

저장소 실행 script의 역할·사용 시점·재사용성·배치 경로나 `bootstrap`, `operations`,
`verify`, `quality` 분류를 설명하거나 추천하면
[도구 도입과 생애주기 워크플로우](../../../docs/workflow/130-tool-adoption-workflow.md)와
[스크립트 엔지니어링 가이드](../../../docs/workflow/240-script-engineering-guideline.md)를
현재 canonical source로 함께 읽습니다. 설치·실행 순서, 기술 제품명과 사용 생애주기를
서로 대신하는 분류 근거로 사용하지 않습니다. 같은 executable에 둘 이상의 생애주기가
보이면 경로를 임의로 고르지 않고 책임 분할 필요성까지 판정합니다.

다만 플랫폼 기본 기능과 script의 같은 기능 중 누가 맡아야 하는지를 묻는 선택 질문에는
이 두 workflow를 선행 admission으로 사용하지 않습니다. implementation-choice의 첫 화면과
최소 대안 비교를 먼저 닫고, script의 도입·존치·생애주기 배치가 그 판정 뒤에도 열린 별도
질문일 때만 읽습니다.

사용자가 열거한 항목이 전부인지 묻거나 답변이 `딱`, `오직`, `전부`, `이것뿐`, `다른
경로가 없다` 같은 완결성 판정을 포함하면, 먼저 그 항목들이 함께 바꾸는 결과·postcondition을
범위로 고정합니다. 사용자가 언급한 항목은 조사 시작점이지 전체 후보 집합이 아닙니다.
현재 source에서 같은 결과를 만들거나 다시 바꾸거나 성공을 막는 독립 경로를 caller·형제
branch·precondition·postcondition·test·계약 문서까지 추적한 뒤에만 개수와 `전부`를
확정합니다. 이 범위를 닫지 못하면 확인한 항목과 미확인 경계를 분리하며 정확한 개수를
추측하지 않습니다.

사용자가 설명 상세를 일부 항목으로 좁힌 것과 사실상 다른 경로가 없다고 확정한 것을
분리합니다. 요청한 항목에 설명을 집중하되, 생략한 경로가 직접 결론을 뒤집으면 그 존재와
차이만 먼저 밝히고 상세는 확장하지 않습니다. 질문인지 설명 범위 지시인지 두 해석이
가능해도 `설명은 두 항목에 집중할 수 있지만 전체 경로는 N개다`처럼 두 축을 분리해
source가 유일하게 닫는 사실을 사용자에게 다시 찾게 하지 않습니다.

발견한 source가 구체적이라는 이유로 처음 고정한 역할을 바꾸지 않습니다. 다른 mode·환경·
과거 snapshot의 설계나 현재 구현은 사용자가 연결한 요구·제약 또는 열린 비교의 결론이
없으면 현재 목표의 필수값·보존 제약·선택 이유가 아닙니다.

요청의 읽기 전용·실행 원자와 권한은
[작업 실행 워크플로우](../../../docs/workflow/100-work-execution-workflow.md)가
판정합니다.

## 2. 하나의 인과 모델

비자명한 설명은 다음 모델에서 질문에 필요한 연결만 사용합니다.

```text
출처·생산자
→ 값·artifact
→ 필요한 해석·변환·판정
→ 소비자의 실제 행동
→ 관찰 결과와 사용자의 판단
```

선택한 코드·설정의 정체와 이유를 묻는 설명은 이 모델을 다음 dependency 순서로
구체화합니다.

```text
원문 literal·실제 문법 → 각 token이 가리키는 대상·역할
→ 왜 이 exact 이름·값인가 → consumer의 판정·행동
→ 현재 코드가 바꾸는 상태 → 변경 전·후와 변경 이유
```

현재 literal에 없는 선택 field를 필수인 것처럼 소개하거나, 뒤 연결의 전제로 쓸 새
용어를 정의하지 않은 채 이 경로를 완료로 계산하지 않습니다. 상세 gate와 repair 절차는
[code-and-config.md](references/code-and-config.md)의 설명 dependency 절을 따릅니다.

모든 항목과 상세 reference의 근거 field를 내부에서 확인하되 답변에 무조건 다 노출하거나
그 field 순서를 답변 목차로 사용하지 않습니다. reference가 고정 evidence card나 조사
순서를 제시해도 이 user-facing 조립 계약을 대체하지 않습니다. 한 문장으로 정확히 정의할
수 있는 질문은 쉬운 전체 뜻과 concrete 사례 하나면 충분합니다. 값이 여러 단계를 건너거나
두 대상을 혼동할 위험이 있을 때만 빠진 연결을 펼칩니다.

첫 화면은 다음 순서로 만듭니다.

1. 선택 span 전체의 뜻을 일상어 중심의 한 문장으로 직접 답합니다. token 분류나 상위
   흐름을 이 문장보다 앞세우지 않습니다.
2. 사용자가 물은 token·차이를 그 전체 뜻에 붙이고, concrete 입력 하나가 어떤 관찰 결과를
   만드는지 바로 보여 줍니다.
3. 결론에 꼭 필요한 새 용어만 최초 인과 사용 문장 안에서 닫습니다. 정의가 또 다른
   미정의 기술 명사에 기대면 정의로 계산하지 않고, 더 앞의 쉬운 개념부터 설명하거나 그
   용어를 제거합니다.
4. 선택 span이 앞 단계의 값·artifact를 소비하거나 뒤 단계의 효과를 유발하면, 사용자의
   `무엇·왜`를 답하는 데 필요한 경계까지만 producer와 최초 consumer를 concrete 값 하나로
   연결합니다.
5. 같은 상위 목적에서 두 단계가 서로 다른 상태를 바꾸면 그 차이와 별도 단계가 필요한
   이유를 자연스러운 before→after 설명으로 붙입니다. evidence card의 field 이름을 그대로
   제목이나 목록으로 출력하지 않습니다.
6. 잘못 고르면 결과가 달라지는 지점과 적용 범위가 있을 때만 덧붙입니다.

이 순서의 source 경계와 handoff chain은 0절 admission을 적용합니다. 사용자가 직접 의미를
사용해 known임을 보인 값만 반복 정의하지 않습니다.

`CI가 안다`, `설정이 사용한다`, `연결된다`처럼 actor와 행위를 숨기지 않습니다.
생산자, 전달되는 실제 값, 판정 주체와 소비자의 동작을 확인된 범위에서 씁니다.
`parser`, `consumer`, `producer` 같은 역할명은 대상의 고정 신분이 아니라 특정 artifact에
대한 관계입니다. 따라서 역할을 쓸 때마다 `누가 → 무엇을 → 어떤 행위로 → 어느 phase에서`
관여하는지 결속하고, source에서 앞뒤에 있다는 위치를 호출·전달·인과 관계로 바꾸지
않습니다.
정확한 중간 전제를 독자가 대신 추론하게 두지 않되, 질문과 무관한 edge case를
선제적으로 나열하지 않습니다.

문법 분류, source 권위와 공식성은 직접 답의 근거이지 별도의 선행 목표가 아닙니다.
사용자가 이름·글자·표현을 이해하고 기억하려는 경우에는 그 표기와 기억 가능한 의미,
실제 동작의 연결을 첫 결론에 둡니다. 공식 유래가 확인되지 않는다는 판정은 근거 수준을
제한할 뿐, source로 뒷받침되는 기억 연결을 뒤로 밀거나 동작 설명으로 대체하지 않습니다.

선택 span이 여러 token으로 이루어진 문법이면 token별 효과를 나열하기 전에 span 전체의
종류와 최초 해석자를 한 문장으로 정의합니다. 그다음 문법을 정한 주체와 내부 이름·값의
의미를 정한 주체가 다르면 분리하고, 실제 값이 다음 consumer에 전달되는 경로를 연결합니다.
enclosing line의 나머지 흐름은 이 국소 연결이 닫힌 뒤에만 설명합니다. 실행 context를
바꾸는 span은 `parse·분류 → 값 확장·실행 입력 준비 → consumer 호출 → consumer 사용`의
실제 phase 순서로 설명하고, consumer를 먼저 실행한 뒤 환경·인자·redirection을 전달하는
것처럼 순서를 뒤집지 않습니다.

사용자가 이전 답변에서 처음 등장한 용어를 `X가 뭐야`, `왜 X인데`, `그래서 무엇을
지우는가`처럼 다시 묻거나, 직전 답변이 설명 없이 의존한 source 하위 표현을 선택해
되물으면 별개의 새 질문으로만 처리하지 않습니다. 그 재질문은 이전 설명 단위의
dependency가 닫히지 않았다는 실패 증거입니다. 사용자가 새로 물은 span을 첫 문장에서
직접 답한 뒤, 이전 단위를 무효화하고 최초로 빠진 선수 개념부터 원래 질문의 결론·이유까지
한 번에 다시 조립합니다. 직전 문장만 보충하거나 repair에서 또 다른 미정의 용어를 남기지
않으며, line-by-line 진행 중이면 해당 단위의 다음 line 설명을 중단합니다. repair한 전체
단위를 닫은 뒤에만 기존 coverage 복귀점과 다음 시작 line을 복구합니다.
재질문이 artifact의 필수성·caller·분류축 중 하나를 바로잡으면 최초 질문에서 열렸던 각
판정을 다시 엽니다. 새 직접 답이 기존 판정을 바꾸면 의존한 추천·절차도 함께 폐기하거나
교체하며, caller 한 곳의 국소 보충으로 이전 모순을 남기지 않습니다.

## 3. 요청한 상세

인과 방향이 잡힌 뒤에만 요청한 깊이로 들어갑니다.

- line-by-line은 요약 형식이 아니라 요청한 snapshot의 모든 물리 line을 원래 순서대로
  설명하는 coverage 계약입니다. 여러 line인 하나의 명령·조건·YAML 문법은 함께 설명할
  수 있지만 구성 line을 모두 제시하고 각 line·token의 역할과 차이를 생략하지 않습니다.
  함수·range 요약을 `논리 Line-by-Line`으로 다시 이름 붙여 완료로 계산하지 않습니다.
  상세 형식과 분할·후속 continuation은 [code-and-config.md](references/code-and-config.md)의
  Line-by-line 절을 따릅니다.
- 두 대상의 관계는 실제 actor, 행위, 직접 대상과 결과를 같은 설명에 둡니다.
- 세 단계 이상의 흐름이나 세 개 이상의 반복 비교는 작은 표·diagram을 고려합니다.
  한 문장으로 분명한 관계에 큰 시각화를 만들지 않습니다.
- 범위가 커서 한 응답에 같은 품질을 유지할 수 없으면 commit·파일·함수 경계는 응답을
  나누는 전달 경계로만 사용합니다. 그 경계 안에서도 line coverage를 줄이지 않고, 현재
  완료한 exact line·남은 exact line·다음 시작 line을 밝힙니다. 진행 중 사용자가 한
  line·용어를 다시 물어도 전체 요청을 취소한 것으로 보지 않으며, 국소 답 뒤 기존
  coverage와 다음 시작점을 복구합니다. 사용자는 대상을 다시 열거하지 않고 `계속` 같은
  짧은 후속 표현만으로 그 지점부터 이어갈 수 있어야 합니다.

일반 정의와 이 저장소에서의 역할을 분리합니다. 비유는 문자 그대로의 설명 뒤에만
사용하고 정확한 범위와 한계를 밝힙니다.

## 4. 사실·시간·이유

다음을 문장 가까이에서 구분합니다.

- 현재 구현과 직접 wiring에서 확인한 사실
- 문서상 계약·의도
- 외부 제품의 공식 동작
- 확인한 사실에서 도출한 기술적 추론
- 현재 source로 확인할 수 없는 공백

commit이나 과거 파일은 당시 snapshot, 현재 구현과 목표 흐름을 분리합니다. 일반적인
장점을 저장소 작성자의 실제 선택 이유로 바꾸지 않습니다. `왜`에는 명시된 결정 근거,
구조에서 도출한 추론과 일반 원리를 구분합니다.

commit hash·과거 diff·선택 line은 설명의 초점이지 현재 시간축의 제외가 아닙니다.
사용자가 `그 당시만`, `현재는 제외`처럼 현재 축을 명시적으로 닫지 않았다면 현재 구현을
확인하고 `지금도 문제인가·쓰이는가`를 첫 결론에 둡니다. snapshot에서 발견한 한계마다
현재 처분을 `유지·후속 수정·교체·제거·확인 불가` 중 실제 source가 증명하는 상태로
연결하며, 현재 판정을 별도 후속 질문으로 넘기지 않습니다.
첫 문단만 남겨도 현재 문제 여부·현재 역할과 snapshot의 현재 기여·handoff를 답할 수
있기 전에는 과거 code·line과 당시 한계의 상세를 시작하지 않습니다. snapshot의 함수명·
line을 바로잡는 문장도 이 현재 판정 카드를 대신하지 않습니다.

## 5. 독자 oracle

상세를 가리고 첫 화면만 읽습니다. 처음 접한 독자가 추가 추론 없이 다음을 답할 수
있어야 합니다.

```text
질문의 직접 답은 무엇인가?
선택한 exact span 자체가 첫 답변 단위이며 enclosing context로 확대되지 않았는가?
사용자가 이해·기억하려던 연결은 무엇이며 첫 결론에 있는가?
필수 새 용어는 어떤 종류이며 누가 만들거나 사용하는가?
원문을 복사한 것뿐인 이름을 사용자가 안다고 가정하지 않았는가?
선택 표현의 실제 문법·대상·역할·exact 이름의 이유·상태 변화 이유가 한 단위에 있는가?
실제 필수 선행조건과 단순 권장 순서·리마인더는 무엇이며, 독립 트랙은 어디서 처음 합류하는가?
관계를 말한다면 양 끝 대상·전달 artifact·직접 행위가 실제 source와 일치하는가?
commit 설명이면 첫 문단만으로 현재 판정·지속 기여·후속 handoff를 알 수 있는가?
완결성 판정이면 같은 결과를 바꾸는 독립 경로와 확인하지 않은 경계를 source에서 닫았는가?
무엇을 선택하거나 하지 말아야 하며 그 범위는 어디까지인가?
```

하나라도 답할 수 없으면 설명 전체를 늘리지 말고 최초로 끊긴 연결만 복구합니다.
반대로 질문이 단순한데 불필요한 단계·예외·표가 남으면 제거합니다.

초안을 보며 독자가 다시 `그 말은 뭐야?`라고 물을 가능성이 있는 기술 명사를 표시합니다.
각 명사는 `직접 선행 문맥에서 이해가 확인됨 / 같은 문장에서 일상어로 닫힘 / 삭제됨` 중
하나여야 합니다. 원문 token을 사용자가 복사했다는 사실은 첫 상태의 증거가 아닙니다.
`객체는 object다`, `consumer가 소비한다`처럼 이름을 바꿔 반복하거나 다른 미정의 역할명으로
넘긴 것도 닫힌 정의가 아닙니다. 국소 질문의 답이 내부 조사 목차 때문에 여러 heading·표로
늘어났다면 먼저 쉬운 전체 뜻과 예시로 다시 압축하고, 실제로 구분할 여러 단계가 있을 때만
구조를 사용합니다.

추가로 다음을 확인합니다.

- 첫 문장이 직접 판정이며 애매한 가능성 표현으로 회피하지 않습니다.
- 원문의 모든 질문 행을 최종 답변의 문장에 역대조했고, 요구한 답의 종류를 목적·순서·
  lifecycle·인접 질문의 값이 대신하지 않았습니다.
- Agent가 제시한 모든 행동 단계는 현재·제안·미확정 상태와 actor·event·위치·실제 수단·
  대상·결과가 같은 항목에서 닫혔으며, 동작명이나 인접 화살표로 빠진 값을 대신하지
  않았습니다.
- 새 이름은 최초 인과 사용 전에 정의됐습니다.
- 이전 답변 때문에 생긴 `X가 뭐야·왜 X인가·그래서 무엇이 달라지는가` 재질문이면,
  새 span을 직접 답하면서도 X만 보충하지 않고 원래 설명 단위를 최초 누락부터 결론까지
  교체했습니다.
- lifecycle의 차이를 묻는데 phase를 나열했다면, 설정 원본·현재 실행 상태·새 실행
  상태와 그 사이를 바꾸는 event를 구분해 같은 점·다른 점을 첫 결론에서 답했습니다.
- 남은 단계나 순서를 말하면 모든 필수 선행 edge가 `producer 결과 → 처음 소비하는 exact
  단계`로 설명됩니다. 나중의 적용·검증 전제를 앞선 설계·작성 단계까지 소급하지 않으며,
  지금 시작 가능한 독립 트랙과 최초 합류점·늦어도 필요한 시점이 보입니다.
- 사용자가 `왜 A가 먼저인가`, `A 없이는 B를 못 하는가`, `둘이 연결되는가`를 되물으면
  직전 문장만 완화하지 않고 원래 의존 지도 전체를 다시 판정했습니다.
- 구현 선택 질문이면 첫 화면만으로 현재 방식, 본래 필수인지 여부, 실제 선택 근거의
  증거 수준, 현재 조건에서의 합리성, 같은 결과의 실질 대안과 trade-off를 판단할 수
  있습니다. 첫 두 문장에 앞의 네 판정이 모두 있고, 현재 구현의 작동 경로나 기술 용어
  목록이 이 판정을 대신하지 않았습니다.
- 선택 공간·필수성·합리성을 되묻는다면 직전 설명을 보충하지 않고 원래 선택 질문을
  무효화해 [implementation-choice.md](references/implementation-choice.md)의 첫 화면부터
  전체 답을 교체했습니다.
- 현재 화면·출력의 literal로 인용한 문자열마다 최초 출처와 읽을 수 있는 target 증거가
  있습니다. 긴 screenshot의 전체 view나 실패한 OCR을 exact text 증거로 사용하지
  않았습니다.
- `사용한다`, `실행한다`, `보장한다`마다 caller·조건·대상·결과 근거가 있습니다.
- 확인 불가와 미실행을 현재 사용이나 성공으로 승격하지 않습니다.
- concrete 사례와 최종 판단이 일치합니다.

최종 답변에는 내부 gate와 조사 일지를 노출하지 않고 결론, 필요한 인과, 근거와
사용자가 요청한 상세만 전달합니다.
