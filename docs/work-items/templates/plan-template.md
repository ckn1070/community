## 현재 결론과 다음 행동

이 표는 상세 내용보다 먼저, 다음 안정 actor가 대화 없이 행동할 수 있게 씁니다. 한 행에는
하나의 결론·상태·행동만 둡니다. `현재 결론`에는 현재 단계 후보 전체의 단일 판정만 쓰고,
닫힌 범위나 남은 gate를 섞지 않습니다.

| 항목 | 현재 값 |
| --- | --- |
| 현재 단계 | `결과 정의` |
| 현재 결론 | `<검토 가능/결정 필요/차단 등 현재 단계 후보 전체에 대한 단일 판정>` |
| 닫힌 결과 | `<다시 묻지 않을 대상·결과·제약과 보증하지 않는 경계>` |
| 남은 gate | `<gate identity>: <canonical 상태>. <외부 gate이면 owner와 처음 막는 downstream 효과>` |
| 지금 actor | `<모든 gate 뒤 처음 행동할 안정 actor>` |
| 지금 할 일 | `<그 actor가 수행할 exact 행동 하나>` |
| 사용자 차례 | `<지금 필요한 결정 ID 전체/차례가 오는 조건/사용자 작업 없음>` |
| 응답 방식 | `<본문 결합 응답 형식 또는 design의 결정 ID·exact anchor/exact 단계 확정·수정 방식/해당 없음>` |
| 이 행동 뒤 결과 | `<만들어질 artifact·상태와 첫 consumer>` |
| 다음 단계 전환 | `<현재 단계 closure와 다음 단계가 열리는 조건>` |

`남은 gate`가 둘 이상이면 identity별로 행을 반복하고, 없으면 `남은 gate | 없음`을
유지합니다. 사용자가 지금 actor가 아니어도 `사용자 차례`와 `응답 방식`을 삭제하지 않고
각각 `사용자 작업 없음`, `해당 없음`으로 표시합니다. 본문과 `-design`이 함께 존재하면
같은 순서·값을 투영하되 상세 근거는 owner section으로 연결합니다.

### 활성 결정

사용자가 지금 선택해야 하는 제품 결과·범위·수용 값이 있을 때만 이 block 전체를 둡니다. 현재 source와 닫힌
선행 결과로 완전한 후보를 만들 수 있는 독립 결정은 모두 포함합니다. 이미 확정된 결정은
여기서 제거하고 같은 ID의 `결정 색인 > 본문 소유 확정 결과 결정`로 옮기며, 선행 선택 없이는 후보 차이를 만들 수 없는 결정은
아직 질문하지 않습니다. 장기 복원할 기술 결정은 `-design`의 활성 block 한 곳만 소유하고
이 본문의 `응답 방식`이 그 결정 ID와 exact anchor를 가리킵니다.

#### R1. `<한 번의 응답으로 닫을 수 있는 결정 질문>`

결정 질문은 `<현재 맥락에서> <실제 후보 중> <어떤 결과를 정할 것인가?>`로 씁니다.
구현 방법을 모르는 상태나 이미 확정된 값을 질문으로 바꾸지 않습니다.
다른 값을 고정한 채 이 값만 바꿀 수 있거나 다른 consumer·영향·재검토 조건이 생기는 값은
같은 주제·응답 시점이어도 별도 카드로 분리합니다. 여러 카드는 아래 결합 응답 형식으로 함께
받을 수 있지만 한 카드나 비교표에 합치지 않습니다.

- 사용자 소유 근거: `<제품 결과·비용·운영 의사처럼 이 값을 사용자만 정할 수 있는 이유>`
- 공통 전제·제약: `<모든 후보에 같은 source 사실·닫힌 요구·비교 시작 상태>`

| 비교 축 | A. `<실제 후보>` | B. `<실제 후보>` |
| --- | --- | --- |
| `<현재 목표에서 결과를 바꾸는 축>` | `<구체적 구조·행위 → 상태 변화 → 효과·비용·위험>` | `<같은 축과 인과 문법의 실제 차이>` |
| `<두 번째 축>` | `<실제 차이>` | `<실제 차이>` |

- 추천: `<후보 하나>`
- 추천 근거: `<보존할 목표 → 두 후보의 결정적 차이 → 이 후보가 목표를 만족하는 이유>`
- 판정 기준·우선순위: `<사용자 요구·source에서 나온 필수 기준 → 통과 후보의 우열 기준>`
- 비채택 대안: `<후보별 필수 기준 위반 / 충족하지만 현재 우선순위에서 뒤지는 이유>`
- 감수 비용·위험: `<추천을 택할 때 실제로 부담하는 비용과 실패 표면>`
- 근거·한계: `<판정을 뒷받침하는 요구·source 위치 / 아직 확인하지 못한 주장>`
- 재검토 조건: `<관찰 가능한 event/threshold/source 변경 → 다시 열 결정 ID>`

후보가 셋이면 열을 하나 추가합니다. 같은 질문·시작 상태·목표 종료 상태가 아닌 후보는
같은 표에 넣지 않습니다. `장점/단점/기타`나 모든 대안에 같은 설명이 들어가는 축은
비교축이 아닙니다. 장기 기술 대안의 상세 비교는 `-design`이 소유하고, 이 카드는 사용자가
소유한 결과 값만 비교합니다.

표 앞에서 후보가 실제로 어떤 사용자 경험·업무 결과를 만드는지 설명하고, 비교 축마다 현재
목표와의 관계를 밝힙니다. ‘편리함’, ‘안전함’ 같은 평가어만 쓰지 않고 누가 어떤 조건에서
무엇을 할 수 있거나 할 수 없게 되는지 씁니다. 기술 용어가 판단에 필요하면 첫 사용 위치에서
그 대상과 역할을 풀어 설명합니다. 추천 이유를 읽으려고 기술 상세를 먼저 해독하게 하지 않습니다.

#### 결합 응답 형식

`R1=<A 또는 B>, R2=<A 또는 B>`

모든 활성 카드를 한 번에 답할 수 있는 형식은 이곳 하나만 소유합니다. 응답 뒤 만들어질
결과와 다음 단계 전환은 상단 표에만 씁니다.

## 달성할 결과

`<대상/주체>가 <바뀔 상태>가 되며, <보존할 불변식>을 유지하고, <관찰 가능한 결과>로
확인할 수 있습니다.`

해결책 이름이나 작업 목록 대신 완료 뒤 달라질 상태를 씁니다. 결과가 둘 이상이면 하나의
성공 조건으로 함께 검증되는지 확인하고, 독립적으로 관찰·복구해야 하면 work item을 나눕니다.

## 현재 문제와 배경

`<현재 source와 동작> 때문에 <목표와의 exact 간극>이 있고, 그 결과 <사용자·시스템의 실제
영향>이 발생합니다.`

현재 사실과 간극만 씁니다. 대안·구현 순서·원하는 기술을 문제 설명에 미리 넣지 않습니다.
Improvement에서는 이 heading을 `현재 문제`로 바꾸어 같은 문법을 한 번만 쓰고, 아래 조건부
묶음에 별도 `현재 문제` section을 추가하지 않습니다.

문제를 뒷받침하는 source 위치와 그곳에서 확인한 동작을 같은 문단에서 연결합니다. 사용자
요구, source로 확인한 사실, 검증 전 가설을 구분하고 측정하지 않은 성능·부하를 사실로 쓰지
않습니다. 자료가 없으면 정확한 공백과 그 때문에 아직 정할 수 없는 결과를 밝힙니다.

## 범위

- `<포함 표면> → <책임 경계> → <이 결과에 필요한 이유>`

파일 목록을 범위로 대신하지 않습니다. 변경되는 책임과 그 경계를 먼저 쓰고, 파일은 실행
계획에서 source 위치를 식별할 때만 사용합니다.

## 제외 범위

- `<제외 표면> → <보증하지 않는 결과> → <다시 여는 관찰 trigger와 owner>`

`나중에`, `필요 시`처럼 재검토 시점을 복원할 수 없는 표현은 쓰지 않습니다.

## 수용 기준

- [ ] `<조건/입력>에서 <관찰 결과>를 <증거·판정 수단>으로 확인하며, <통과·실패 경계>를 적용합니다.`

각 기준은 달성할 결과나 요구사항 하나 이상과 연결되어야 합니다. 내부 구현 사실만 확인하고
사용자 결과를 입증하지 못하는 기준은 단독 수용 기준으로 두지 않습니다.

정상·실패·경계·회귀 중 해당 결과가 달라지는 조건을 빠뜨리지 않습니다. ‘테스트 통과’,
‘성능 개선’, ‘보안 고려’만으로 끝내지 말고 무엇을 관찰하면 요구가 충족되지 않은 것인지
알 수 있게 씁니다. 수치 기준은 사용자 요구나 source에 근거해야 하며 임의로 만들지 않습니다.
결과 정의에서는 관찰할 조건과 결과만 정하고 테스트 코드·명령·구현 방법은 실행 계획에 둡니다.

## 차단·rollback 변형

계획 중 `Blocked`이면 일반 `계획 단계`를 제거하고 첫 화면을 `현재 결론 → 차단 전 계획
단계 → 닫힌 결과 → blocker identity·상태·owner → 지금 actor·할 일 → 사용자 차례·응답
방식 → 재개할 계획 단계 → closure 조건 → 재개 뒤 결과` 순서로 교체합니다.

선행 결과가 다시 열리면 기존 downstream artifact를 삭제하거나 전부 활성 질문으로 돌리지
않습니다. 결정·artifact별로 `현재 유효`, `부분 재검토 대기`, `전체 재검토 대기` 중 하나를
표시하고, 제외할 decision ID, 첫 downstream consumer, 다시 닫을 조건을 함께 씁니다.

## 작성자용 품질 예시와 대조

이 절은 완성된 작업 문서에 복사하지 않습니다. 아래는 ‘완성된 보고서를 일정 기간 다시
다운로드하는 서비스’의 가상 입력을 사용한 결과 정의 예시입니다. 실제 프로젝트의 요구·
구현·측정 결과가 아니며, 이전 대화 없이 설명 깊이를 맞추기 위한 것입니다.

### 완성 예시: 결과·범위·수용 기준의 연결

**주어진 입력:** P1은 ‘요청자만 완성본을 다시 받을 수 있고 만료 뒤에는 다운로드할 수 없어야
한다’는 사용자 요구입니다. E1은 ‘현재는 생성 화면을 닫으면 완성본을 다시 찾는 경로가
없다’는 확인 사실입니다. 실제 문서에서는 E1을 확인한 source 위치를 함께 연결합니다.
재다운로드 가능 기간은 아직 정해지지 않아 아래 R1에서 사용자에게 묻습니다.

- 현재 문제: E1 때문에 화면을 닫은 요청자가 이미 만든 결과를 다시 받으려면 생성을 반복해야 합니다.
- 달성할 결과: 요청자는 완성본을 정해진 기간 안에 다시 다운로드할 수 있고, 다른 사용자와
  만료 뒤의 요청자는 해당 파일을 다운로드할 수 없습니다.
- 범위: 완성본을 다시 찾는 경로와 재다운로드 허용 여부를 다룹니다. 이는 재생성 없이 결과를
  받되 접근 범위를 제한하기 위해 필요합니다.
- 제외 범위: 파일 생성 속도와 내용 형식은 바꾸지 않습니다. 이 결과를 처리량 개선의 증거로
  사용하지 않습니다.
- 수용 기준: 기간 안의 요청자는 최초 완성본과 동일한 결과를 받으며, 다른 사용자는 파일
  내용을 받지 못해야 합니다. 만료 직전은 허용하고 만료 시각부터는 거부해야 합니다. 기간 값은
  R1의 확정값을 사용합니다. 아직 사용자 결정 전이므로 결과 정의는 닫히지 않았습니다.

### 완성 예시: R1. 완성본을 얼마 동안 다시 받을 수 있게 할 것인가

**사용자 소유 근거:** 편의와 접근 가능 기간 사이의 제품 정책을 정하는 값입니다.

**공통 전제:** P1의 요청자 제한은 두 후보에 똑같이 적용합니다. 사용자가 제시한 후보는 완료
시각부터 1일 또는 7일이며, ‘완료 뒤 24시간 이내에 다시 받으면 충분하고 접근 가능 기간을 짧게
유지하는 편을 우선한다’는 선호가 있습니다. 원본 데이터의 보존 기간과 물리적인 파일 삭제
시점은 이 결정에 포함하지 않습니다.

| 비교 축 | A. 완료 시각부터 1일 | B. 완료 시각부터 7일 |
| --- | --- | --- |
| 다시 받을 수 있는 시간 | 완료 뒤 24시간 안에 다시 받을 수 있습니다. 이 시간이 지나면 새 생성이 필요합니다. | 완료 뒤 7일 안에 다시 받을 수 있어 며칠 뒤에도 재생성을 피할 수 있습니다. |
| 접근 허용 기간 | 만료 검사가 올바르면 1일 이후의 다운로드는 거부됩니다. 더 짧은 기간만 완성본 접근을 허용합니다. | 같은 요청자에게 6일 더 접근을 허용합니다. 다른 사용자에 대한 권한이 늘어나는 것은 아닙니다. |
| 현재 목표 판정 | P1을 만족하며 짧은 접근 기간을 우선하는 사용자 선호에 맞습니다. | P1을 만족하지만 더 긴 재이용 편의를 우선하는 선택입니다. |

**추천: A. 1일.** 요청자 제한과 만료 후 거부가 필수 기준이고, 두 후보 모두 이를 만족합니다.
그다음 사용자가 정한 ‘짧은 접근 기간’ 우선순위를 적용하면 A가 맞습니다. 대신 1일 뒤 다시
필요한 요청자는 재생성해야 합니다. B가 불안전해서 탈락한 것이 아니라 현재 편의·기간
우선순위에서 채택하지 않는 것입니다.

- 근거·한계: P1과 명시된 사용자 선호에 따른 추천입니다. 실제 재다운로드 빈도·저장 비용은
  측정하지 않았으므로 ‘대부분 충분하다’거나 ‘비용이 크게 줄어든다’고 주장하지 않습니다.
- 영향·비보증: 다운로드 허용 기간만 정합니다. 만료 즉시 물리적으로 삭제된다는 보장은 아닙니다.
- 재검토 조건: 제품 요구가 ‘완료 3일 뒤에도 재생성 없이 다시 받아야 한다’로 바뀌면 R1과
  만료 수용 기준을 다시 엽니다.
- 응답 방식: `R1=A 채택·반영` 또는 `R1=B 채택·반영`. 값만 선택한 응답은 세션의 선택 후보만
  갱신하며 문서를 확정 상태로 바꾸지 않습니다. 채택·반영 요청이 있을 때 같은 ID의 확정
  결정으로 옮겨 비교 근거를 보존하고 수용 기준의 기간을 채웁니다. 이 값의 확정과 현재 단계
  전체의 확정은 구별하며, 단계 전환은 기존 lifecycle의 조건을 따릅니다.

### 미달 예시와 이유

> 재다운로드 기능을 추가합니다. 1일은 보안성이 좋고 7일은 편리합니다. Best Practice에
> 따라 1일을 추천하며 충분히 테스트합니다.

이 설명은 누가 언제 어떤 결과를 받는지, 두 기간을 어떤 우선순위로 평가하는지, 보안성이
어떤 의미인지, 무엇을 확인해야 통과인지 알 수 없습니다. ‘1일’이라는 같은 결론을 냈어도
그 판단을 다른 작업자가 복원할 수 없으므로 미달입니다.

활성 결정이 없으면 비교 카드를 억지로 만들지 않고 확정 결과와 남은 단계 전환만 확인합니다.
원래 요구에서 본문·수용 기준으로, 본문의 각 결과에서 요구·source로 양방향 대조합니다.
작성 중 채팅으로만 설명한 내용이 판단에 필요하다면 해당 질문의 본문 owner에 반영합니다.
