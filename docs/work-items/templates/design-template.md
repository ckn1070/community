## 비교 방법과 결정 기준

| 우선순위 | 기준 | 통과·탈락 또는 우열 판정 |
| --- | --- | --- |
| 1 | `<보존해야 할 필수 목표>` | `<위반 후보를 탈락시키는 관찰 경계>` |
| 2 | `<핵심 효과·증거>` | `<후보 간 우열을 가르는 실제 결과>` |
| 3 | `<비용·유지보수성>` | `<필수 목표가 동률일 때만 적용할 tie-break>` |

필수 기준 위반 후보를 먼저 탈락시키고, 핵심 효과와 증거를 비교한 뒤, 동률일 때만 비용을
적용합니다. 점수 합산이나 `Best Practice`라는 이름만으로 선택하지 않습니다.

각 기준이 어느 닫힌 목표·제약에서 나왔는지 함께 밝힙니다. 정확성·장애·보안·확장성·비용을
모두 같은 비중의 상투적인 행으로 넣지 말고, 현재 선택을 실제로 바꾸는 기준을 고릅니다.
필수 기준을 모두 만족하지만 덜 적합한 후보와, 필수 기준을 위반해 사용할 수 없는 후보를
구별합니다. 우열을 가를 근거가 없으면 동률 또는 미확정이라고 씁니다.

## 결정

아래 네 유형은 배타적입니다. 실제 결정마다 한 유형만 복사합니다.

### 유형 A — 비교 결정

#### D1. `<한 번의 선택으로 닫을 설계 차원>`

**결정 질문:** `<현재 맥락에서> <실제 후보 중> <어떤 목표 결과를 정할 것인가?>`

**공통 전제:** `<모든 후보에 같은 시작 상태·source 제약·보존 목표>`

각 후보가 실제로 무엇을 하는지 첫 등장에 풀어 씁니다. 기술명만 나열하지 않고 `누가 어떤
입력을 받아 무엇을 처리하고 어디에 결과를 넘기는 방식인지`를 밝힙니다. 공통 전제에는 왜
지금 이 문제를 정해야 하는지와 이 결정에서 바꾸지 않는 범위도 포함합니다.

| 비교 축 | A. `<실제 후보>` | B. `<실제 후보>` |
| --- | --- | --- |
| `<결과를 바꾸는 축>` | `<구체적 구조·행위 → 상태 변화 → 효과·비용·위험>` | `<같은 축과 인과 문법의 실제 차이>` |
| `<운영·실패·관찰 축>` | `<실제 차이>` | `<실제 차이>` |
| 현재 목표 판정 | `<통과/탈락 → exact 이유>` | `<통과/탈락 → exact 이유>` |

**선택: `<후보 하나>`**

`<보존할 목표>`를 유지하려면 `<두 후보의 결정적 차이>`가 필요하므로 이 후보를 선택합니다.
그 대신 `<감수할 비용·위험>`을 받아들입니다.

- 배제 대안: `<후보> — <필수 기준 위반 또는 현재 목표에서 뒤지는 exact 이유>`
- 근거 한계: `<선택 근거로 사용하지 않는 주장과 그 이유>`
- 목표 계약·영향: `<owner/caller/input/action/output/failure 경계>`
- 보증하지 않음: `<이 선택만으로 보장되지 않는 결과>`
- 재검토 조건: `<관찰 가능한 event·threshold·source 변경 → 다시 열 ID와 consumer>`

공통점은 표 앞에 한 번만 쓰고, 셀에는 차이만 씁니다. `더 좋다`, `단순하다`, `유연하다`는
구조·상태 변화와 측정 가능한 결과가 뒤따르지 않으면 비교 근거가 아닙니다.
비교 축은 앞의 목표·판정 기준과 연결하고 모든 후보를 같은 조건에서 평가합니다. 한 후보의
기본 기능과 다른 후보의 추가 구현을 비교하면 추가 책임·비용도 같은 축에 표시합니다.
대안이 현재 목표를 만족하도록 보완될 수 있다면 불가능하다고 단정하지 말고, 필요한 보완과
그 뒤에도 남는 차이를 설명합니다. 표를 읽은 뒤 독자가 차이의 중요성을 추론해야 한다면
해당 셀에 사용자 결과·실패 범위·운영 부담 중 실제 영향을 보완합니다.
선택 문장과 아래 prose에는 이 ID의 독립 변경값만 둡니다. 다른 축의 default·owner·경계·
표현·위치·version·운영 수단은 해당 ID나 고정·source 파생 block으로 이동합니다.

### 유형 B — 고정 입력

고정 입력은 위 `R0` 형식으로만 기록합니다. 선택·추천 문장을 만들지 않습니다.

### 유형 C — source 파생 계약

#### D1-C. `<source에서 유일하게 파생되는 계약>`

- 근거 source와 현재 사실: `<source → 관찰 사실>`
- 파생 규칙: `<사실 → 유일한 계약>`
- 허용 결과: `<이 계약이 여는 downstream 행동>`
- 금지 결과: `<이 계약만으로 확정할 수 없는 것>`
- 검증·재검토: `<source 대조 증거 → 변경 시 다시 열 consumer>`

후보가 실제로 하나라면 억지 비교표나 Agent 추천을 만들지 않습니다.

### 유형 D — 입력 부재·보류 gate

#### D1-B. `<현재 닫을 수 없는 결정>`

- 부족한 입력: `<정확한 값·source·권한>`
- 현재 확인한 범위: `<확정 사실과 미확정 경계>`
- 지금 금지되는 결론: `<가정하면 안 되는 결정·downstream 효과>`
- 입력 owner와 획득 행동: `<actor → exact 행동>`
- 처음 막는 consumer: `<단계·결정·결과>`
- 입력 뒤 비교 후보: `<실제 후보 A/B/...>`
- 후보가 공유할 목표 종료 상태: `<같은 질문에서 모두 달성하려는 결과>`
- 재개 조건: `<관찰 가능한 terminal 상태>`

Agent의 불확실성을 사용자 결정 부재로 바꾸지 않습니다. 접근 가능한 source가 있으면 먼저
끝까지 읽고, 정말 사용자만 소유한 값일 때만 활성 결정으로 올립니다.

새 외부·내부 도구가 결정 결과에 포함될 때만 둡니다.

| 질문 | 답 |
| --- | --- |
| 해결할 exact 문제 | `<현재 수단이 충족하지 못하는 결과>` |
| 기존·최소 대안 | `<추가 도구 없이 가능한 경로와 탈락 근거>` |

| 실패·운영 비용 | `<failure mode, owner, 유지관리 부담>` |

도구 이름이나 학습 목적 자체를 도입 근거로 쓰지 않습니다.

## rollback 시 보존

선행 결과가 다시 열리면 decision별로 `현재 유효`, `부분 재검토 대기`, `전체 재검토 대기`
중 하나를 표시합니다. 부분 재검토는 제외할 ID, 첫 downstream consumer, 다시 닫을 조건을
함께 쓰고, 영향받지 않은 결정은 활성 질문으로 되돌리지 않습니다. 공통 전제가 무효일 때만
전체 소비를 금지합니다.

## 작성자용 품질 예시와 대조

이 절은 템플릿 사용자를 위한 설명 깊이의 기준이며 완성된 작업 문서에 복사하지 않습니다.
아래는 가상의 파일 생성 서비스입니다. `E1/E2`는 예시 안에서 주어진 사실이며 이 저장소의
구현·측정 결과가 아닙니다. 실제 문서에서는 현재 source 위치와 관찰 결과로 대체합니다.

### 완성 예시: D1. 생성한 파일을 언제 다운로드 가능하게 만들 것인가

**결정 질문:** 파일 생성 중 실패하더라도 사용자가 일부만 작성된 파일을 받지 않도록,
다운로드 공개를 어느 시점에 허용할 것인가?

**공통 전제:** 두 후보 모두 같은 입력으로 파일 하나를 만들고, 성공하면 요청자에게 완성본을
제공합니다. E1에 따르면 현재 생성기는 최종 파일 위치에 순차적으로 쓰며, 다운로드 경로는
파일 존재만 확인하므로 생성 도중에도 일부를 읽을 수 있습니다. E2에 따르면 저장소는 비공개
파일 작성과 완성본 참조의 원자적 게시를 지원합니다. 원자적 게시란 독자가 게시 전 상태 또는
완료된 참조 중 하나만 보고 중간 상태는 보지 않는다는 뜻입니다. 생성 알고리즘·접근 권한·
실패 파일 정리 정책은 이 결정에서 바꾸지 않습니다.

**판정 기준:** 사용자 요구인 ‘불완전한 파일 제공 금지’를 필수 기준으로 적용합니다. 이를
만족한 후보끼리는 새로 관리할 상태와 실패 처리 책임이 적은 쪽을 우선합니다.

| 비교 축 | A. 파일 존재 시 공개 | B. 완성본 참조 게시 뒤 공개 |
| --- | --- | --- |
| 공개 동작 | 다운로드 경로가 파일 존재만 확인합니다. 첫 쓰기부터 읽을 수 있어 생성 중인 내용도 사용자에게 전달됩니다. | 생성기는 비공개 파일을 완성한 뒤 참조를 게시합니다. 다운로드 경로는 게시된 참조만 읽어 완성 전 파일을 제공하지 않습니다. |
| 생성 중 실패 | 일부 파일이 남아도 존재 검사를 통과하므로 불완전한 결과를 제공할 수 있습니다. E1의 실패 경로입니다. | 게시 전 실패이면 다운로드 가능한 참조가 없습니다. 사용자는 불완전한 파일 대신 아직 제공할 결과가 없다는 상태를 받습니다. |
| 관리 책임 | 현재 존재 검사만 유지합니다. 별도 게시 상태는 없지만 필수 결과를 지키지 못합니다. | 생성 완료와 공개 가능 상태를 구별하고 게시 실패를 처리해야 합니다. 비공개 파일 정리는 기존 정책이 계속 소유합니다. |
| 현재 목표 판정 | 필수 기준 위반으로 탈락합니다. | E2의 원자적 게시와 게시된 참조만 읽는 경계가 유지되면 필수 기준을 만족합니다. |

**선택: B. 완성본 참조 게시 뒤 공개.** 불완전한 파일 제공을 막으려면 파일이 존재한다는
사실과 공개해도 된다는 사실을 구분해야 합니다. B는 생성 실패가 다운로드 결과로 노출되는
경로를 끊습니다. 대신 별도 게시 상태와 게시 실패 처리 책임을 받아들입니다.

- 배제 대안: A의 존재 검사만으로는 필수 기준을 만족하지 못합니다. A에 완료 상태 검사와
  공개 차단을 추가하면 보완할 수 있지만, 그때는 이 비교의 B와 같은 공개 경계를 도입하는 것입니다.
- 근거 한계: 이 선택은 E1/E2와 실패 경로에 따른 판단입니다. 생성 속도 향상이나 처리량 증가는
  측정하지 않았으며 선택 근거로 사용하지 않습니다.
- 목표 계약·영향: 생성기가 쓰기 완료를 확인한 뒤 완성본 참조를 게시하고, 다운로드 경로는
  게시된 참조만 소비합니다. 생성 또는 게시가 실패하면 다운로드 가능한 참조를 남기지 않습니다.
- 보증하지 않음: 파일 내용의 업무적 정확성과 다운로드 권한은 기존 검증·인가 경계가 소유합니다.
- 재검토 조건: 저장소가 E2의 원자적 게시를 지원하지 않게 되면 D1과 다운로드 경로의 공개
  조건을 다시 검토합니다. 현재 계약을 새 저장소에도 그대로 적용하지 않습니다.

### 미달 예시와 이유

> A는 구현이 간단하고 B는 안정성과 확장성이 좋습니다. 운영 Best Practice에 따라 B를
> 선택합니다. 나중에 규모가 커지면 재검토합니다.

이 설명은 후보의 동작, 같은 비교군인 이유, 어떤 실패를 막는지, 무엇을 추가로 관리하는지,
어느 기준이 선택을 갈랐는지를 복원할 수 없습니다. ‘규모가 커짐’도 어떤 전제가 깨지는지
알려주지 않습니다. 표 안에 이 문장을 옮겨도 미달입니다.

### 완성 여부를 판정하는 질문

활성·확정 비교 결정마다 아래 답을 완성 문서에서 직접 찾습니다. 고정 입력·source 파생·입력
부재는 각 전용 유형의 근거·허용 범위·재개 조건을 확인하며 비교표를 억지로 만들지 않습니다.
항목의 존재나 문장 길이가 아니라 실제 답과 근거를 대조합니다. 이 표를 작업 문서의 새
checklist로 복사하지 않습니다.

| 독자가 답할 질문 | 미달로 보는 상태 |
| --- | --- |
| 무엇을 왜 지금 결정하며 후보들은 왜 같은 비교군인가? | 기술 이름만 나열하거나 서로 다른 질문의 답을 한 표에 묶음 |
| 각 후보는 어떻게 작동하고 같은 조건에서 무엇이 달라지는가? | 후보별 평가 조건이 다르거나 추상적인 장단점만 있음 |
| 그 차이가 현재 목표·실패·운영에 어떤 영향을 주는가? | 작동 방식에서 결과로 이어지는 설명이 빠짐 |
| 어떤 기준을 먼저 적용하고 무엇이 최종 선택을 갈랐는가? | 요약·선택에서 비교표에 없던 우열이나 근거를 새로 도입함 |
| 다른 후보는 왜 채택하지 않았고 선택의 대가는 무엇인가? | 대안을 약하게 만들어 비교하거나 비용·비보증을 생략함 |
| 근거는 어디에 있고 무엇이 아직 미검증인가? | 링크 목록만 있거나 가설을 사실·측정 결과로 표현함 |
| 다음 작업자는 어떤 책임·입출력·실패 경계를 구현하며 언제 결정을 다시 여는가? | ‘적절히 처리’, ‘필요 시 재검토’만 남거나 다른 독립 선택값이 섞임 |

제출 전에는 원래 요구에서 결정·목표 계약으로, 다시 최종 선택 요약에서 상세 비교와 source로
양방향 대조합니다. 빠진 답은 해당 질문을 소유한 절에서 보완하며 같은 설명을 여러 곳에
반복하거나 새 근거를 요약에만 추가하지 않습니다.
