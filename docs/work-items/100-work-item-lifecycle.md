# 작업 문서 생명주기

이 문서는 work item의 유형·상태 label과 계획에서 결과로 전환되는 문서 구조를
소유합니다. work item 생성, 차단·완료, 재개와 후속 분리의 실제 판정은
[작업 실행 워크플로우](../workflow/100-work-execution-workflow.md), 공통 문서 유형과 보존
기준은 [문서 정보 구조 가이드](../100-documentation-guide.md)가 소유합니다.

## 작업 유형

| 유형 | 사용 시점 |
| --- | --- |
| Feature | 새로운 제품 기능 |
| Bug | 기대 동작과 실제 동작의 결함 |
| Improvement | 구조, 품질, 운영, workflow와 문서 개선 |
| Spike | 제한된 범위에서 불확실성을 줄이는 조사 |
| Backlog | 아직 실행 작업으로 전환되지 않은 후보 |

## 상태

| 상태 | 의미 |
| --- | --- |
| Open | 아직 실행 작업으로 전환되지 않은 backlog 후보 |
| Proposed | 결과 정의·해결 설계·실행 계획 중 현재 계획 단계의 결과를 작성·검토 중 |
| Planned | 선택·source 제약·검증된 Agent 기술 선택을 반영한 실행 계획을 사용자가 확정해 구현 입력으로 동결함 |
| In Progress | 확정된 범위를 실행 중 |
| Blocked | 공통 blocker gate가 확정한 입력·권한·외부 상태를 기다리는 문서 상태 |
| Done | 공통 완료 판정이 닫힌 결과를 보존하는 문서 상태 |
| Closed | backlog가 작업으로 전환되거나 폐기됨 |

이 표는 판정을 다시 수행하는 상태 머신이 아니라 canonical owner가 확정한 결과의 문서
label입니다. 계획 검증 통과만으로 `Planned`가 되지 않습니다. 사용자 선택이 남았거나,
선택·source 제약·Agent 기술 선택을 반영한 현재 단계 결과를 사용자가 아직 확정하지 않은
계획 제안은 `Proposed`를 유지합니다. `추천`, `선택`, `확정`의 의미와 사용자 단계 확정
source는 작업 실행 workflow의 활성 결정 기준선을 따릅니다. 공통 blocker·완료 판정은
각각 `Blocked`와 `Done`으로 투영합니다.

## 생성·승격 결과의 문서 투영

문제 발견, work item 생성과 실행 작업 선정은 서로 다른 결과입니다.

```text
발견됨 ≠ Open backlog 등록 ≠ Proposed ≠ Planned
```

[작업 실행 workflow의 새 발견](../workflow/100-work-execution-workflow.md#새-발견)과 권한
판정이 생성·승격 여부를 결정하며, 이 문서는 그 결과를 다음처럼 기록합니다.

- 채팅 보고로 닫힌 발견은 work item을 만들지 않습니다.
- `Open` backlog에는 문제, 직접 근거, 영향, 현재 작업에서 제외한 이유와 다음 결정
  경계만 둡니다. 해결 방법·우선순위·수용 기준을 계획처럼 확정하지 않습니다.
- 실행 후보로 확정된 결과는 목표가 하나인 Feature·Bug·Improvement·Spike의
  `Proposed` 문서에 투영합니다.
- 사용자 소유 값, source 제약과 Agent 기술 선택을 반영·검증한 실행 계획을 사용자가 exact
  범위로 확정한 뒤에만 `Planned`로 투영합니다. 계획 작성·상세화·검증·commit·push 요청과
  verifier verdict는 값 선택이나 단계 확정을 대신하지 않으며, 기술 선택을 사용자 선택으로
  바꾸지도 않습니다.

## 계획 단계와 최소 artifact

이 절은 Feature·Bug·Improvement·Spike의 계획 단계, 단계별 artifact 수와 각 artifact의
책임, 단계 closure와 rollback을 유일하게 소유합니다. 작업 실행 workflow는 권한·상태와
채팅 순서를, 설계 workflow는 설계 방법을, 계획 writer와 verifier는 이 계약의 작성·감사만
소유합니다.

계획은 다음 순서로만 진행합니다.

```text
Proposed/결과 정의
→ Proposed/해결 설계
→ Proposed/실행 계획
→ Planned/계획 완료
```

선행 단계 closure가 다음 결과를 바꿀 수 있으면 선행 단계를 닫기 전에 dependent 다음
단계의 문서·section·후보 상세를 만들지 않습니다. 현재 단계에서 필요한 artifact는
최소화하되, 허용된 artifact에는 그 단계의 결과와 closure 근거를 빠짐없이 둡니다.

이 순서는 새 결정을 작성하고 다음 실행 입력으로 소비하는 순서입니다. 닫혔던 선행 단계가
논의 중 다시 열렸다고 이미 존재하는 downstream artifact를 삭제하지 않습니다. 기존
downstream 결정은 영향에 따라 다음 세 상태로 나눕니다.

| 상태 | 의미 | 소비 규칙 |
| --- | --- | --- |
| 현재 유효 | 다시 열린 값과 무관해 기존 근거·계약이 그대로 성립함 | 후속 설계 입력으로 유지 |
| 부분 재검토 대기 | 바뀌거나 미정인 상위 값의 exact consumer만 아직 확정할 수 없음 | 해당 계약만 구현·실행 계획 입력에서 제외 |
| 전체 재검토 대기 | 공통 전제가 무효여서 artifact 전체를 다시 대조해야 함 | artifact는 기준선으로 보존하되 전체를 구현 입력에서 제외 |

이 상태와 현재 활성 계획 단계, 재개 조건은 work item 본문, 보존된 design 첫 화면과 연도
router에서 같은 관계로 표시합니다. 선행 단계가 닫히기 전에는 미확정 상위 값에 의존하는
새 downstream 상세를 쓰지 않습니다. 다시 열린 값과 독립적인 기존 결정의 보완은 피드백
workflow가 기술 질문으로 분류하고 영향 없음이 확인된 범위에서만 허용합니다.

### 모든 계획 artifact의 첫 화면

Work item 본문과 같은 번호의 `-design`을 포함해 독자 목적이 계획의 작성·검토·확정인 모든
artifact는 파일명이나 현재 단계와 무관하게 [문서 정보 구조 가이드의 Plan](../100-documentation-guide.md#plan)
첫 화면 계약을 적용합니다. 제목과 `상태`·`계획 단계` 바로 다음, 첫 배경·문서 경계·상세
결정 전에 최소한 다음 관계를 보여 줍니다.

```text
현재 단계·결론
→ 닫힌 결과
→ 남은 gate와 source-backed 현재 상태
→ 지금 actor·exact 행동
→ 사용자 차례의 조건·응답 방식
→ 현재 행동 뒤 결과·다음 단계 전환 조건
```

활성 사용자 값 결정이 0개여도 Agent 검증·보완, 현재 단계 후보의 사용자 확정이나 다른
closure gate가 남아 있으면 이 계약을 생략하지 않습니다. 지금 사용자 입력보다 먼저 닫을
Agent gate가 있으면 사용자를 현재 actor로 앞당기지 않고, 그 gate의 상태와 사용자 차례가
오는 조건을 표시합니다. 반대로 모든 gate가 닫혔으면 완료 결론과 다음 허용 행동만 두고
새 결정 카드나 중복 확정을 만들지 않습니다. 상세 결정·근거·검증 계약은 하단의 exact
section이 소유하며 첫 화면은 그 범위로 연결합니다. 후보 작성, 검증 시작·결과, 재검토,
사용자 확정이나 단계 전환이 이 관계를 바꾸면 사용자 검토·다음 actor 인계 전에 work item
본문과 현재 단계의 companion 첫 화면을 같은 상태로 갱신합니다.

상태 전환, rollback, 완료 정규화와 design 정리 중 문서 전체 또는 핵심 독자 질문·canonical
owner 계약·상태나 결정 section 묶음을 실질적으로 없애면 `삭제에 준하는 대규모 제거`입니다.
Git 복원 가능성이나 중복 여부로 이 효과를 축소하지 않으며, 작업 실행 workflow의 명시적
허락과 documentation workflow의 삭제 admission 전에는 기존 내용을 보존합니다. 국소적인
현재값 교체와 고유 계약을 남긴 채 반복 로그·문장을 압축하는 편집은 이 gate의 대상이
아닙니다.

### 적용과 전환

- `계획 단계` field는 `Proposed`와 `Planned` Plan 구조에만 둡니다.
- 이 계약 도입 뒤 새로 생성하거나 다시 여는 work item과 계획 내용을 실질적으로 바꾸는
  모든 Feature·Bug·Improvement·Spike는 변경 전에 이 구조로 전환합니다.
- 계약 도입 전에 존재한 다음 아홉 Proposed Bug는 이번 전환과 독립된 legacy snapshot으로
  유지합니다. 각 문서의 다음 plan-content mutation 전에 현재 source에서 결과 정의부터
  다시 판정하고 `계획 단계`와 현재-stage-only 구조로 이관합니다.
  - `bugs/2026/001-notification-provider-exception-logging.md`
  - `bugs/2026/002-auth-secret-separation-validation.md`
  - `bugs/2026/003-shared-clock-bean-ownership.md`
  - `bugs/2026/004-api-exception-5xx-logging.md`
  - `bugs/2026/005-notification-audit-result-separation.md`
  - `bugs/2026/006-bootstrap-next-action-message.md`
  - `bugs/2026/007-spring-mvc-exception-classification.md`
  - `bugs/2026/008-notification-template-clock.md`
  - `bugs/2026/009-authentication-enumeration-timing.md`
- `In Progress`, `Done`, `Closed`에서는 계획 단계 field를 제거하고 해당 상태 구조만
  사용합니다. 계획 중 `Blocked` 전환은 아래 차단 계약을 사용합니다.

### 결과 정의

`Proposed/결과 정의`의 활성 artifact는 work item 본문 하나입니다. 이 단계에서 `-design`과
구현·수정·실험 계획 문서를 새로 만들지 않습니다. 이전 단계에서 존재하던 `-design`은
위 상태를 표시한 보존 기준선으로 남을 수 있으며 재검토 대기 계약은 활성 구현 입력이
아닙니다. 유형별로 본문은 다음 결과만 소유합니다.

| 유형 | 결과 정의가 소유하는 내용 |
| --- | --- |
| Feature | 제품 결과, 범위·제외 범위, 사용자에게 보이는 요구사항·수용 기준, 사용자 결정 |
| Bug | 기대·실제 동작, 재현·영향, 수정 결과를 바꿀 수 있는 원인 경계, 수정 수용 기준 |
| Improvement | 현재 문제, 목표 결과, 범위·제외 범위, 품질 수용 기준 |
| Spike | 답할 질문, 조사 범위·제한 시간, 성공·중단 기준, 남길 지식 |

API, schema, module, transaction, 해결 대안과 기술 목표 계약, 구현·수정·실험 방법, task와
test 상세는 이 단계에 두지 않습니다. 결과 정의 권위 안의 제품 동작·범위·수용 값이 정확히
선택되거나 명시적으로 유예되고 요구사항과 수용 기준이 정렬되며 활성 사용자 결정이 0개이고,
그 결과 후보를 사용자가 확정했을 때만 닫힙니다. 마지막 값의 채택·반영 원문이 작업 실행
workflow의 무모호 closure 조건을 충족하면 같은 원문이 단계 확정도 소유하며 별도 확인
왕복을 만들지 않습니다. 기술 해결 값은 이 closure 입력이 아니라 해결 설계에서 선택합니다.
다만 원인
경계가 수정 결과나 범위를 바꾸는 Bug는 그 원인 경계가 확인되기 전까지 결과 정의를 닫지
않습니다.

현재 단계에는 활성 결정 블록을 하나만 두고, 그 블록은 현재 source와 닫힌 선행 결과로
선택지를 만들 수 있는 사용자 결정 카드 `0..n`을 모두 포함합니다. 앞 블록의 선택이 있어야
질문·대안·결과 차이를 만들 수 있는 결정만 다음 의존 블록으로 보류합니다. 단계별 진행
지시는 카드 수를 `0..1`로 줄이는 근거가 아닙니다. 현재 단계 안의 서로 독립적인 결정까지
한 번에 하나씩 묻도록 사용자가 exact 범위를 명시한 경우에만 활성 카드를 `0..1`로 제한합니다.
전체 설계 표면 inventory와 채팅에서 다음 블록을 여는 순서는 저장소에 보존하지 않으며 작업
실행 workflow가 소유합니다.

활성 사용자 결정이 하나라도 있으면 상태와 계획 단계 바로 다음 첫 화면에 활성 결정 블록을
둡니다. 현재 결론이 `결정 필요`라면 이 블록 자체가 다음 탐색 경로입니다. 따라서 아래쪽
section을 찾아가라는 안내나 열린 결정의 요약만으로 대신하지 않고, 사용자가 첫 화면에서
바로 판단할 수 있도록 exact 질문, 모든 선택지와 결과 차이, 추천과 근거, 한 번에 답할 수
있는 응답 형식, 답변 뒤 Agent가 보완할 현재 단계 결과와 다음 단계 전환 조건을 함께
제시합니다. 마지막 열린 카드의 응답 형식은 값의 채택·반영까지 표현할 수 있어야 하며,
그 응답 뒤 새 사용자 판단이 생기지 않으면 Agent가 결과 정의를 닫고 다음 단계로 진행한다는
전환 결과도 함께 보여 줍니다.

### 해결 설계

`Proposed/해결 설계`는 결과 정의 closure 뒤에만 엽니다. 본문은 닫힌 결과 정의와 현재
결정 색인·정확한 source 관계를 유지합니다. 다음 조건을 모두 만족할 때만 같은 번호의
`-design`을 추가합니다.

1. 설계 workflow가 적용되는 중대한 설계 표면입니다.
2. 장기 복원할 결정 이유나 목표 계약이 있습니다.
3. 문서 정보 구조 가이드의 새 문서 분리 기준을 만족합니다.

`-design`은 결정 질문, 대안, 선택, 이유, trade-off, 재검토 조건과 목표 계약만 소유합니다.
task, 실행 순서와 test 실행은 소유하지 않습니다. 국소적이고 쉽게 되돌릴 수 있는 기술
선택은 실행 계획에서 정확한 source 관계와 선택으로 기록하고, 일회성 Spike 실험 방법도
실행 계획에 둡니다.

해결 설계 첫 화면은 위 공통 계약에 따라 설계 후보 작성, Agent 기술 선택의 독립 검증과
exact 후보의 사용자 단계 확정을 서로 다른 gate로 표시합니다. 독립 검증이 사용자 확정보다
먼저라면 검증의 현재 상태·actor·행동을 현재 차례로 두고, 통과 뒤 사용자가 확인할 exact
후보 범위와 승인·수정 응답 방식을 함께 보여 줍니다. D번호·기술 표면과 `설계 전체 미확정`
같은 상태 나열만으로 이 actor·행동·전환 관계를 대신하지 않습니다.

`-design`을 만들지 않으려면 새 장기 기술 계약이 없고 모든 구현 영향 값이 기존 SOT나
현재 source로 유일하게 닫혀야 합니다. 이 경우 본문은 그 정확한 source 관계만 연결합니다.
모든 적용 설계 표면이 Agent 기술 선택·source 제약 또는 근거 있는 해당 없음이고, 활성
사용자 결정이 0개이며, 새 장기 계약마다 canonical owner가 하나이고, 그 결과 후보의 exact
범위를 사용자가 확정했을 때 해결 설계가 닫힙니다. 확정은 별도 고정 문구가 아니라 작업 실행
workflow가 복원한 exact 대상과 긍정 채택 의미로 판정하며, 무모호한 진행 요청 뒤 재확인을
추가하지 않습니다.

### 실행 계획과 계획 완료

`Proposed/실행 계획`은 해결 설계 closure 뒤에만 엽니다. 새 문서를 만들지 않고 work item
본문에 구현·수정·실험 결과 단위, 실제 의존 관계, 검증, 전환·복구·처분과 영구 SOT 책임을
추가합니다. `-design`은 task·순서·test 실행을 소유하지 않습니다.

모든 요구가 `-design`의 목표 계약 또는 정확한 기존 SOT, 실행 단위, 검증과 문서 책임으로
이어지고 독립 계획 검증을 통과한 실행 계획 후보를 사용자가 exact 범위로 확정할 때 실행
계획이 닫힙니다. 현재 후보가 하나이고 사용자가 그 계획의 반영·진행을 긍정하면 literal
`확정` 응답을 다시 요구하지 않습니다. 그 뒤에만 상태를 `Planned`,
계획 단계를 `계획 완료`로 투영합니다. `Planned` 본문은 완성된 Plan 구조를, `-design`은
장기 결정과 목표 계약만 유지합니다.

### planning-Blocked

계획 중 실제 blocker로 `Blocked`가 되면 Plan 구조를 현재 Status 구조로 바꾸고 일반
`계획 단계` field를 제거합니다. 대신 다음 재개 계약을 한 곳에 보존합니다.

- `차단 전 계획 단계`: 결과 정의, 해결 설계, 실행 계획 또는 계획 완료
- `재개할 계획 단계와 closure 조건`: blocker 해제 뒤 돌아갈 정확한 단계와 다시 확인할 조건
- `재개 입력`: 차단 직전까지 유효한 현재-stage 결과·확정값의 압축, 정확한 blocker 또는
  필요한 입력·결정 카드, source와 허용된 design 관계

다음 단계 상세를 재개 입력에 추가하지 않습니다. 차단 해제 때 작업 실행 workflow가 blocker와
상위 결과의 유효성을 다시 확인한 뒤 정확한 재개 단계의 Plan 구조로 복원합니다. 상위 결과가
무효화됐으면 기록한 단계보다 앞선 원인 단계로 rollback합니다.

### rollback

- 논의·질문·추가 발견 자체는 rollback trigger가 아닙니다. 실제로 상위 결과가 바뀌거나
  결정이 다시 열릴 때만 그 원인 단계로 돌아갑니다.
- 결과 정의가 바뀌면 `Proposed/결과 정의`로 돌아가 바뀐 결정과 그 exact downstream
  consumer를 찾습니다. 영향받지 않은 design 결정은 `현재 유효`로 유지하고 영향받은
  결정만 `부분 재검토 대기`로 둡니다. 공통 전제가 무효면 design 전체를 `전체 재검토
  대기`로 두되 파일과 router link는 보존합니다.
- 해결 설계가 바뀌면 `Proposed/해결 설계`로 돌아가 영향을 받은 design 결정과 실행 계획의
  첫 consumer만 다시 열고 나머지 결정은 유지합니다.
- 실행 계획만 검증에 실패하면 `Proposed/실행 계획`으로 돌아가 유효한 결과 정의와 해결
  설계를 유지하고 계획만 보완합니다.
- `Planned`도 무효화 원인이 생긴 단계로 같은 방식으로 내려갑니다. 재검토 대기 상세는
  보존된 기준선으로 명시하고 구현·실행 입력에서 제외합니다.
- 보존 기준선의 실제 파일 삭제는 이 rollback의 자동 처분이 아닙니다. 문서 정보 구조
  가이드의 삭제 예외와 작업 실행·문서화 workflow의 명시적 허락·admission을 별도로
  통과해야 합니다.
- `In Progress`와 `Done`의 상위 결과 무효화·재개 판정은 작업 실행 workflow가 소유합니다.

## 본문의 단일 책임

작업 본문은 현재 상태의 진입점이며 상태에 맞는 하나의 구조만 사용합니다.

### Open: Backlog 구조

1. 상태
2. 상단 단일 `목적` 또는 `배경`
3. 아직 작업으로 전환되지 않은 활성 후보
4. 후보별 검토할 문제와 결정 경계
5. 실행 작업으로 전환하거나 폐기하는 조건
6. 현재 SOT와 완료 작업으로 향하는 관계

`Open`은 구현 계획이나 완료 상태를 소유하지 않습니다. 실제 실행을 시작할 후보는 목표와 완료 조건이 하나인 Feature, Bug, Improvement 또는 Spike로 옮기고, 원래 backlog에는 중복 계획을 남기지 않습니다.

### Proposed·Planned: Plan 구조

1. 상태와 계획 단계, 모든 계획 artifact의 첫 화면 결론·현재 actor·다음 행동
2. 현재 단계까지 닫힌 결과와 source 관계
3. 현재 단계에서 허용된 내용
4. 현재 단계의 남은 결정·공백과 closure 조건
5. 관련 문서와 canonical owner

`실행 계획`과 `계획 완료`에서만 의미 단위 계획, 검증·전환·복구와 영구 SOT 책임을
추가합니다. 구체 section은 이 문서의 `계획 단계와 최소 artifact`를 따르며 template의 빈
heading이나 과거 work item 구조를 다음 단계 상세의 생성 근거로 사용하지 않습니다.

### In Progress·Blocked: 현재 Status 구조

1. 상태
2. 상단 단일 `결과`
3. 전체 목표 대비 완료·미완료 결과
4. 정확한 미완료·차단 사유
5. AI와 외부 실행자의 남은 책임
6. 다음 실행자와 시작·완료 조건
7. 확정 결정과 design 링크
8. 영구 SOT 반영 상태

현재 상태를 여러 진행표·완료 목록·검증 기록에서 반복하지 않습니다. 로컬 branch, staged·unstaged 상태, commit SHA와 반복 test 수치는 현재 채팅 보고와 Git이 소유합니다.

### Done: Result 구조

1. 상태
2. 상단 단일 `결과`
3. 완료한 사용자·시스템 결과
4. 보존할 범위와 제외 범위
5. 확정 결정 색인과 design 링크
6. 승격한 영구 SOT
7. 남은 책임 없음 또는 실제 외부 후속 범위

`Done` 전환 때 계획과 실행 과정은 뒤에 누적하지 않고 결과 구조로 교체·압축합니다. Task
순서, 명령 로그, 검증 횟수와 과거 상태를 정규화하기 전에 위 대규모 제거 여부를 판정하며,
Git 복원 가능성은 제거 권한이 아닙니다. Gate 미만의 반복 기록만 결과에 필요한 현재
관계로 압축합니다.

### Closed: Disposition Result 구조

1. 상태
2. 상단 단일 `결과`
3. 후보를 작업으로 전환했는지 폐기했는지에 대한 최종 처분
4. 전환·폐기 사유와 그 판단을 뒷받침하는 현재 SOT
5. 전환했다면 새 Feature·Bug·Improvement·Spike owner
6. 원래 backlog에 남은 활성 후보와 책임이 없는지에 대한 판정

`Closed`는 완료된 구현을 뜻하지 않습니다. backlog 후보의 소유권을 새 작업으로 모두
넘겼거나 더 이상 추진하지 않기로 확정했음을 뜻합니다. 상세 계획과 진행 상태는 새
owner가 소유하며, 원래 backlog에는 중복 계획 대신 처분 결과와 이동 경로만 남깁니다.

작업 카테고리는 `features`, `bugs`, `improvements`, `spikes`, `backlog` 디렉터리 경로가 소유합니다. 본문에 같은 카테고리 section을 반복하지 않습니다.

## 번호와 배치

Work item 번호는 현재 `category/creation-year` 디렉터리 안의 읽기 순서입니다.

- 새 work item은 category의 생성 연도 디렉터리에 직접 만들며 topic 하위 디렉터리를
  만들지 않습니다.
- 현재 work item은 `001`부터 빈자리 없이 증가합니다.
- 본문·`-design`·`-history`는 같은 번호와 slug를 공유하고 번호 하나로 셉니다.
- 새 문서는 현재 마지막 번호 다음에 추가합니다.
- 문서를 삭제·병합하거나 읽기 순서를 바꾸면 뒤의 현재 문서를 다시 번호 붙이고,
  old path와 new path의 move map, router와 모든 inbound link를 같은 변경에서
  갱신합니다.
- 연도 router는 현재 번호 순서와 상태를 실제 파일과 일치시킵니다. 폐기 번호,
  미발급 gap 또는 별도 번호 발급 원장을 유지하지 않습니다.
- 연도나 상태가 바뀌어도 work item은 생성 연도 디렉터리에 둡니다.
- 과거 번호와 경로는 Git commit과 rename 이력으로 복원합니다.

## Design

`-design`은 해결 설계 단계에서 생성 조건을 통과한 장기 결정과 목표 계약만 소유합니다.

- 결정 질문과 배경
- 검토한 선택지
- 선택·근거와 trade-off
- 영향, 배제 대안과 재검토 조건
- API·데이터·transaction·보안·운영 등 확정 목표 계약

구현·검증 task, 실행 순서와 test 실행 기록은 포함하지 않습니다. `Done` 전환 시 파일 목록·
실행 결과를 정규화하기 전에 위 대규모 제거 여부를 판정하고, gate 미만의 반복 기록만
제거하며 고유 결정은 남깁니다. 현재 SOT와 Git은 이 판정을 대신하지 않습니다.

## History

History는 기본 산출물이 아닙니다. Git으로 복원할 수 없고 이후 방어 설계에 필요한 고유 사건만 다음 구조로 보존합니다.

- 사건과 영향
- 시스템 수준 원인
- 기존 방어가 실패한 이유
- 변경한 현재 통제
- 남은 위험과 재검토 조건

대화 원문, Why chain, 날짜별 실행, dirty baseline과 commit 나열은 저장하지 않습니다. 현재 규칙과 필수 실행 기준은 workflow가 소유합니다.

## 결정과 계획

별도 보존 조건을 충족한 장기 결정은 design에 두고 본문에는 결론과 관계 link만 둡니다.
그 밖의 현재 단계 결정은 본문이 소유합니다. 남은 결정은 현재 단계 closure에 필요한 항목만
포함하며 추천, 영향과 응답 형식을 연결합니다. 다음 단계의 작업 후보는 현재 결정 카드에
붙이지 않습니다.

계획의 각 작업은 다음을 답합니다.

- 어떤 결과를 만들 것인가
- 왜 필요한가
- 무엇에 의존하는가
- 어떤 경계를 바꾸는가
- 어떻게 검증하고 복구하는가
- 완료 뒤 무엇을 관찰할 수 있는가

파일 목록과 설정 key는 작업 의미를 대신하지 않습니다.

## 상태 변경의 문서 반영

canonical owner가 상태 변경을 결정한 뒤에만 다음 문서 작업을 수행합니다.

1. 결정된 상태, 결과와 근거 owner를 확인합니다.
2. Plan 구조이면 상단 `상태`·`계획 단계`와 허용 artifact를, 그 밖의 상태이면 상단 `상태`와
   해당 상태의 본문 구조를 함께 바꿉니다.
3. 본문·design·history와 영구 SOT의 현재성·중복·관계를 동기화합니다.
4. category·연도 router의 상태와 요약을 실제 본문에 맞춥니다.
5. 이전 상태의 계획·진행 기록을 현재 구조로 정규화합니다. 문서 전체나 이에 준하는 대규모
   제거이면 명시적 허락·admission 전에는 보존하고, 그 밖의 반복 기록만 제거합니다.
6. 관련 문서 전체와 링크를 다시 확인합니다.

## 재개·후속 결정의 문서 반영

완료 무효화와 같은 work item 재개, 독립된 새 목표의 후속 분리는 작업 실행 workflow가
원래 요구·당시 수용 기준·완료 증거에서 판정합니다. 이 문서는 판정 결과만 보존합니다.

- 재개 결정은 기존 본문을 `In Progress` Status 구조로 바꾸고 잘못된 Result를 현재
  완료·미완료 결과로 교정합니다.
- 독립 후속 결정은 새 work item과 선행 Result의 유효 범위·후속 owner를 양쪽에
  연결하며 선행 본문에 중복 계획을 남기지 않습니다.
- `미완료 없음`은 canonical owner가 닫은 범위에만 투영하고 알려진 외부 책임이나
  검증 공백을 숨기지 않습니다.

## 보존과 종료

- 현재 규칙과 제품·기술 상태는 영구 SOT에 승격합니다.
- 중요한 결정만 design에 남깁니다.
- 반복 실행과 변경 과정은 Git에서 복원합니다.
- 고유 감사 증거만 history 기준으로 보존합니다.
- 완료된 문서가 현재 탐색을 방해하면 먼저 요약·link·상태 표시를 보완합니다. 책임과 모든
  고유 정보가 다른 canonical owner로 완전히 이관된 경우에만 병합·삭제 후보로 분류합니다.

Git 복원 가능성이나 탐색 비용만으로 완료 본문과 design을 삭제하지 않습니다. 실제 삭제는
문서 정보 구조 가이드의 보존 기준과 작업 실행·문서화 workflow의 명시적 허락·admission을
따릅니다.
