# 차량과 분리해 시작하는 일반 커뮤니티

## 상태

Proposed

## 계획 단계

결과 정의

## 달성할 결과

차량 관련 기능이나 데이터가 없어도 독립적으로 사용할 수 있는 일반 커뮤니티의 첫 제품
범위를 정합니다. 사용자는 게시글을 중심으로 댓글과 1단 답글을 주고받을 수 있습니다.
현재에는 대화·참여·운영에 필요한 핵심만 선택하고, 나중에 차량 관계나 추가 커뮤니티 기능을
붙일 때 이미 제공한 일반 커뮤니티를 폐기하거나 차량 전용 커뮤니티로 교체하지 않습니다.

## 범위

- 차량과 연결하지 않고 먼저 제공할 일반 커뮤니티의 제품 범위
- 게시글·댓글·1단 답글로 이어지는 첫 대화 경험
- 첫 게시 공간, 읽기·작성·삭제, 참여·탐색·알림·작성자 표시와 최소 운영 범위
- 이후 차량 관계와 추가 커뮤니티 기능이 기존 핵심과 함께 존재할 수 있다는 제품 경계

## 제외 범위

- 현재 출시 범위의 차량·브랜드·모델·세대·트림 연결 기능
- 무제한 대댓글과 화면에 2단 이상 중첩되는 답글
- 아직 선택하지 않은 부가 기능을 현재 범위로 간주하거나 영구 폐기하는 결정
- 신고 사유 체계, 제재 수위, 복구·이의제기와 보존 기간 같은 상세 운영 정책
- 결과 정의가 닫히기 전의 API, schema, module, transaction, 저장·조회 방식과 구현·검증 task

## 확정된 제품 결과

1. 현재 일반 커뮤니티는 차량 관련 기능과 데이터에 의존하지 않습니다.
2. 미래의 차량 연결은 일반 커뮤니티를 대체하지 않고 기존 핵심에 관계를 추가하는 방식이어야
   합니다.
3. 현재에는 핵심 기능만 포함하되, 이후 기능 추가 때문에 먼저 제공한 핵심 사용자 경험을
   폐기하지 않습니다.
4. 첫 콘텐츠 계층은 게시글·댓글·1단 답글입니다. 현재 화면에는 2단 이상의 답글 계층을
   표시하지 않지만, 이 표시 제한을 미래의 더 깊은 대화까지 영구 금지하는 규칙으로 만들지
   않습니다.

### 1단 답글을 선택한 근거

특정 댓글에 직접 응답하는 경험은 첫 범위에 포함하되, 무제한 중첩으로 생기는 가독성과 운영
복잡도는 현재 범위에 넣지 않습니다. 유명 서비스도 한 방식만 사용하지 않습니다. YouTube는
[최상위 댓글과 답글](https://developers.google.com/youtube/v3/docs/commentThreads)을 한
스레드로 묶고, Reddit은 댓글이
[게시글 또는 다른 댓글을 부모로 가질 수 있는 구조](https://developers.reddit.com/docs/api/redditapi/models/classes/Comment)를
사용합니다. GitHub Discussions는
[댓글과 답글 스레드](https://docs.github.com/en/graphql/guides/using-the-graphql-api-for-discussions)를
구분하고, Discourse는 평면 대화와 함께
[중첩 답글 보기](https://meta.discourse.org/t/introducing-nested-replies/402812)를
제공합니다. 따라서 서비스 규모를 모방하지 않고 현재 대화 목적에 맞춰 1단을 선택했습니다.

## 현재 source가 고정한 제약

- 쓰기 기능은 현재 account 정책상 `ACTIVE` account의 full session이며 필수 비밀번호 변경이
  남아 있지 않은 계정만 사용할 수 있습니다. 일반 회원은 이메일 소유권 확인으로 `ACTIVE`가
  되고, 초대 관리자는 초대 token을 수락해 초대된 이메일의 소유권을 확인한 뒤 `ACTIVE`가
  됩니다. 최초 최고 관리자는 이메일 소유권 확인 없이 운영 명령으로 `ACTIVE` 생성되지만
  최초 비밀번호 변경을 마치기 전에는 일반 쓰기 기능을 사용할 수 없습니다. 정지·탈퇴
  계정이나 제한 session의 접근 정책을 이 작업에서 우회하지 않습니다.
- 작성자에게는 현재 account의 공개 표시 이름을 사용합니다. 새 익명 신원이나 차량 소유자
  배지는 현재 범위에 넣지 않습니다.
- 커뮤니티, moderation, media와 별도 공개 profile은 아직 구현 module이나 확정 domain이
  아닙니다. 아래 제품 선택이 닫히기 전에 이를 미리 만들지 않습니다.

## 수용 기준

- 차량 데이터가 없어도 사용자가 일반 커뮤니티의 게시글 목록과 상세에서 대화를 시작하고,
  게시글 아래에 댓글과 1단 답글을 작성할 수 있습니다.
- 화면에는 게시글·댓글·1단 답글만 나타나고 2단 이상의 답글 들여쓰기는 나타나지 않습니다.
- 현재 기능과 나중에 추가할 차량 관계·부가 기능을 구분할 수 있으며, 후속 확장이 기존
  게시글과 대화 경험을 교체한다는 전제가 없습니다.
- 아래 활성 결정 블록의 모든 항목이 선택된 뒤, 그 exact 값이 범위·요구사항·수용 기준에
  함께 반영돼 구현자가 제품 범위를 다시 선택하지 않아도 됩니다.
- 활성 결정이 남아 있는 동안에는 추천안을 확정값으로 간주하지 않고 해결 설계나 실행 계획을
  만들지 않습니다.

## 활성 결정 블록

아래 12개는 **현재 결과 정의 단계에서 지금 선택지와 결과 차이를 모두 설명할 수 있는 사용자
소유 결정 전체**입니다. 어느 질문도 다른 질문의 선행 답이 있어야만 선택지를 이해할 수 있는
상태가 아니므로 한 블록에 함께 제시합니다. 이 블록의 답을 한 번에 반영한 뒤에만, 선택
조합에 의존해 새 제품 질문이 생기는지 대조하고 결과 정의 단계의 종료 여부를 판단합니다.

### 1. 로그인하지 않은 방문자의 읽기 범위

- **결정 이유**: 가입 전 탐색과 공유를 우선할지, 콘텐츠 접근을 회원에게 한정할지에 따라
  사용자가 보는 결과가 달라집니다.
- **A. 대화 전체 공개 — 추천**: 게시글 목록·상세와 댓글·답글을 모두 읽을 수 있습니다.
  공유와 신규 유입에 유리하며, 쓰기는 계속 정상 로그인 계정에만 허용합니다.
- **B. 게시글만 공개**: 게시글 목록·상세만 공개하고 댓글·답글은 로그인 뒤 보여 줍니다.
- **C. 회원만 열람**: 목록부터 댓글·답글까지 모두 로그인 뒤 보여 줍니다.
- **영향과 재검토**: 이후 회원 전용 공간을 추가할 수 있지만 첫 일반 공간의 공개 약속은
  별도 변경 결정 없이 축소하지 않습니다. 이 선택은 결정 12의 출시 게이트가 열렸을 때
  실제 사용자에게 적용할 열람 범위이며, `운영=C`이면 그 전까지 외부 공개를 보류합니다.
- **응답**: `공개=A`, `공개=B` 또는 `공개=C`

### 2. 첫 게시 공간의 구성

- **결정 이유**: 사용자가 글을 어디에 쓰고 찾는지는 첫 화면의 정보 구조입니다.
- **A. 일반 게시판 하나 — 추천**: 하나의 일반 공간에서 시작합니다. 이후 게시판이나
  카테고리를 추가해도 기존 글은 그대로 유지합니다.
- **B. 고정된 자유·질문·정보 게시판**: 처음부터 세 공간을 보여 줍니다. 글을 쓸 때 공간을
  선택하며, 작성자는 자신의 글을 세 공간 사이에서 옮길 수 있습니다.
- **C. 관리자가 게시판을 만들고 운영**: 첫 버전에 게시판 생성·정렬·비활성화까지 포함합니다.
  일반 사용자의 대화 기능과 함께 관리자용 게시 공간 운영 화면도 현재 제품 범위가 됩니다.
- **영향과 재검토**: 차량별 공간은 어느 선택에도 포함하지 않으며 차량 연결 단계에서
  기존 일반 공간 옆에 추가합니다.
- **응답**: `게시공간=A`, `게시공간=B` 또는 `게시공간=C`

### 3. 작성자가 자신의 콘텐츠에 할 수 있는 일

- **결정 이유**: 작성 뒤 오탈자를 고치거나 의사를 철회할 수 있는지는 직접 보이는 제품
  동작입니다.
- **A. 작성·수정·삭제 — 추천**: 게시글·댓글·답글을 만들고 자신의 것만 수정·삭제합니다.
- **B. 작성·삭제**: 자신의 콘텐츠를 만들고 삭제할 수 있지만 게시 뒤 수정할 수 없습니다.
- **영향과 재검토**: 관리자의 숨김은 작성자 권한과 섞지 않고 결정 12의 운영 동작으로
  구분합니다.
- **응답**: `작성=A` 또는 `작성=B`

### 4. 답글에 다시 답할 때의 동작

- **결정 이유**: 화면은 1단까지만 보여 주므로, 답글 작성자에게 다시 응답하려는 행동을
  어떻게 처리할지 정해야 합니다.
- **A. 같은 1단 묶음에 추가하고 대상을 표시 — 추천**: 새 답글을 더 깊게 들여쓰지 않고
  같은 댓글 아래에 추가하며, 누구에게 한 답인지 표시합니다.
- **B. 답글에는 다시 답할 수 없음**: 최상위 댓글에만 답글을 달 수 있습니다.
- **영향과 재검토**: A를 선택해도 화면 깊이는 1단입니다. 향후 다단계 표시가 필요해질 때
  현재 대화 대상을 잃지 않는 방향으로 확장합니다.
- **응답**: `재응답=A` 또는 `재응답=B`

### 5. 작성자 삭제 뒤 대화를 보여 주는 방식

- **결정 이유**: 작성자의 삭제 의사와 다른 사람이 남긴 대화의 보존 중 무엇을 우선할지
  제품 판단이 필요합니다.
- **A. 원문을 지우고 대화 자리는 유지 — 추천**: 삭제한 원문과 작성자 표시는 보여 주지
  않습니다. 하위 대화가 있으면 `삭제된 글/댓글` 자리와 남은 대화를 유지하고, 하위 대화가
  없는 항목은 화면에서 제거합니다.
- **B. 해당 항목과 하위 대화를 모두 숨김**: 다른 사용자의 댓글·답글도 함께 보이지 않게
  합니다.
- **C. 하위 대화가 있으면 삭제 불가**: 먼저 하위 대화가 없어져야 작성자가 삭제할 수
  있습니다.
- **영향과 재검토**: 개인정보 보존 기간과 계정 탈퇴 때의 익명화는 별도 privacy 결정이며,
  현재에는 사용자에게 보이는 삭제 결과만 정합니다.
- **응답**: `삭제=A`, `삭제=B` 또는 `삭제=C`

### 6. 첫 참여 기능

- **결정 이유**: 대화 외의 가벼운 참여를 어디까지 핵심으로 볼지에 따라 첫 범위가 달라집니다.
- **A. 댓글·답글만 제공**: 좋아요와 북마크는 후속 기능으로 둡니다.
- **B. 좋아요까지 제공 — 추천**: 게시글·댓글·답글에 좋아요를 누르고 취소할 수 있습니다.
  여러 감정 표현과 비추천은 포함하지 않습니다.
- **C. 좋아요와 게시글 북마크 제공**: B에 더해 사용자가 게시글을 나중에 볼 목록에
  저장합니다.
- **영향과 재검토**: 어떤 선택도 반응 종류 확장, 개인 보관함 고도화나 추천 점수를 영구
  금지하지 않습니다.
- **응답**: `참여=A`, `참여=B` 또는 `참여=C`

### 7. 첫 글 작성 형식과 이미지

- **결정 이유**: 이미지 첨부는 보관·삭제·검사와 운영 범위를 함께 늘리므로 첫 글쓰기 결과로
  명시해야 합니다.
- **A. 제목과 일반 텍스트만 — 추천**: 게시글은 제목과 텍스트 본문, 댓글·답글은 텍스트로
  작성합니다. 이미지 업로드와 꾸밈 편집기는 후속 기능입니다.
- **B. 게시글에만 이미지 첨부**: 게시글은 텍스트와 이미지를 함께 올리고 댓글·답글은
  텍스트로 제한합니다.
- **C. 게시글·댓글·답글에 이미지 첨부**: 모든 대화 단계에 이미지를 올립니다.
- **영향과 재검토**: B나 C를 선택하면 media 보관·삭제·노출 책임도 작업 범위에 포함됩니다.
  A는 후속 이미지 관계 추가를 막지 않습니다.
- **응답**: `글형식=A`, `글형식=B` 또는 `글형식=C`

### 8. 첫 탐색 기능

- **결정 이유**: 사용자가 글을 찾는 기본 경로를 최신 목록만으로 시작할지 검색·인기까지
  포함할지 정해야 합니다.
- **A. 최신 글 목록만 — 추천**: 게시 공간에서 최신 글부터 보고 상세로 들어갑니다.
- **B. 최신 목록과 제목·본문 검색**: A에 키워드 검색을 추가합니다.
- **C. 최신·인기 정렬과 검색**: B에 좋아요·대화 활동을 이용한 인기 보기까지 추가합니다.
- **영향과 재검토**: A를 선택해도 이후 검색·인기·추천 화면은 기존 글을 소비하는 별도 탐색
  기능으로 추가할 수 있습니다. C에서 결정 6이 A이면 대화 활동만, B나 C이면 좋아요와 대화
  활동을 사용하며 정확한 산정 방식은 해결 설계에서 검증합니다.
- **응답**: `탐색=A`, `탐색=B` 또는 `탐색=C`

### 9. 댓글과 답글의 기본 표시 순서

- **결정 이유**: 댓글과 답글이 많아질 때 먼저 보이는 대화가 달라지므로 기본 표시 순서를
  제품 결과로 정해야 합니다.
- **A. 오래된 대화부터 — 추천**: 댓글은 먼저 작성된 것부터, 각 댓글의 답글도 먼저 작성된
  것부터 보여 줍니다. 대화 흐름을 시간 순서대로 읽기 쉽습니다.
- **B. 최신 댓글부터**: 댓글은 최근 작성된 것부터 보여 주되, 각 댓글의 답글은 오래된
  것부터 보여 줍니다. 새 댓글은 빨리 찾지만 전체 맥락은 뒤에서 앞으로 이동합니다.
- **C. 활발한 댓글부터**: 답글 수를 기본으로 하고 결정 6에서 좋아요를 제공하면 좋아요도
  함께 반영해 활발한 댓글을 먼저 보여 줍니다. 각 댓글의 답글은 오래된 것부터 보여 줍니다.
- **영향과 재검토**: 기본 순서 외의 정렬 선택 화면은 현재 범위에 넣지 않습니다. 사용량이
  늘어 다른 정렬 요구가 확인되면 기존 기본값을 유지한 채 선택 정렬을 추가할 수 있습니다.
- **응답**: `대화순서=A`, `대화순서=B` 또는 `대화순서=C`

### 10. 새 대화를 알려 주는 범위

- **결정 이유**: 답변을 다시 확인하게 하는 핵심 경험과 알림 기능의 구현·운영 범위를 함께
  선택해야 합니다.
- **A. 첫 버전에는 알림 없음**: 사용자가 직접 글을 다시 방문해 새 대화를 확인합니다.
- **B. 서비스 안 알림 — 추천**: 내 게시글의 새 댓글과 나를 대상으로 한 답글을 서비스 안에서
  확인합니다. 자신이 만든 대화에는 알리지 않고, 같은 동작으로 내가 여러 조건에 해당해도
  알림은 하나만 만듭니다. 이메일·문자·푸시는 포함하지 않습니다.
- **C. 서비스 안 알림과 이메일**: B에 이메일 전달과 수신 설정을 포함합니다.
- **영향과 재검토**: 전달 방식 확장은 기존 대화와 별도 기능으로 추가합니다.
- **응답**: `알림=A`, `알림=B` 또는 `알림=C`

### 11. 작성자 정보를 눌렀을 때의 범위

- **결정 이유**: 표시 이름만 보여 줄지, 다른 사용자의 활동을 탐색하는 공개 profile까지
  제공할지는 개인정보 노출과 기능 범위를 바꿉니다.
- **A. 표시 이름만 — 추천**: 게시글·댓글·답글에 작성자 표시 이름만 보여 주며 별도 공개
  profile 화면은 만들지 않습니다.
- **B. 작성 글·댓글·답글을 모아 보는 공개 profile**: 표시 이름을 누르면 해당 사용자의 공개
  활동 목록을 봅니다.
- **C. 소개를 포함한 공개 profile**: B에 사용자가 작성한 공개 소개를 포함합니다. profile
  사진, 팔로우와 개인 메시지는 포함하지 않습니다.
- **영향과 재검토**: A에서도 안정된 작성자 관계는 유지해 나중에 공개 profile을 추가할 수
  있어야 합니다. B나 C에서 profile 화면과 소개·활동 각각의 노출은 결정 1을 그대로 따릅니다.
  `공개=A`이면 profile과 공개 활동 모두 비로그인에게 보입니다. `공개=B`나 `공개=C`이면
  profile 화면은 로그인 뒤에만 보이며, 비로그인에게는 게시글 안의 표시 이름 외에 별도
  profile·소개·활동 목록을 공개하지 않습니다. 결정 5·12로 삭제·숨김된 콘텐츠는 활동
  목록에서 다시 노출하지 않습니다.
- **응답**: `프로필=A`, `프로필=B` 또는 `프로필=C`

### 12. 첫 출시에 포함할 최소 운영 기능

- **결정 이유**: 사용자 생성 콘텐츠를 공개하면서 부적절한 콘텐츠를 처리할 책임을 현재
  범위에 얼마나 포함할지 정해야 합니다.
- **A. 사용자 신고와 관리자 숨김 — 추천**: 로그인 사용자는 게시글·댓글·답글을 신고하고,
  관리자는 신고를 확인해 콘텐츠를 숨길 수 있습니다. 제재·복구·이의제기의 상세 정책은
  별도 작업으로 둡니다.
- **B. 관리자 숨김만**: 사용자의 신고 접수 화면 없이 관리자가 직접 확인한 콘텐츠만
  숨깁니다.
- **C. 이번 작업에서는 제외하고 외부 공개를 보류**: 대화 기능은 만들되 별도 moderation
  작업이 완료되기 전에는 실제 사용자에게 공개하지 않습니다. 결정 1의 공개 범위는 이
  출시 게이트가 열린 뒤 적용하며, 그 전에는 내부 개발·검증에서만 사용합니다.
- **영향과 재검토**: 어떤 선택에서도 작성자 삭제와 관리자 숨김을 같은 동작으로 취급하지
  않습니다. 계정 제재와 신고 이력 보존은 별도 제품·운영 결정입니다.
- **응답**: `운영=A`, `운영=B` 또는 `운영=C`

### 한 번에 답하는 형식

추천 묶음은 다음 exact 값을 뜻합니다.

`공개=A, 게시공간=A, 작성=A, 재응답=A, 삭제=A, 참여=B, 글형식=A, 탐색=A, 대화순서=A, 알림=B, 프로필=A, 운영=A`

그대로 선택하면 `추천안 전체`라고 답할 수 있습니다. 일부만 바꾸려면 위 한 줄에서 해당
값만 바꿔 한 번에 답하면 됩니다. 이 블록에 답하기 전에는 어느 추천도 확정된 제품 결과가
아닙니다.

위 선택지에 이름이 없는 태그, 투표, 팔로우, 개인 메시지, 임시 저장, 구독, 실시간 채팅과
게시물 고정은 현재의 `핵심 기능만`이라는 확정 범위에 포함하지 않습니다. 영구 폐기하는 것은
아니며 실제 제품 필요가 생기면 기존 게시글·대화와 함께 존재하는 후속 기능으로 추가합니다.

## 결정 블록 뒤의 단계 전환 조건

1. 12개 답을 한 번에 이 문서의 확정 결과·범위·요구사항·수용 기준에 반영합니다.
2. 선택 조합 때문에만 생기는 새 제품 질문이 있는지 대조합니다. 지금은 질문·대안·영향을
   만들 수 없고 선택 뒤에만 구체화되는 질문이 있을 때만 같은 결과 정의 단계의 다음 의존
   블록으로 제시합니다.
3. 활성 사용자 결정이 0개이고 제품 결과가 정렬됐을 때만 결과 정의를 닫습니다.
4. 그 뒤에만 `해결 설계`로 전환해 API, schema, module, 권한·저장·조회 방식과 확장 경계를
   Agent 기술 결정으로 설계합니다.
