# 코드와 설정 주석 작성 가이드

주석은 코드를 번역하지 않고 코드만으로 복원하기 어려운 정책, 경계, 위험과 변경 조건을 설명합니다.

## 원칙

- 실제 code, 설정과 test가 보장하는 범위만 말합니다.
- 이름과 타입으로 충분한 단순 동작은 반복하지 않습니다.
- 호출자가 알아야 하는 계약과 위험한 순서 가까이에 둡니다.
- 긴 대안과 선택 근거는 design 문서가 소유합니다.
- 파일명, 디렉터리명과 `.example` 같은 suffix를 파일 역할의 근거로 사용하지 않습니다.
- 변경한 파일 전체를 완료 전에 다시 읽고 필요한 주석, 오래된 주석과 과장을 직접 검토합니다.
- 주석의 기술적 정확성과 충분성을 regex verifier로 판정하지 않습니다.

## 위치: 재귀적인 의미 범위

주석을 둘 위치와 주석을 쓰는 방법을 분리해 판정합니다. 먼저 파일 형식의 고정된 깊이가
아니라 독자가 개념·책임·범위·실행 주체나 lifecycle을 전환해 읽는 의미 범위를 찾습니다.
의미 범위는 다음처럼 재귀적으로 중첩될 수 있으며 이 목록은 고정 계층이 아닙니다.

```text
파일
└─ 문서·job·구성요소
   └─ 하위 block·단계
      └─ option 묶음·분기·호출
         └─ 더 작은 의미 범위
```

각 범위에서 다음 판정을 하위 범위에 재귀적으로 반복합니다.

1. 현재 경계에서 독자가 별개의 역할·적용 범위·actor·입력·결과나 인접 단위와의 관계로
   전환해야 하는지 확인합니다.
2. 의미 전환이 있다면 이름과 구조만으로 그 역할·범위·관계가 충분히 드러나는지
   확인합니다.
3. 드러나지 않으면 해당 범위가 시작되는 위치에 역할·범위·관계를 설명하는 주석을
   둡니다. 명확한 의미 block의 설명 책임을 하위 option 주석에 넘기지 않습니다.
4. 하위 범위에도 상위 설명과 다른 비자명한 의미가 있으면 별도 주석을 둡니다. 상위
   주석이 하위의 선택 이유·위험을 대신하거나 하위 주석이 상위 block의 역할을 대신하지
   않습니다.
5. 문법적인 mapping·key·method라는 이유만으로 주석을 강제하지 않습니다. 상위 설명과
   다른 의미가 없고 이름·구조로 충분하면 생략합니다.

제목처럼 읽히는 주요 의미 경계의 주석은 최소 하한입니다. 주석을 삭제하려면 같은 의미
범위에 동일한 역할·범위·관계가 다른 주석이나 구조로 남는지 확인합니다. 상위나 하위
범위의 설명은 삭제 근거가 아닙니다.

## 작성: 구체적이고 완전한 설명

주석이 필요한 위치를 확정한 뒤 내용을 작성합니다. 문장은 실제 source에서 확인한
다음 요소 중 독자가 의미를 복원하는 데 필요한 요소를 명시합니다.

- 누가 실행·생성·변환·전달·소비하는지
- 어떤 값·artifact·권한·상태를 대상으로 하는지
- 무엇을 수행·보장·차단하며 결과가 어디로 전달되는지
- 어떤 조건과 이유로 선택됐고 실패하거나 바꿀 때 무엇이 달라지는지
- 인접 block·단계와 적용 범위가 어떻게 다른지

주어·대상·행위나 결과가 빠진 `검증합니다`, `관리합니다`, `연결합니다` 같은 표현,
지시 대상이 불명확한 대명사와 정의되지 않은 추상어를 사용하지 않습니다. 의도와 실제
강제를 구분하고 `보장`, `전용`, `오직`, `재현 가능`처럼 source가 강제하지 않는 범위로
확대하지 않습니다. 한 문장에 모든 배경을 넣는 대신 범위 시작 주석은 역할과 관계를,
하위 주석은 그 범위에서만 필요한 이유·위험·변경 조건을 설명합니다.

둘 이상의 구성요소가 하나의 결과에 관여하면 각 절을 `문법상 주어 → 그 주어가 직접
수행하는 행위 → 직접 결과`로 분해해 source와 대조합니다. 앞 구성요소가 뒷 구성요소의
실행 조건을 마련한다는 이유로 뒷 구성요소의 판정·차단 효과를 앞 구성요소의 술어로 쓰지
않습니다. 실행 조건을 제공하는 주체와 실제 판정하는 주체가 다르면 문장을 분리합니다.

외부 플랫폼·도구의 기본 계약을 설명하는 주석은 사용 version의 공식 source에서 적용
범위를 확인합니다. local 변수명이나 호출 구조가 값의 사용을 보여준다는 이유만으로
플랫폼이 정하는 생성 주체·적용 범위·lifecycle까지 구조에서 복원된다고 판정하지 않습니다.

## Java

다음 비자명한 계약에는 주석이나 Javadoc을 검토합니다.

- public API와 application port의 입력·결과·예외·side effect
- 인증·인가 예외와 Security matcher
- transaction, rollback과 외부 호출 순서
- password, token, 개인정보와 redaction
- DB constraint·lock, 동시성, retry·timeout·fallback
- 예외와 HTTP status·error code mapping
- 복잡한 fixture와 보안·아키텍처 assertion

단순 getter, 코드 한 줄의 번역과 형식만 채운 Javadoc은 작성하지 않습니다.

## 설정과 workflow

YAML, properties, Gradle, Docker, Kubernetes, workflow와 env 계약에는 필요한 경우 다음을 가까이 설명합니다.

- 파일이나 block의 목적과 비목표
- 입력, 결과와 side effect
- trigger, 권한과 secret 경계
- 실패 시 동작
- timeout, resource, probe, version·checksum의 이유
- 운영자가 바꿀 수 있는 조건

모든 step과 환경변수에 설명을 기계적으로 강제하지 않습니다. 이름만으로 자명하지 않거나 보안·운영 판단을 바꾸는 내용만 남깁니다.

## SQL

새 table·constraint·index, destructive `ALTER`·`DROP`과 data update block에는 필요한 경우 다음을 설명합니다.

- 보장하는 도메인 불변식
- application과 DB의 책임 분리
- lock, backfill과 rollback 위험
- 민감정보와 보존 조건

## TODO와 suppression

TODO는 발동 조건, 현재 보류 이유와 제거 조건을 포함합니다. `@SuppressWarnings`와 `NOSONAR`는 rule, 적용하지 못하는 근거와 제거 조건을 가까이에 둡니다.

## 주석 의미 검토

주석 적용 결과는 `현재 source → 후보의 설명 충분성`과 `작업 시작 baseline의 주석 →
후보의 정보 보존`을 서로 대체할 수 없는 두 방향으로 검토합니다. 현재 후보만 읽으면
삭제된 주석이 유일하게 담던 정보가 사라질 수 있으므로 baseline을 함께 사용합니다. 새
파일처럼 변경 전 주석이 없으면 정보 보존 방향만 해당 없음입니다.

1. 대상 source·test·설정·workflow·SQL 전체와 의미를 결정하는 caller·helper·runbook을
   읽습니다.
2. 대상 파일마다 의미 범위를 재귀적으로 찾고 각 범위를 `주석 필요`, `기존 주석 정확`,
   `이름·구조로 충분` 중 하나로 판정합니다.
3. 필요한 주석마다 artifact, actor, 입력·결과, 변환·전달 경로, 최종 소비자와 소비 시점을
   실제 source에 연결합니다. 확인하지 못한 역할은 추측해 쓰지 않습니다.
4. 위치 판정과 별도로 각 절의 문법상 주어·대상·직접 행위·직접 결과를 source에 대조합니다.
   인접 구성요소의 선행조건과 판정 효과를 한 주어에 합치지 않았는지, 조건·이유·관계에
   모호한 표현이나 과장이 없는지도 확인합니다.
5. baseline에서 수정·삭제·병합된 각 주석을 actor, 대상 artifact, 적용 범위와 lifecycle,
   행위·결과, 인접 범위와의 관계·조건으로 분해합니다. 각 정보를 최종 구조, 같은 의미
   범위의 주석 또는 authoritative source에 근거한 교정에 독립적으로 대응시킵니다.
   잘못되거나 실제로 중복된 정보는 그 근거를 확인하며, 대응되지 않은 정보가 남으면
   주석 기준을 충족하지 못합니다.
6. diff가 아니라 대상 파일 전체를 읽어 현재 source의 설명 충분성과 변경 전 정보의
   보존·교정을 별도로 대조합니다. 어느 방향이든 누락·오배치·부정확·과장·불필요가
   남으면 주석 기준을 충족하지 못합니다.
7. 주석 전용 작업은 비주석 동작·설정·권한 변경이 없는지 별도로 확인합니다. syntax와
   동작 불변 검증은 주석의 정보 보존·충분성 검증을 대신하지 않습니다.

후보 동결, 독립 감사의 순서·횟수, 실패 뒤 상태 전이와 전체 완료 판정은
[작업 실행 워크플로우](100-work-execution-workflow.md)가 소유하며, 개발 결과의 독립
주석 감사 축은 `$verify-dev`가 이 두 방향을 사용합니다.
