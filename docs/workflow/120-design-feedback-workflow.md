# 설계 피드백 반영 워크플로우

이 문서는 질문, 반론, 비교 제안과 댓글을 현재 설계의 요구, 제약, 평가 기준과 추천
결론에 정확한 의미 역할로 반영하는 절차를 소유합니다.
피드백 원문 전체와 시간순 처리 기록은 최종 문서에 복사하지 않습니다. 대신 실질적인 설계
피드백이 드러낸 고민, Agent의 답변·반영 판단과 최종 설계를 역할별로 구분해 현재 계획
단계와 의미 유형에 맞는 canonical owner에 압축 보존합니다. 독자는 원 대화를 기억하지
않아도 무엇이 사용자 의견이었고, Agent가 어떻게 답했으며, 무엇으로 반영됐는지 복원할 수
있어야 합니다.
요청·변경 권한, 공통 상태·차단과 후속 실행 lifecycle은
[작업 실행 워크플로우](100-work-execution-workflow.md)가 소유합니다.

## 적용 시점

- 작업 문서나 설계 문서의 댓글 반영
- 기존 추천에 대한 질문·우려·반론
- 대안 비교와 Best Practice 재검토
- 일부 승인과 미답 질문이 섞인 피드백

## 핵심 원칙

- 문장 형태보다 실제로 요구하는 판단을 파악합니다.
- 물음표가 있는 비교 제안을 단순 질문으로 축약하지 않습니다.
- [작업 실행 워크플로우](100-work-execution-workflow.md)의 의미 역할·source 권위를
  적용해 원래 요구, 명시 제약, 우려와 Agent 추천을 분리합니다.
- 추천에 대한 우려는 명시적인 요구 변경이 없는 한 해당 추천의 전제·결론만
  재평가하고 원래 요구를 교체하지 않습니다.
- 기존 추천을 유지, 변경 또는 폐기했는지 직접 답합니다.
- 기술적으로 닫을 수 있는 선택을 다시 결정 사항으로 떠넘기지 않습니다.
- 피드백을 대화 순서가 아니라 설계 주제 순서로 반영합니다.
- 최종 문서에는 댓글 원문·작성 시각·외부 comment ID 같은 대화 이력이 아니라, `사용자
  의견 요약`, `Agent 답변·판단 요약`, `최종 반영`의 의미 역할과 완결된 결정·근거를
  남깁니다.
- 질문형 피드백을 해결했다는 이유로 그 질문이 드러낸 장기 고민이나 결론·근거를 바꾼 고유
  논점을 삭제하지 않습니다.
- 단순 승인, 오탈자 정정과 문서 변경을 명시적으로 제외한 읽기 전용 질문은 존재하지 않은
  설계 논의를 만들거나 영구 기록을 추가하는 근거가 아닙니다.

## 피드백 확보

반영 대상은 다음 순서로 확인합니다.

1. 현재 메시지에 포함된 선택 텍스트와 댓글
2. 지정된 작업 문서의 인용문과 검토 메모
3. 명시된 GitHub, Google Docs 또는 다른 외부 댓글 시스템

대상을 확인하지 못하면 추정으로 설계를 바꾸지 않습니다.
확인 과정과 원문 목록은 현재 세션에서만 관리하고 repository에 댓글 원문 전문이나 처리
매트릭스를 만들지 않습니다. 다만 현재 논의가 아직 닫히지 않았다면 현재 단계 artifact의
결정 블록에 사용자 질문·우려 요약, Agent의 현재 답변·추천과 남은 결정을 보존합니다.

## 의미 복원

각 피드백에 대해 내부적으로 다음 질문에 답합니다.

1. 현재 활성 사용자 요구와 명시 제약은 무엇인가
2. 어떤 사실·우려·평가 기준을 제시했는가
3. 기존 추천의 어느 전제나 결론을 직접 문제 삼는가
4. 사용자가 요구·제약·우선순위를 실제로 변경했는가
5. 명시하거나 강하게 시사한 대안은 무엇인가
6. 원래 요구에 대해 실제로 필요한 답변은 무엇인가
7. 이 답변이 기존 추천, 결정, 계획과 검증을 어떻게 바꾸는가

이 질문에 답한 뒤 실질적인 설계 피드백이면 아래 `논의 요약` 계약과 최종 결과를 문서에
반영합니다.
Why chain, 해석 매트릭스와 내부 사고 과정은 저장하지 않습니다.

### 기존 산출물을 보완하는 피드백

사용자가 기존 초안·설계·계획을 두고 `보완`, `부족한 점 확인`, `댓글 반영`, `더 깊게
검토`와 동등한 표현을 사용하면, 그 표현은 기존 결과를 폐기하거나 전면 재설계하라는
권한이 아닙니다. Writer나 reviewer를 호출하기 전에 다음 입력을 같은 candidate identity에
결속합니다.

```text
기준선 B = 피드백 전 artifact snapshot
          + 이미 제공하던 관찰 가능한 결과
          + 구체적으로 닫힌 구현 계약
변경분 D = 피드백 원문이 겨냥한 대상
          + 새로 요구한 정보·품질 축
          + 명시적으로 바꾼 요구·제약 또는 없음
논의 요약 R = 사용자 의견·질문의 핵심
             + Agent 답변·반영 판단의 핵심
             + 현재 논의 상태와 최종 반영 또는 남은 결정
```

`종합적`, `총체적`, `최적`, `빠진 것이 없는지` 같은 품질 표현은 `D`의 조사 깊이와
비교 기준을 높입니다. 그 자체로 제품 범위·data lifecycle·감사 수준을 새로 선택하거나,
`B`의 구체적인 계약을 더 추상적인 분류 목록으로 바꾸는 source는 아닙니다.

후보가 바꾸는 각 관찰 효과와 유한한 구현 단위는 다음 네 처분 중 하나여야 합니다.

| 처분 | 필요한 근거 | 후보에서의 행동 |
| --- | --- | --- |
| 보존 | 피드백이 바꾸지 않은 `B`의 결과·계약 | 같은 구체성으로 유지 |
| 수정 | `D`가 겨냥한 결함 또는 authoritative source 충돌 | 영향받는 값만 교체하고 전후 차이를 검증 |
| 추가 | `D`의 누락 보완이나 기존 consumer에 필요한 독립 근거 | 요구·consumer·불변식과 새 단위를 연결 |
| 제거·대체 | 사용자의 명시적 취소·전면 재설계 또는 기존 계약과 양립할 수 없는 authoritative source | 제거되는 결과와 후속 consumer의 대체 경로까지 연결 |

`제거·대체`가 문서 전체 삭제 또는 핵심 독자 질문·canonical owner 계약·상태나 결정 section
묶음을 실질적으로 없애는 대규모 제거이면, 이 표의 근거만으로 실행하지 않습니다. 작업 실행
workflow의 현재-generation 명시 권한과 documentation workflow의 삭제 admission을 먼저
통과합니다. 허락 전에는 기존 내용을 보존하고 영향 범위만 재검토 대기로 표시합니다.

테이블·field·API·module·script처럼 구현자가 유한하게 만들어야 하는 표면은 후보 전체
manifest를 다시 복원합니다. 추가·분리한 각 단위가 서로 다른 요구·consumer·불변식 중
무엇을 소유하는지 설명하지 못하면 별도 단위로 만들지 않습니다. 단위 수를 늘린 결과 기존
계약보다 구체성이 낮아지거나 구현자가 type·필수값·관계·제약·입출력 같은 핵심 값을 다시
결정해야 하면, 그 후보는 보완 결과가 아니라 무효화된 설계 후보입니다. 분류 이름과 공통
pattern만으로 구현 계약을 대신하지 않습니다.

작성자는 실제 대표 입력 하나를 `source 정보 → 후보의 exact 단위와 값 → 관계·제약 → 첫
consumer 결과`까지 통과시킵니다. 이 경로에서 `B`에 있던 결과가 사라지거나 후보에 없는
값·관계·정책을 새로 결정해야 하면 전체 표면으로 확장하지 않고 분해 기준으로 돌아갑니다.

Reviewer에게는 후보만 전달하지 않고 피드백 원문, `B`, `D`, `R`, 네 처분과 대표 경로를
같은 identity로 전달합니다. Reviewer는 상세 완성도보다 먼저 다음을 판정합니다.

1. `B`의 보존 대상이 같은 구체성으로 남아 있는가
2. 수정·추가·제거가 각각 `D`나 독립 source로 역추적되는가
3. 미승인 효과가 있으면 그 내부 결함을 보강 대상으로 열지 않고 효과 전체 제거를
   closure 조건으로 반환했는가
4. 대표 경로와 전체 manifest가 추가 결정을 남기지 않고 구현 가능한가
5. 실질적인 설계 피드백이면 사용자 의견, Agent 답변·판단과 최종 반영을 원 대화 없이
   역할별로 구분할 수 있고, 결론·근거를 바꾼 고유 논점이 빠지지 않았는가

이 입장 판정이 실패하면 누락 field나 새 구조의 내부 결함을 계속 열거해 후보를 키우지
않습니다. `B`로 복귀한 뒤 승인된 `D`만 다시 반영합니다. Reviewer finding은 정확하더라도
원래 피드백에 없던 효과의 구현 권한이 아니며, 현재 Agent는 finding을 위 네 처분으로 다시
대조한 뒤에만 correction writer에 전달합니다.

## 분류와 처리

| 성격 | 처리 |
| --- | --- |
| 명확한 범위 확정 | 범위, 제외 범위와 수용 기준에 반영 |
| 명확한 요구·제약 변경 | 직접 영향받는 요구·제약·우선순위만 갱신 |
| 즉시 반영 가능한 설계 의견 | 별도 선택이 필요 없으면 바로 반영하고 사용자 의견·Agent 반영 판단·최종 설계를 역할별로 요약 |
| 제품·UX 질문 | 활성 요구에 직접 답하고, 새 사용자 결정이 필요하면 해당 결정과 직접 consumer만 다시 엶 |
| 기술·확장성 질문 | 제품 범위를 새로 만들지 않고 해당 설계 결정의 근거·호환성·재검토 조건을 보완 |
| 단순 동의 | 직접 붙은 exact 선택만 사용자 값 확정으로 기록하고 새 판단 맥락을 만들지 않음. 다만 마지막 열린 값에 대한 채택·반영이고 현재 단계 후보가 하나이며 새 사용자 판단이 생기지 않으면 작업 실행 workflow의 무모호 closure 조건으로 같은 원문을 단계 확정에도 소비함 |
| 오탈자·표현 정정 | 지정한 문구만 고치고 설계 결정이나 논의 요약을 새로 만들지 않음 |
| 변경 제외 읽기 전용 질문 | 직접 답하되 설계 반영·영구 논의 기록·재승인을 시작하지 않음 |
| 반론·우려 | 활성 요구를 유지한 채 기존 추천의 전제를 재검토하고 유지·변경·폐기를 명시 |
| 비교 제안 | 기존안과 대안을 같은 기준으로 다시 비교 |
| 추가 분석 | 공식 근거, 대안과 추천 결론을 보강 |
| 후속 후보 | 현재 설계와 독립된 발견으로 정규화하고 영향·owner를 작업 실행 workflow에 인계 |
| 혼합 | 확정 가능한 부분과 미답 판단을 분리 |

`A가 표준에 가까운데 처음부터 A를 쓰는 편이 낫지 않은가`는 A와 기존 추천을 다시 비교하라는 반론입니다.
`표준 방식으로 진행하면 되지 않는가`는 불필요한 조사나 선택을 열어두지 말고 표준 경로를 기본안으로 닫으라는 요구일 수 있습니다.

## 직접 답변 기준

- 피드백의 전제와 대안을 제거해도 같은 답변이 나온다면 직접 답변이 아닐 가능성이 큽니다.
- 활성 요구의 해법·결론을 먼저 답하고, 피드백이 그 해법에 미치는 영향과
  trade-off, 갱신된 추천을 뒤에 연결합니다.
- 우려로 기존 추천이 폐기되면 원래 요구를 함께 폐기하지 않고 이를 만족하는 다음
  대안을 제시합니다. 안전한 대안이 모두 충돌할 때만 충돌과 필요한 결정을 밝힙니다.
- 기존 추천을 유지하면 제시된 전제가 왜 결론을 바꾸지 않는지 설명합니다.
- 기존 추천을 바꾸면 이전 추천, 후속 전환, 남은 결정과 검증 순서를 함께 갱신합니다.
- 설계 결정과 실제 환경에서의 동작 검증을 분리합니다.
- 공식 지원 경로와 프로젝트 제약으로 기술값이 하나로 닫히면 선택 질문 없이 Agent 기술
  선택으로 기록하고 구현 검증만 남깁니다. 이 기술 선택만으로 설계 단계가 확정되지는
  않습니다.

## 문서 반영

피드백은 다음 최종 형태 중 하나로 변환합니다.

- 권위와 상태가 구분된 결정
- 요구사항 또는 수용 기준
- 범위 또는 제외 범위
- 남은 결정
- 재검토 조건
- 현재 설계와 독립된 후속 후보

해결된 질문과 댓글 원문 인용은 제거하되, 실질적인 설계 피드백의 의미 역할은 제거하지
않습니다.
결정에는 다음 일곱 항목을 보존합니다.

1. 배경
2. 검토한 선택지
3. 선택
4. 선택 근거
5. 영향
6. 배제한 대안
7. 재검토 조건

이 일곱 항목은 기술 결정의 완결성을 소유하며 아래 논의 요약을 대신하지 않습니다. `배경`,
`검토한 선택지`, `선택`, `선택 근거`만 나열해 사용자 의견과 Agent 답변의 역할을 독자가
추론하게 두면 반영 완료가 아닙니다.

댓글 작성 시각, 외부 comment ID, 승인 문구 전문과 사람 식별 정보는 남기지 않습니다.
그러나 `사용자 의견`과 `Agent 답변·판단`이라는 의미 역할, 사용자 소유 결정과 Agent 기술
선택의 권위 구분은 출처 잡음이 아니므로 반드시 보존합니다.

### 설계 논의의 역할별 보존

즉시 반영 가능한 설계 의견, 질문, 반론과 비교 제안은 원문 인용을 제거하기 전에 같은 설계
주제의 논의 단위로 모읍니다. 영구문서의 해당 결정 가까이에 다음 세 역할을 간략히
보존합니다.

- **사용자 의견 요약**: 무엇을 반영하라고 했거나, 무엇이 불분명·위험하다고 보아 질문했고,
  어떤 제약·대안·평가 기준을 제시했는지
- **Agent 답변·판단 요약**: 질문에 대한 직접 답, 실제로 비교한 대안, 추천의 유지·변경·폐기와
  결론을 바꾼 차이
- **최종 반영**: 확정된 요구·설계, 직접 영향받은 계약, 선택 근거·감수한 trade-off와
  재검토 조건

별도 논의가 필요 없는 설계 의견은 내용을 반영하는 같은 변경에서 세 역할을 닫습니다.
Agent 답변·판단 요약에는 왜 추가 결정 없이 바로 반영할 수 있었는지를 포함하되, 존재하지
않은 왕복 대화를 만들지 않습니다.

논의가 필요한 피드백은 먼저 직접 답하고, 결론이 확정되기 전에는 `최종 반영`을 확정값으로
쓰지 않습니다. 현재 단계 결정 블록에는 `사용자 질문·우려 요약`, `Agent의 현재 답변·추천`,
`남은 결정`을 구분합니다. 사용자가 결론을 확정하고 반영을 요청하면 같은 주제의 모든
왕복에서 결론·근거에 영향을 준 고유 논점을 모아 위 세 역할로 정규화하고, 임시 질문·추천·
미결정 표현은 최종 상태로 교체합니다. 시간순 회의록은 만들지 않고 반복된 논점은 합치되,
결론이나 근거를 바꾼 논점을 생략하지 않습니다.

이 논의 요약은 한 문서 유형에 일률적으로 넣지 않습니다. 결과 정의 단계의 제품·UX 논의는
work item 본문, 생성 조건을 통과한 장기 기술 결정은 `-design`, 구현된 현재 불변식은 책임
SOT가 소유합니다. 계획 단계와 artifact 허용 범위는 작업 문서 생명주기를 따릅니다. 같은
논의 요약과 최종 계약을 기존 canonical owner에서 이미 역할별로 복원할 수 있으면 문장을
중복하지 않고 해당 결정 가까이에서 그 owner로 향하는 관계를 표시합니다.

사용자 소유 결정이 남은 질문은 추천을 확정값으로 쓰지 않고 현재 단계의 단일 결정 블록에
질문, 대안별 결과 차이, 추천과 선택 뒤 달라지는 범위를 함께 남깁니다. 기존 결정을 단순
동의한 댓글은 새 판단 맥락을 만들지 않으므로 원문만 제거하고 exact 선택의 사용자 값 확정
상태만 유지합니다. `ㅇㅋ`처럼 특정 결정에 직접 붙은 동의는 인접 결정·문서 전체·다음 계획
단계의 확정으로 확대하지 않습니다.

Work item에 반영하기 전에는 [작업 문서 생명주기](../work-items/100-work-item-lifecycle.md#계획-단계와-최소-artifact)의
현재 계획 단계, closure와 재검토 상태를 먼저 소비합니다. 질문이나 추가 발견 자체를
rollback trigger로 사용하지 않습니다. 실제로 상위 결과가 바뀌거나 다시 열리면 변경한
결정과 exact downstream consumer만 `재검토 대기`로 표시하고 영향받지 않은 기준선은
유지합니다. 현재 단계가 닫히기 전에는 미확정 상위 값에 따라 달라지는 새 downstream
artifact·section·후보 상세를 만들지 않습니다. 전체 문서 삭제나 이에 준하는 대규모 제거는
별도 삭제 권한과 documentation admission으로만 인계합니다.

## 남은 결정

다음처럼 프로젝트 외부 판단이 필요한 항목만 남깁니다.

- 제품 정책과 UX 우선순위
- 운영 비용과 보안 강도 사이의 감수 수준
- 법적 보존과 개인정보 처리
- 출시 범위와 일정

모듈 경계, 보편적 보안 기본값, 기술 표준형 선택, 테스트 전략과 API 의미는 먼저 기술 추천을 제시합니다.
구체적인 가설과 성공·실패 기준이 없는 spike를 만들지 않습니다.

## 실행 표면

이 workflow는 피드백의 의미 변화·권위·영향 범위를 정규화하고 갱신 후보 artifact를
식별합니다. 계획 단계, artifact 수와 rollback은 작업 문서 생명주기가 소유합니다. 문서, 코드,
테스트, 설정과 migration의 실제 변경 권한과 실행 경로는 작업 실행 workflow가 원래 요청의
원자별 권한으로 판정하고 각 전문 owner에 인계합니다.

## 완료 확인

- 반영 대상 피드백을 모두 확인했습니다.
- 기존 산출물 보완이면 피드백 전 기준선, 변경분과 `보존·수정·추가·제거` 처분을 writer와
  reviewer가 같은 identity로 소비했습니다.
- 유한한 구현 표면은 전체 manifest, 단위별 근거와 대표 입력의 end-to-end 경로를 통해
  기존 구체성과 구현 가능성을 보존했습니다.
- 질문과 반론에 직접 답했습니다.
- 기존 추천의 유지·변경·폐기가 문서 전체에 일관되게 반영됐습니다.
- 해결된 원문 전문과 시간순 처리 과정은 최종 문서에 남지 않았습니다.
- 실질적인 설계 피드백마다 사용자 의견 요약, Agent 답변·판단 요약과 최종 반영이 역할별로
  구분되고, 원 대화 없이 논의의 출발점·답변·결과를 복원할 수 있습니다.
- 여러 번 논의한 주제는 결론·근거를 바꾼 고유 논점이 모두 최종 요약에 포함됐고 반복
  표현만 합쳐졌습니다.
- 기술 결정의 일곱 항목만으로 역할별 논의 요약을 대신하지 않았습니다.
- 단순 승인·오탈자 정정·변경 제외 읽기 전용 질문에는 존재하지 않은 논의 기록이나 추가
  승인 절차를 만들지 않았습니다.
- 진짜 남은 결정과 AI가 작성할 세부사항을 구분했습니다.
- 문서 상태, 계획과 검증 기준이 새 결론과 일치합니다.
- Work item 본문·보존된 design 첫 화면·router가 현재 단계, 유지 계약, 재검토 범위와
  재개 조건을 같은 identity로 표시하며 재검토 대기 계약은 구현 입력으로 소비되지 않습니다.
