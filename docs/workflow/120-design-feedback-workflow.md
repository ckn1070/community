# 설계 피드백 반영 워크플로우

이 문서는 질문, 반론, 비교 제안과 댓글을 현재 설계의 요구, 제약, 평가 기준과 추천
결론에 정확한 의미 역할로 반영하는 절차를 소유합니다.
피드백 원문과 처리 과정은 최종 문서에 보존하지 않습니다.
요청·변경 권한, 공통 상태·차단과 후속 실행 lifecycle은
[작업 실행 워크플로우](100-work-execution-workflow.md)가 소유합니다.

## 적용 시점

- 작업 문서나 설계 문서의 댓글 반영
- 기존 추천에 대한 질문·우려·반론
- 대안 비교와 Best Practice 재검토
- 일부 승인과 미답 질문이 섞인 피드백

## 핵심 원칙

- 문장 형태보다 실제로 요구하는 판단을 파악합니다.
- 물음표가 있는 비교 제안을 단순 질문으로 축약하지 않습니다.
- [작업 실행 워크플로우](100-work-execution-workflow.md)의 의미 역할·source 권위를
  적용해 원래 요구, 명시 제약, 우려와 Agent 추천을 분리합니다.
- 추천에 대한 우려는 명시적인 요구 변경이 없는 한 해당 추천의 전제·결론만
  재평가하고 원래 요구를 교체하지 않습니다.
- 기존 추천을 유지, 변경 또는 폐기했는지 직접 답합니다.
- 기술적으로 닫을 수 있는 선택을 다시 결정 사항으로 떠넘기지 않습니다.
- 피드백을 대화 순서가 아니라 설계 주제 순서로 반영합니다.
- 최종 문서에는 피드백 출처가 아니라 완결된 결정과 근거를 남깁니다.

## 피드백 확보

반영 대상은 다음 순서로 확인합니다.

1. 현재 메시지에 포함된 선택 텍스트와 댓글
2. 지정된 작업 문서의 인용문과 검토 메모
3. 명시된 GitHub, Google Docs 또는 다른 외부 댓글 시스템

대상을 확인하지 못하면 추정으로 설계를 바꾸지 않습니다.
확인 과정은 현재 세션에서만 관리하고 repository에 댓글 원문 목록이나 처리 매트릭스를 만들지 않습니다.

## 의미 복원

각 피드백에 대해 내부적으로 다음 질문에 답합니다.

1. 현재 활성 사용자 요구와 명시 제약은 무엇인가
2. 어떤 사실·우려·평가 기준을 제시했는가
3. 기존 추천의 어느 전제나 결론을 직접 문제 삼는가
4. 사용자가 요구·제약·우선순위를 실제로 변경했는가
5. 명시하거나 강하게 시사한 대안은 무엇인가
6. 원래 요구에 대해 실제로 필요한 답변은 무엇인가
7. 이 답변이 기존 추천, 결정, 계획과 검증을 어떻게 바꾸는가

이 질문에 답한 뒤 결과만 문서에 반영합니다.
Why chain, 해석 매트릭스와 내부 사고 과정은 저장하지 않습니다.

## 분류와 처리

| 성격 | 처리 |
| --- | --- |
| 명확한 범위 확정 | 범위, 제외 범위와 수용 기준에 반영 |
| 명확한 요구·제약 변경 | 직접 영향받는 요구·제약·우선순위만 갱신 |
| 질문 | 활성 요구에 직접 답하고, 기존 추천을 겨냥했다면 해당 추천 결론을 갱신 |
| 반론·우려 | 활성 요구를 유지한 채 기존 추천의 전제를 재검토하고 유지·변경·폐기를 명시 |
| 비교 제안 | 기존안과 대안을 같은 기준으로 다시 비교 |
| 추가 분석 | 공식 근거, 대안과 추천 결론을 보강 |
| 후속 후보 | 현재 설계와 독립된 발견으로 정규화하고 영향·owner를 작업 실행 workflow에 인계 |
| 혼합 | 확정 가능한 부분과 미답 판단을 분리 |

`A가 표준에 가까운데 처음부터 A를 쓰는 편이 낫지 않은가`는 A와 기존 추천을 다시 비교하라는 반론입니다.
`표준 방식으로 진행하면 되지 않는가`는 불필요한 조사나 선택을 열어두지 말고 표준 경로를 기본안으로 닫으라는 요구일 수 있습니다.

## 직접 답변 기준

- 피드백의 전제와 대안을 제거해도 같은 답변이 나온다면 직접 답변이 아닐 가능성이 큽니다.
- 활성 요구의 해법·결론을 먼저 답하고, 피드백이 그 해법에 미치는 영향과
  trade-off, 갱신된 추천을 뒤에 연결합니다.
- 우려로 기존 추천이 폐기되면 원래 요구를 함께 폐기하지 않고 이를 만족하는 다음
  대안을 제시합니다. 안전한 대안이 모두 충돌할 때만 충돌과 필요한 결정을 밝힙니다.
- 기존 추천을 유지하면 제시된 전제가 왜 결론을 바꾸지 않는지 설명합니다.
- 기존 추천을 바꾸면 이전 추천, 후속 전환, 남은 결정과 검증 순서를 함께 갱신합니다.
- 설계 결정과 실제 환경에서의 동작 검증을 분리합니다.
- 공식 지원 경로와 프로젝트 제약으로 결론을 낼 수 있으면 설계는 닫고 구현 검증만 남깁니다.

## 문서 반영

피드백은 다음 최종 형태 중 하나로 변환합니다.

- 확정 결정
- 요구사항 또는 수용 기준
- 범위 또는 제외 범위
- 남은 결정
- 재검토 조건
- 현재 설계와 독립된 후속 후보

해결된 질문과 댓글 인용문은 제거합니다.
확정 결정에는 다음 일곱 항목을 보존합니다.

1. 배경
2. 검토한 선택지
3. 선택
4. 선택 근거
5. 영향
6. 배제한 대안
7. 재검토 조건

`댓글에서 승인`, `요청에 따라`, `누가 선택` 같은 출처 표현은 남기지 않습니다.

## 남은 결정

다음처럼 프로젝트 외부 판단이 필요한 항목만 남깁니다.

- 제품 정책과 UX 우선순위
- 운영 비용과 보안 강도 사이의 감수 수준
- 법적 보존과 개인정보 처리
- 출시 범위와 일정

모듈 경계, 보편적 보안 기본값, 기술 표준형 선택, 테스트 전략과 API 의미는 먼저 기술 추천을 제시합니다.
구체적인 가설과 성공·실패 기준이 없는 spike를 만들지 않습니다.

## 실행 표면

이 workflow는 피드백에서 갱신할 설계 의미와 영향받는 artifact를 식별합니다. 문서, 코드,
테스트, 설정과 migration의 실제 변경 권한과 실행 경로는 작업 실행 workflow가 원래 요청의
원자별 권한으로 판정하고 각 전문 owner에 인계합니다.

## 완료 확인

- 반영 대상 피드백을 모두 확인했습니다.
- 질문과 반론에 직접 답했습니다.
- 기존 추천의 유지·변경·폐기가 문서 전체에 일관되게 반영됐습니다.
- 해결된 원문과 처리 과정이 최종 문서에 남지 않았습니다.
- 결정 근거는 대화 없이 복원할 수 있습니다.
- 진짜 남은 결정과 AI가 작성할 세부사항을 구분했습니다.
- 문서 상태, 계획과 검증 기준이 새 결론과 일치합니다.
