# 도구 도입과 생애주기 워크플로우

도구는 실행 시간뿐 아니라 설계, 구현, test, 문서, 갱신, 장애 조사, 오판과 제거 비용을 계속 발생시키는 유지보수 대상입니다. 새 도구의 기본값은 **도입하지 않음**이며, 기존 도구도 같은 기준으로 존치를 다시 입증해야 합니다.

## 적용 범위

- 외부 executable, GitHub Action, SaaS, package manager와 container image
- 저장소가 소유하는 shell·Python·Java 실행 script, verifier, hook, installer와 dispatcher
- skill에 포함된 mutation·검증 helper
- version, checksum, 설치·실행 방식, 호출 빈도와 hard gate 여부 변경

기존 도구의 단순 사용은 결정 문서를 반복하지 않습니다. 다만 caller, 보장, 비용이나 대체 가능성이 달라지면 존치 결정을 다시 엽니다.

## 평가 단위

도입·존치·제거는 파일, package, toolchain이나 실행 묶음이 아니라 **독립적으로
성공·실패하고 제거할 수 있는 관찰 책임**마다 판정합니다. 실제 executable과 caller에서
function, branch, parser, allow-list, assertion과 외부 호출이 각각 무엇을 차단하는지
먼저 복원합니다.

도구가 실행 platform·architecture·format·protocol·network path·actor처럼 Agent가 고른
선행 조건의 차이를 변환·우회·중계·호환하는 역할이라면, 그 도구만 평가 단위로 고립시키지
않습니다. 공통 시작·종료 상태를 고정하고 `선행 조건을 바꿔 도구가 사라지는 경로`와
`기존 선행 조건에 도구를 더하는 경로`를 완전한 경로끼리 비교합니다. 기본 template이나
현재 구현이 그 선행 조건을 사용한다는 사실은 선택을 확정하는 권위가 아닙니다.

- 표준 linter·schema 검증처럼 타당한 책임이 같은 파일의 custom 문자열 검사까지
  정당화하지 않습니다.
- 하나의 wrapper가 여러 단계를 orchestration해야 해도 각 blocking 책임은 아래 판단
  순서와 hard gate 필수조건을 독립적으로 통과해야 합니다.
- 보안 목적, 작은 코드 크기와 기존 구현 비용은 심사를 생략하거나 다른 책임의 근거를
  빌릴 이유가 아닙니다.
- 평가 문서의 도구군 이름이나 작성자가 분류한 목록을 coverage 증거로 사용하지 않고,
  최종 source의 모든 blocking 동작에서 존치 결정으로 역추적합니다.

## 판단 순서

다음 순서를 각 관찰 책임마다 건너뛰지 않습니다.

1. **근본 문제**: 도구 이름 없이 관찰된 실패, 영향, 빈도와 현재 증거를 정의합니다.
2. **원인 제거**: 책임·구조·인터페이스를 단순화해 문제가 사라지는지 검토합니다. 도구가
   선택한 선행 조건을 보상한다면 그 조건을 다시 열어 표준 경로로 도구 자체를 제거할 수
   있는지 먼저 확인합니다.
3. **무도구 대안**: review, 문서, 교육, 절차, 권한 경계와 수동 확인으로 충분한지 검토합니다.
4. **기존 기능**: 언어, build system, test framework, Git, CI 플랫폼과 이미 도입한 도구의 표준 기능을 우선합니다.
5. **가장 단순한 도구**: 그래도 자동화가 필요하면 가장 작은 관찰·경고·test부터 비교합니다.
6. **독립성**: 도구가 작성자의 자기 선언이 아니라 독립된 authoritative source를 읽는지 확인합니다.
7. **순효과**: 예방 효과에서 전체 생애주기 비용과 새 실패 위험을 뺀 값이 보수적으로도 충분히 큰지 판단합니다.
8. **배치**: 실제 사용 주체, 시점과 실패 경계 중 가장 좁은 위치에 둡니다.
9. **수명주기**: owner, 갱신, 관측, 강등·제거 조건과 복구 방법을 정합니다.
10. **검증**: 정상·실패·경계 동작과 실제 caller를 확인한 뒤에만 도입합니다.

앞 단계에서 충분한 해결책이 나오면 뒤 단계로 넘어가지 않습니다.
실행 platform이나 표준 도구가 실제 위험을 더 권위 있는 위치에서 강제하면 local
parser로 같은 조건을 복제하지 않습니다.

## custom hard gate의 필수조건

custom blocking verifier나 hook은 다음 조건을 **모두** 만족해야 합니다.

1. 막으려는 실패가 구체적이고 반복 가능하며 영향이 큽니다.
2. 대상이 기계적으로 관찰 가능한 불변식입니다.
3. verifier가 작성자와 독립된 authoritative source를 읽습니다.
4. 구조 변경, 표준 도구, 기존 test와 review로 충분히 해결할 수 없습니다.
5. false positive와 false negative의 발생 경로·영향·상한을 설명할 수 있습니다.
6. 실행 위치와 빈도가 위험에 비례하며 모든 작업에 무조건 실행할 이유가 있습니다.
7. 실패 메시지가 원인과 복구 행동을 바로 알려줍니다.
8. verifier가 만드는 새 실패 표면이 원래 위험보다 작고 별도 범용 방어를 요구하지 않습니다.
9. 구현·test·fixture·문서·호출자 유지 비용을 포함해도 순효과가 압도적입니다.
10. owner, 점검 시점과 warning 전환·삭제 조건이 있습니다.

하나라도 충족하지 못하면 hard gate로 두지 않습니다. 특히 다음은 hard gate 대상이 아닙니다.

- 자연어가 질문인지 실행인지 같은 열린 의미 판단
- 작성자가 다시 쓴 evidence·coverage·계획 JSON의 자기일관성
- 문서가 충분히 상세한지, 주석이 기술적으로 정확한지 같은 review 판단
- 다른 표준 gate의 성공 여부를 문자열로 복제한 판정
- 정확한 source 없이 추정한 caller·owner·failure boundary

서비스 기동, build, 배포 또는 운영 진입을 새로 중단시키는 custom hard gate는 내부 구현
방식만 바꾸는 기술 선택이 아니라 가용성과 운영 실패 경계를 바꿉니다. 독립 authoritative
source가 그 경계를 유일하게 강제하지 않으면 Agent는 위 필수조건을 모두 심사한 뒤에도
대안·추천까지만 제시하고, 사용자가 exact 실행 시점과 차단 결과를 긍정적으로 선택하기 전에는
선택된 설계·계획·구현으로 기록하거나 writer에 넘기지 않습니다. Proposed 문서에 후보로
비교하는 것은 가능하지만 현재 적용되는 gate처럼 서술하지 않습니다.

## 순효과 평가

다음 비용을 실행 시간과 별도로 계산합니다.

- 최초 설계·구현과 test·fixture 작성
- 호출자, schema, 문서와 하위 호환 유지
- version·platform 갱신과 공급망 검토
- false block 조사, 우회와 재실행
- false pass가 만드는 잘못된 확신
- 실패 로그 해석과 Agent context·token 비용
- 도구 자체 결함의 복구와 change amplification
- 더 중요한 작업을 늦추는 기회비용

도구가 A를 막지만 같은 심각도의 B를 만들거나, B 때문에 다시 범용 verifier가 필요하면 도입하지 않습니다. 유일한 해결책이라는 사실도 순효과가 음수인 도구를 정당화하지 않습니다.

## 실행 등급과 배치

| 등급 | 사용 조건 | 기본 배치 |
| --- | --- | --- |
| hard gate | 위 필수조건을 모두 만족하고 실패 뒤 진행이 위험함 | 관련 CI·release·operations 단계 |
| test | 구현 계약을 직접 재현하며 변경 시에만 필요함 | 해당 source와 가까운 test suite |
| advisory | 불확실하거나 오판 비용이 있어 사람이 판단해야 함 | review·진단 절차 |
| manual | 운영자·Agent의 상황 판단과 실제 환경이 필요함 | workflow 또는 runbook |

Agent 보조 도구를 애플리케이션 CI나 개발자 hook에 넣지 않습니다. 운영 live 검증을 일반 CI에 넣지 않으며, fake contract test와 live 실행을 같은 성공으로 표현하지 않습니다. 비싼 검증은 가장 늦고 좁은 권위 있는 경계에서 한 번 실행합니다.

## 결정 기록

도입하거나 중요한 방식으로 변경하는 도구는 work item design 또는 책임 기술 문서에 다음을 기록합니다.

```md
### 도구 또는 능력

#### 근본 문제와 증거
#### 공통 시작·종료 상태와 비교한 완전한 경로
#### 도구의 필요성을 만든 선행 조건과 그 권위
#### 도구를 쓰지 않는 대안
#### 비교한 도구와 가장 단순한 선택
#### 독립 oracle과 보장 범위
#### false positive·negative와 새 실패 표면
#### 생애주기 비용과 순효과
#### 실행자·시점·실패 경계
#### owner·갱신·강등·제거 조건
```

외부 도구는 공식 배포 방식, exact version·checksum 또는 immutable digest, 지원 OS·CPU, 최소 권한, secret·network·filesystem 신뢰 경계와 공식 근거를 추가합니다.

## 구현 인계 조건

도입·존치 판정을 통과한 저장소 실행 script는
[스크립트 엔지니어링 가이드](240-script-engineering-guideline.md)로 구현을 인계합니다.
이 문서는 다음 결정만 구현의 입력으로 넘깁니다.

- 독립적으로 성공·실패하고 제거할 수 있는 관찰 책임
- 공통 시작·종료 상태, 선택한 완전한 경로와 배제한 더 단순한 표준 경로
- 도구의 필요성을 만든 선행 조건과 사용자·source·Agent 중 그 선택의 권위
- 실제 caller, 실행 시점과 가장 좁은 실패 경계
- 독립 oracle, 보장 범위와 허용 가능한 오판
- 생애주기 비용, owner, 갱신·강등·제거와 복구 조건
- 외부 tool·version·checksum·권한·secret·network의 신뢰 경계

parser와 framework보다 기존 표준 기능을 우선하고, 여러 책임을 묶는 wrapper도 각 책임의
독립 판정과 제거 가능성을 유지해야 한다는 도입 조건은 구현 뒤에도 바뀌지 않습니다.
self-test는 구현 동작만 확인하며 도구의 필요성, 독립 oracle과 순효과를 대신 입증하지
않습니다. 구체적인 파일 분할, interface, 멱등성, 오류 처리, 보안, test와 운영 기준은
스크립트 엔지니어링 가이드가 소유합니다.

## 존치 검토와 제거

다음 중 하나가 생기면 기존 도구를 다시 평가합니다.

- 실제 caller 또는 owner가 사라졌습니다.
- 표준 도구가 같은 불변식을 더 직접 검증합니다.
- 고유 결함을 잡지 못하고 다른 gate를 복제합니다.
- false block, flake 또는 verifier 자체 결함이 반복됩니다.
- 실행·유지 비용이 검출 가치보다 커졌습니다.
- 원래 위협 모델이나 제품 단계가 바뀌었습니다.

존치 결론은 “이미 만들었음”이나 sunk cost로 정당화하지 않습니다. 복합 executable은
파일 전체를 한 번에 `유지`로 판정하지 않고 내부 관찰 책임마다 유지·분리·제거를
결정합니다. 타당한 형제 책임이나 전체 self-test 성공은 독립적인 존치 근거가 아닙니다.
제거할 때 caller, test, fixture, 문서와 설치 흔적을 같은 변경에서 정리하고, 필요한
보장을 더 단순한 owner로 이전합니다.

## 완료 조건

- 근본 문제와 관찰 증거를 정의했습니다.
- 도구가 보상하는 선행 조건을 고정하지 않고 같은 시작·종료 상태의 완전한 경로를
  비교했습니다.
- 구조적 해결, 무도구 대안과 기존 표준 기능을 먼저 비교했습니다.
- 선택이 가장 단순하며 독립 oracle과 보장 한계가 명확합니다.
- 순효과가 전체 비용과 오판·새 실패 위험을 포함해도 충분합니다.
- 실행자·시점·실패 경계가 가장 좁은 위치에 있습니다.
- owner, 갱신·강등·제거 조건과 복구 방법이 있습니다.
- 실제 caller와 정상·실패 검증이 성공했습니다.
- 최종 executable의 모든 blocking 동작이 책임별 존치 결정으로 역추적되며, 묶음 판정이나
  self-test만으로 통과한 책임이 없습니다.
