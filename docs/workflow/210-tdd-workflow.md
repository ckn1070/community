# TDD 워크플로우

이 문서는 기능 추가, 버그 수정, 도메인 로직 변경을 TDD 방식으로 진행하는 기준을 정의합니다.

## 목적

- 테스트를 사후 확인 수단이 아니라 구현 방향을 결정하는 기준으로 사용합니다.
- 작은 실패, 작은 구현, 작은 리팩터링 사이클로 변경 위험을 줄입니다.
- TDD가 적절하지 않은 작업은 이유와 대안을 명확히 남깁니다.

## 적용 범위

- 기능 추가
- 버그 수정
- 도메인 로직 변경
- API 동작 변경
- 데이터 처리 규칙 변경
- 회귀 가능성이 있는 리팩터링

문서 수정, 단순 설정 변경, 탐색용 spike, 시각 조정처럼 TDD의 이점이 낮은 작업은 예외가 될 수 있습니다.

## 핵심 원칙

- 대부분의 개발 작업은 TDD를 기본 방식으로 진행합니다.
- 먼저 실패하는 테스트를 작성하고, 실패 이유가 기대한 이유인지 확인합니다.
- 테스트를 통과시키는 최소 구현을 먼저 합니다.
- 테스트가 통과한 상태에서만 리팩터링합니다.
- 테스트는 구현 세부사항보다 관찰 가능한 동작을 검증합니다.
- TDD가 어렵다면 작업 전에 이유와 대안을 제시합니다.

## 기본 사이클

1. 테스트 목록을 작성합니다.
2. 가장 작은 동작 하나를 고릅니다.
3. 실패하는 테스트를 작성합니다.
4. 테스트가 기대한 이유로 실패하는지 확인합니다.
5. 테스트를 통과시키는 최소 코드를 작성합니다.
6. 관련 테스트를 통과시킵니다.
7. 중복과 구조 문제를 리팩터링합니다.
8. 다음 작은 동작으로 반복합니다.

이 흐름은 `Red -> Green -> Refactor`를 기본 리듬으로 사용합니다.

## 테스트 작성 기준

- 테스트 이름은 검증하는 동작을 드러냅니다.
- 하나의 테스트는 하나의 핵심 동작을 검증합니다.
- 실패하지 않는 테스트, assertion이 없는 테스트, 구현만 따라가는 테스트는 피합니다.
- 버그 수정은 먼저 버그를 재현하는 실패 테스트를 작성합니다.
- 경계값, 예외, 권한, 데이터 무결성은 우선순위를 높게 둡니다.
- 외부 시스템은 가능한 한 fake, mock, test fixture, test container 등으로 통제합니다.

테스트 코드 내부 구조, test double 선택, 커버리지와 테스트 완료 기준은 [230-test-writing-guide.md](230-test-writing-guide.md)를 따릅니다.

## Spring Boot 적용 기준

- 순수 도메인 로직은 단위 테스트를 우선합니다.
- 웹 요청/응답 계약은 MVC slice 테스트 또는 통합 테스트로 검증합니다.
- JPA, Flyway, PostgreSQL 동작이 핵심이면 실제 DB에 가까운 통합 테스트를 검토합니다.
- 보안 규칙은 인증/인가 성공과 실패 케이스를 함께 검증합니다.
- 테스트 범위는 변경 위험과 실행 비용의 균형을 기준으로 정합니다.

## TDD 예외 기준

다음 경우에는 TDD를 바로 적용하지 않을 수 있습니다.

- 문서만 변경하는 작업입니다.
- 빌드, 설정, 의존성 변경처럼 검증 명령이 더 직접적인 작업입니다.
- 요구사항이나 기술 가능성을 확인하는 짧은 spike 작업입니다.
- UI 시각 조정처럼 자동 테스트보다 화면 확인이 더 적절한 작업입니다.
- 기존 코드에 테스트 작성 지점이 없어 먼저 구조 파악이나 test seam이 필요한 작업입니다.
- 외부 서비스, 인프라, 운영 환경 의존성이 커서 테스트 환경을 먼저 설계해야 하는 작업입니다.

## 예외 시 대안

TDD로 진행하지 않는 경우에는 다음 중 적절한 대안을 제시합니다.

- 검증 명령을 먼저 정의하고 작업 후 실행합니다.
- characterization test로 현재 동작을 고정한 뒤 변경합니다.
- test seam을 먼저 만들고 이후 TDD로 전환합니다.
- spike 결과를 폐기하거나 정리한 뒤 테스트 가능한 구현으로 다시 작성합니다.
- 자동 테스트가 어려운 UI 변경은 브라우저 확인, 스크린샷, 수동 확인 기준을 남깁니다.

## TDD 증거

개발 검증과 완료 판정에 다음 증거를 제공합니다.

- Red가 기대한 이유로 실패한 관찰 결과
- Green에서 고정한 핵심 동작과 위험 경계
- 실행한 test 명령과 실제 결과
- TDD 예외의 이유와 선택한 대체 검증

공통 완료 판정과 이 증거의 채팅 보고 방식은 각각
