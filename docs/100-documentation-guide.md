# 문서 정보 구조 가이드

이 문서는 저장소에 어떤 정보를 어떤 문서가 소유하는지, 목적별 문서 구조와 보존 기준을 정의합니다. 문서를 작성하고 검증하는 순서는 [150 문서화 워크플로우](workflow/150-documentation-workflow.md)가 소유합니다.

## 목표

- 독자가 필요한 현재 사실, 결정, 작업 상태와 실행 절차를 가장 짧은 경로에서 찾게 합니다.
- 하나의 정보에는 하나의 canonical owner만 두고 다른 문서는 관계를 표시해 연결합니다.
- 각 문서는 하나의 독자 목적만 소유하고 같은 질문의 답을 여러 문서에 나누거나 반복하지 않습니다.
- 깊은 조사 결과를 그대로 누적하지 않고 독자의 판단과 행동에 필요한 정수로 압축합니다.
- 내용 누락과 함께 불필요한 반복, 오래된 결론과 과도한 예시도 결함으로 다룹니다.
- 영구 문서와 현재 대화의 보고를 분리합니다.

## 문서 선택 기준

문서 종류는 주제가 아니라 독자가 하려는 일과 정보의 수명으로 선택합니다.

| 유형 | 독자의 핵심 질문 | 소유하는 내용 | 소유하지 않는 내용 |
| --- | --- | --- | --- |
| Router | 어디로 가야 하는가 | 범위, 상황별 canonical owner, 읽기 순서 | 상세 기준과 절차 전문 |
| Reference/SOT | 현재 무엇이 사실인가 | 정의, 경계, 관계, 불변식, 현재 계약 | 작업 진행률과 결정 과정 |
| Decision/Design | 왜 무엇을 선택했는가 | 결정 질문, 대안, 선택·근거, 영향, 재검토 조건, 목표 계약 | 현재 진행률, 실행 로그, dirty 상태 |
| Plan | 무엇을 달성하고 어떻게 판정할 것인가 | 결과, 범위, 제약, 수용 기준, 의존 작업, 검증, 전환·복구, SOT 대상 | 완료 결과를 가장한 예상과 실행 일지 |
| Procedure | 언제 누가 어떻게 실행하는가 | 사용 시점, actor·전제, 정상 흐름, 기대 결과, 중단·복구 | 선택되지 않은 설계와 진행률 |
| Operations Scenario | 전체 운영 목표를 어디까지 실행했고 어디서 재개하는가 | 여러 runbook의 의존 순서·handoff·전체 완료 조건, 해당 환경의 현재 live 상태·다음 행동 | 세부 명령, 영구 구조 설명, 별도 승인 없는 새 운영 설계 |
| Result/Status | 무엇이 끝났고 무엇이 남았는가 | 원래 목표 대비 판정, 완료·미완료, 사유·책임, 검증 요약, SOT 링크 | 과거 계획 전문과 반복 실행 기록 |
| History | 어떤 고유 사건을 장기 보존해야 하는가 | 사건·영향, 시스템 원인, 실패한 방어, 변경 통제, 남은 위험 | 대화 원문, Why chain, 현재 규칙 |

이 유형은 의미 계약이지 파일 수를 늘리는 규칙이 아닙니다. 짧고 응집된 인접 정보는 한 파일에 둘 수 있고, 독자·행동·source·갱신 주기·보존 기간이 다르면 파일을 분리합니다.
Work item의 Plan은 단계마다 별도 문서를 만든다는 뜻이 아닙니다. 현재 단계의 최소 artifact와
단계별 책임은 [작업 문서 생명주기](work-items/100-work-item-lifecycle.md#계획-단계와-최소-artifact)가 소유합니다.

## 목적별 기본 구조

아래 구조는 유형별 독자 질문의 기본 순서이지 모든 문서에 강제하는 목차가
아닙니다. 실제 목적·source·정보 관계에 따라 필요 없는 절은 두지 않고, 인접한
질문은 병합하며, 독자의 판단 순서에 맞게 재배치합니다.

### Router

1. 이 router가 다루는 범위
2. 상황별 canonical owner
3. 필요한 경우 읽기 순서

Router는 상세 내용을 요약해 새로운 사실을 소유하지 않습니다.

### Reference/SOT

1. 목적과 적용 범위
2. 핵심 용어와 mental model
3. 책임·경계·관계
4. 현재 규칙과 불변식
5. 실패·예외 또는 변경 시 동반 확인
6. 구현 source와 방향이 표시된 관련 문서

개념, 정책, 현재 구조 지도와 파일·폴더 README는 이 유형의 변형입니다. 파일·폴더 설명은 역할, 배치 이유, 소비자·변경 주체, 연결 관계와 변경 시 확인 대상을 답합니다.

Reference/SOT의 설명 책임을 Procedure로 대신하지 않습니다. Procedure의 순서와 명령은
현재 구현 관계를 확인하는 source가 될 수 있지만, 독자가 명령을 차례로 읽고 의미를
역추론해야만 개념·구성요소·trigger·값 전달·결과를 알 수 있다면 Reference/SOT에 설명
공백이 있는 것입니다. 설명 문서의 coverage를 검토할 때는 runbook·workflow·development
절차를 합격 근거에서 제외하고, Reference/SOT만으로 mental model과 end-to-end 관계를
복원할 수 있는지 판정합니다.

### Decision/Design

결정마다 다음을 보존합니다.

1. 결정할 질문과 배경
2. 실제로 검토한 선택지
3. 선택과 근거
4. 영향과 감수한 trade-off
5. 배제 대안
6. 재검토 조건

확정된 목표 계약은 포함할 수 있지만 개발 순서와 실행 결과를 반복하지 않습니다.

### Plan

1. 달성할 결과, 범위와 제외 범위
2. 제약, 요구사항과 관찰 가능한 수용 기준
3. 확정 결정과 남은 결정
4. 의존 관계와 의미 단위 작업
5. 검증, 전환·복구와 영구 SOT 대상

작업은 파일 목록이 아니라 행동의 목적·이유·완료 결과로 설명합니다. 구현 세부가 결정 근거와 독자가 다르면 design으로 위임합니다.

문서의 파일명, 접미사, 본문·companion 구분이나 현재 계획 단계와 무관하게 독자 목적이
계획의 작성·검토·확정이면 첫 화면에 현재 결론과 다음 행동을 둡니다. 제목과 상태·계획 단계
바로 다음부터 첫 배경·문서 경계·상세 결정 전에 다음 의미를 한 번에 복원할 수 있어야 합니다.

- 현재 단계와 현재 결론
- 닫힌 결과와 아직 닫히지 않은 gate
- 각 미완료 gate의 canonical owner가 판정한 실제 상태. 이 문서에서 별도 상태 vocabulary를
  만들거나 `검증 불가`·`판정 불가` 같은 결과를 다른 상태로 낮추지 않음
- 지금 행동할 actor와 그 actor가 수행할 exact 행동
- 사용자 입력이 지금 필요하면 exact 질문, 선택지 전체와 결과 차이, 추천·근거와 응답 형식
- Agent 검증·보완처럼 사용자보다 먼저 닫을 gate가 있으면 그 actor·행동, 사용자 차례가 되는
  조건과 그때 사용할 응답 방식
- 현재 행동 뒤 만들어질 결과와 다음 단계 전환 조건

상세 결정과 근거는 해당 section이 소유하고 첫 화면은 그 exact 범위로 연결합니다. 독자가
현재 행동을 알아내기 위해 하단 section이나 다른 문서를 먼저 찾아가게 하지 않습니다. 모든
gate가 닫혔으면 완료 결론과 다음 허용 행동만 표시하며, 새 선택지·재확인이나 응답 형식을
만들지 않습니다. 계획 후보 작성, 검증 시작·결과, 피드백에 따른 재검토, 사용자 확정과 단계
전환으로 결론·gate 상태·actor·다음 행동 중 하나가 바뀌면 사용자 검토나 다음 actor 인계 전에
같은 변경에서 첫 화면을 현재 상태로 교체합니다. 과거 상태를 뒤에 누적하지 않습니다.

### Procedure

1. 언제 누가 사용하는가
2. 전제와 입력
3. 정상 실행 순서와 단계별 기대 결과
4. 중단·실패 판정
5. 복구·되돌리기
6. 완료 확인

Workflow는 반복 가능한 작업 방법, development는 로컬 개발 절차, operations runbook은 실제 환경 명령을 소유합니다. 서로 다른 운영 작업은 한 거대 runbook에 누적하지 않습니다.

Runbook 단계의 실행 우선 배치, 독립 명령 목록의 주석·terminal-visible 구분자와 compound
recipe 보존 기준은
[150 문서화 워크플로우의 Procedure 실행 계약](workflow/150-documentation-workflow.md#4-구조-gate)을
적용합니다. 이 가이드는 표현 형식을 중복 정의하지 않고 해당 실행 gate로 연결합니다.

Operations router와 runbook은 기술 구성요소보다 운영자가 처한 상황과 생애주기를 먼저
구분합니다. 최소한 최초 구축, 평소 반복 작업, 구성·credential 변경, 장애 진단·복구 중
현재 corpus에 존재하는 상황을 서로 다른 진입점으로 제공하고, 한 runbook은 하나의
운영 상황·사람 목표만 소유합니다. 같은 기술을 다루더라도 최초 설치와 반복 검증처럼
생애주기와 사람 목표가 독립적이면 분리하고 서로 링크합니다. 하나의 상황·목표 안에서
단계별 중단·복구 checkpoint와 재개 지점이 여러 개인 것은 같은 runbook이 소유할 수
있습니다.

자동화 script·workflow가 내부에서 수행하는 설치 순서, artifact 가공과 구현 선택은 그
자동화의 Reference/README 또는 구현 source가 소유합니다. Runbook에는 사람이 자동화를
시작·관찰·중단·재개·복구하기 위해 알아야 하는 입력, 명령, 상태와 결과만 둡니다. 반대로
시스템의 actor·구성요소·artifact 전달·자동화 경계·작동 원리와 선택 이유는
Reference/SOT와 Decision/Design에서 누락 없이 복원할 수 있어야 하며, runbook 전문을
읽어야만 알 수 있게 두지 않습니다.

Procedure는 선택돼 현재 유효한 실행 계약을 설명하지, 문서의 빈칸을 채우기 위해
운영 방식을 새로 설계하지 않습니다. 구조 개편에서는 기존 절차를 보존·재배치하고
authoritative source가 유일하게 결정하는 사실 오류를 바로잡을 수 있습니다. 다음
내용을 새로 정하면 문서 보완이 아니라 운영 설계입니다.

- 새 actor와 책임 이관
- 외부 시스템을 변경하는 새 단계나 orchestration
- credential·임시 파일·증거의 생성, 보존과 폐기 lifecycle
- 상태, 전이 조건과 불확실한 결과의 판정 정책
- 보안 경계, 실패 처리, rollback과 복구 정책

이 의미가 사용자 요청, authoritative source 또는 승인된 설계에 없으면 runbook에
완결된 현재 절차로 쓰지 않습니다. 필요한 공백은 정확한 미결정과 영향으로 분리해
결정 경로로 보내며, 문서를 자기 완결적으로 보이게 하려고 임의 계약을 만들지 않습니다.
공통 전제와 반복 절차는 하나의 owner에 두고 각 runbook은 해당 시나리오의 차이와
handoff만 소유합니다.

### Operations Scenario

여러 runbook을 조합하는 operations scenario는 재사용 가능한 전체 흐름과 해당 환경의
현재 live 진행 상태를 명확한 section으로 나눠 한 파일에서 소유할 수 있습니다. Scenario는
상세 명령을 복제하지 않고 각 runbook으로 연결하며, 상태가 바뀌면 과거 snapshot을
누적하지 않고 현재 checklist·근거·다음 행동·blocker를 교체합니다. 외부 환경의 live 상태는
project SOT나 개별 runbook에 중복하지 않으며 과거 값은 Git 이력으로 복원합니다.

재사용 흐름은 빈 환경에서 처음 실행하는 독자가 같은 상태 전이를 한 번만 수행하도록
작성합니다. Artifact revision이나 전달 inventory가 바뀌었다는 이유로 기존 단계를 완료
snapshot과 재실행 단계로 나누지 않고, 기존 단계의 현재 입력·완료 조건을 갱신합니다. 이미
구축한 환경에 그 변경을 다시 적용해야 하는 사실은 현재 live 상태·다음 행동·blocker에만
두며, 적용 뒤에는 새 현재 상태로 교체합니다. 두 실행 항목뿐 아니라 복합 항목 안의 하위
행동도 actor·artifact·effective target state·상태 전이·완료 조건으로 원자화합니다. 이 값이
같고 시점·revision·임시 경로·`확장`·`재전달` 같은 표현만 다르면 하나의 재사용 단계입니다.
제목이나 최종 완료 조건이 다른 항목 안에 있다는 이유로 동일한 하위 전달 전이를 다시 두지
않습니다.

Scenario의 각 실행 항목은 그 항목만 읽어도 다음 내용을 복원할 수 있어야 합니다.

- **행동**: 실제로 확인하거나 상태를 바꾸는 작업
- **실행**: actor, 실행 위치와 exact 진입점
- **완료**: 다음 항목으로 넘어갈 postcondition 또는 확인 증거
- **상세 절차**: 번호와 책임이 표시된 canonical runbook link

Repository script가 진입점이면 exact executable path를 표시합니다. Script가 없는
수동 단계는 실제 Console 화면, workflow, 표준 명령이나 수동 조작을 표시하고 repository
script가 없다는 사실을 명시합니다. 표준 명령 하나가 사람의 전체 목표와 postcondition을
원자적으로 닫을 때만 Scenario가 exact 진입점과 완료 조건을 직접 소유할 수 있습니다.
Credential 획득, 둘 이상의 명령·API 상태 전이 또는 독립 실패·재개가 있으면 실행 빈도와
무관하게 canonical runbook이 전체 인자·명령과 실패 진단을 소유합니다. 이때 별도 work item이나
repository executable까지 만들지는 않습니다.
설명을 읽은 뒤에도 독자가 `누가, 어디에서,
무엇을 실행하고, 무엇을 확인해야 하는가`를 추측해야 하면 실행 항목은 미완료입니다.
Authoritative source에 안전한 진입점이 아직 없으면 명령을 지어내지 않고 해당 행동을
실행 불가·미완료로 표시하며, 결정 owner와 그 전까지의 중단 지점을 명시합니다.

### Result/Status

1. 전체 목표와 현재 판정
2. 완료한 결과
3. 미완료 결과, 사유와 책임
4. 현재 유효한 검증 요약
5. 승격한 SOT와 다음 실행 조건

상태가 바뀌면 이전 상태 설명을 뒤에 누적하지 않고 현재 구조로 교체합니다. commit SHA, staged·unstaged 상태와 반복 test 수치는 영구 사실이 아니므로 현재 보고와 Git이 소유합니다.

## 문서와 보고의 분리

저장소 문서는 다음 작업자가 대화 없이 장기 사실을 복원하기 위한 artifact입니다. 채팅 보고는 현재 사용자가 상태를 판단하고 다음 행동을 결정하기 위한 일시적 projection입니다.

- 문서는 현재 사실·결정·재사용 절차를 보존합니다.
- 보고는 지금의 완료·차단·검증·Git 상태를 전달합니다.
- 보고 전문을 work item이나 별도 Markdown에 복사하지 않습니다.
- 계획 문서는 구현 가능성을, 계획 보고는 준비도와 열린 결정을 우선합니다.
- 결과 문서는 지속되는 결과를, 완료 보고는 현재 실행·검증·Git 사실을 우선합니다.
- 개념 문서는 재사용 가능한 mental model을, 설명 답변은 현재 질문에 대한 직접 답을 우선합니다.

목적별 보고 라우팅과 공통 원칙은 [140 완료 및 작업 보고 워크플로우](workflow/140-completion-reporting-workflow.md)가 소유합니다.

## 문서 그룹 책임

| 위치 | 소유하는 내용 |
| --- | --- |
| `AGENTS.md` | 최상위 불변 조건과 router |
| `docs/000-index.md` | 전체 문서 router |
| 그룹 `000-index.md` | 해당 그룹의 상황별 진입점 |
| `architecture` | 일반 구조 원칙과 설계 방법 |
| `tech-stack` | 기술별 현재 기준과 선택 근거 |
| `project` | 현재 프로젝트 repository에 적용된 영구 구조와 기술 계약 |
| `domain` | 업무 의미, 상태와 정책 |
| `product` | 제품 목표와 기능 범위 |
| `development` | 로컬 설치와 실행 절차 |
| `workflow` | 반복 가능한 작업 절차 |
| `work-items` | 작업별 계획 또는 현재 결과와 결정 연결 |
| `operations` | 실제 환경의 구축·복구·점검 절차와 scenario별 현재 live 상태 |

Repository의 현재 구조·계약은 SOT, 결정 이유는 design, 개발 작업 상태는 work item,
실행 명령은 runbook, 외부 환경의 현재 live 상태·재개 위치는 operations scenario가 각각
소유합니다.

그룹 router는 문서 이름만 나열하지 않고 독자의 상황을 canonical owner로 연결합니다.
특히 operations router는 최초 구축, 반복 운영, 변경, 장애·복구의 실제 보유 범위를
드러내며, 개념을 이해하려는 독자는 해당 Reference/SOT로 보냅니다. Reference/SOT는
관련 동작을 실행할 runbook으로 방향을 표시하되 명령 전문을 복제하지 않습니다.

## 관계 표현

`관련 문서`만 나열하지 말고 독자가 관계의 방향을 알 수 있게 표시합니다.

- **현재 기준**: 지금 적용되는 규칙 또는 상태의 canonical owner
- **결정 근거**: 현재 선택의 배경과 대안
- **구현 source**: 문서의 주장을 실제로 실행하는 코드·설정·schema
- **작업 상태**: 구현 공백, 남은 책임과 다음 단계
- **실행 절차**: 사람이 수행할 명령과 복구
- **대체 문서**: 이 문서의 현재 책임을 이어받은 owner

전체 관계를 별도 catalog로 복제하지 않습니다. 각 문서의 자연스러운 진입점과 관련 절에서 필요한 방향만 표시합니다.
한 질문의 결론을 두 문서에 각각 요약해 current owner를 늘리지 않습니다. 다른 문서가 그
결론을 필요로 하면 관계와 canonical target만 표시하고, 독자가 결론을 찾으려고 두 문서를
왕복해야 하면 owner를 다시 분리합니다.

## 사실의 근거 경계

주장의 종류에 맞는 authoritative evidence를 사용합니다.

| 주장 | 근거 | 확대하면 안 되는 판정 |
| --- | --- | --- |
| repository 실행 사실 | 현재 code·workflow·script·설정·schema | 문서끼리 일치한다는 이유로 실제 동작이라고 판정 |
| 외부 제품·도구 계약 | 사용 version의 공식 upstream 문서 | 과거 local 설명을 현재 공식 계약으로 판정 |
| live 환경 상태 | 실제 환경의 명령·check·관찰 결과 | local 검증 성공을 live 성공으로 판정 |
| 미실행 외부 책임 | 현재 work item의 상태와 실행 책임 | procedure가 존재한다는 이유로 완료로 판정 |

문서 하나에서 여러 종류를 설명할 수 있지만, 각 주장이 어느 근거에 의존하는지와 아직 미검증인지 구분합니다.
Runbook의 명령 syntax·정적 source 대조는 문서와 repository 계약의 정합성만
증명합니다. 실제 계정·권한·네트워크·외부 상태에서 실행하지 않았다면 production
절차의 성공, 멱등성, 복구 가능성과 운영 안전성을 검증했다고 쓰지 않습니다.

## 정보 관계와 표현 선택

표현을 먼저 고르지 않습니다. 문서의 목적과 독자 질문을 확정한 뒤 각 section을
필요한 정보 단위로 나누고, 그 정보가 보존해야 하는 관계에 맞는 가장 작은
표현을 선택합니다.

```text
문서 → section의 독자 질문 → 정보 단위 → 관계 유형 → 최소 표현
```

| 정보 관계 | 보존해야 할 의미 | 적합한 표현 |
| --- | --- | --- |
| 개념·설계 의도 | 정의, 목적, 작동 원리와 이유 | 설명문과 작은 mental model |
| 인과 | 원인, 작동 기제, 결과와 영향 | 설명문, 복잡하면 인과 chain |
| 실행 순서·분기 | 선후 관계, 분기 조건, 합류·종료 지점 | 흐름도·순서도, 단순하면 번호 단계 |
| 계층·소유 | 부모·자식, 소유자, 경계 | tree·계층도 |
| 호출 | 호출자, 대상, 행위, 인자·조건, 결과와 후속 소비자 | 방향 graph, 단순하면 `A → B` 문장 |
| 의존 | 의존하는 대상, 의존 이유, 영향 방향과 변경 여파 | dependency graph·matrix |
| 생산자·값·소비자 | 누가 어떤 값·artifact를 만들고 누가 왜 쓰는지 | 생산자→전달값→소비자 관계표 |
| 비교 | 같은 차원에서의 차이와 선택 기준 | 비교표 |
| 상태 전이 | 상태, event·조건, 다음 상태와 금지 전이 | 상태도·전이표 |
| 범위·경계 | 포함·제외, 책임, 보증·비보증 경계 | 경계표, 단순하면 대응 목록 |
| 규칙·불변식 | 적용 범위, 필수·금지 조건 | 짧은 선언문과 목록 |
| 실행 절차·명령 | actor, 전제, 순서, 기대 결과와 복구 | 번호 단계와 명령 block |

표와 section의 분류 축은 source의 항목 종류나 작성 순서보다 독자가 한 번에 판단할
대상을 우선합니다. 판단 대상 하나의 속성·제약·예외·검증 근거를 함께 봐야 의미를
복원할 수 있으면 같은 하위 section의 인접한 표현에 둡니다. 같은 대상을 이해하려고
떨어진 여러 표에서 식별자를 찾아 다시 합치게 하는 구조는 대상별로 나누거나 필요한
관계를 같은 표현에 모읍니다.

여러 대상을 하나의 표에 모으는 것은 그 대상들을 같은 차원에서 비교하는 것이 독자
질문일 때만 적합합니다. 모든 대상에 똑같이 적용되는 공통 규칙이나 별도 생명주기를
가진 정보는 하나의 owner에 둘 수 있으며, 이때는 대상마다 복제하지 않고 적용 범위와
연결 방향을 표시합니다. 작성 뒤에는 대표 대상 하나를 골라 같은 질문의 답을 얻기 위해
둘 이상의 떨어진 표를 오가며 식별자로 재조합해야 하는지 확인합니다. 그렇다면 분류
축과 인접 배치를 다시 설계합니다.

표·그림 자체가 품질 기준은 아닙니다. 한 문장으로 관계를 하나의 의미로 복원할 수
있으면 더 큰 표현을 만들지 않습니다. 반대로 호출 관계에 호출자만 있거나 흐름에
분기 조건이 없다면 표나 그림이 있어도 완결된 설명이 아닙니다.

각 독자 질문에는 주된 표현을 하나만 두고, prose는 그 표현이 담지 못한 정의·경계·
이유만 보완합니다. 같은 사실을 흐름도·표·본문에서 반복하지 않습니다.

## 핵심과 부가 설명

- 첫 화면과 상위 heading에는 목적, 결론, 핵심 관계와 다음 탐색 경로를 둡니다.
- 배경과 세부 조건은 핵심 판단을 이해하는 데 필요한 만큼만 하위 계층에 둡니다.
- 예시는 제거했을 때 규칙이 실제로 모호해지는 경우에만 사용합니다.
- 대표 정상 예시와 대표 반례면 충분하며 exhaustive case는 test·fixture·source가 소유합니다.
- 표와 목록은 관계를 압축할 때 사용하고 같은 내용을 다시 prose로 풀어쓰지 않습니다.
- line 수를 품질 기준으로 사용하지 않습니다. 문서가 여러 독자 행동이나 갱신 주기를 소유하면 분리합니다.

## 보존 등급

| 등급 | 저장 방식 | 위치 |
| --- | --- | --- |
| 현재 기준 | 현재형으로 정규화 | 책임 SOT |
| 결정 기록 | 판단 구조만 보존 | design 또는 기술 SOT |
| 작업 상태 | 현재 결과와 남은 책임만 유지 | work item |
| 감사 증거 | Git으로 복원할 수 없는 최소 사건만 요약 | 선택형 history 또는 외부 감사 시스템 |
| 비보존 | repository에 저장하지 않음 | 대화와 실행 중 세션 |

지시·승인 원문, 내부 사고 과정과 Why chain, dirty baseline, 반복 commit·검증 기록, 임시 inventory와 자기보고 장부는 저장하지 않습니다. 원문 자체가 제품 산출물이거나 법적·보안 감사에 필요한 최소 증거일 때만 secret과 개인정보를 제거하고 보존 기간·제거 조건과 함께 예외로 둡니다.

### 보완과 삭제

현재 독자 질문과 owner가 유지되는 문서는 보완을 기본 처분으로 삼습니다. 논의 중 새 요구,
질문이나 누락이 발견되더라도 기존 문서 전체가 자동으로 무효가 되지 않습니다. 바뀐 의미와
직접 소비자만 수정하거나 재검토 상태로 두고, 영향받지 않은 결정·계약·고유 정보는 같은
문서에서 보존합니다.

`삭제에 준하는 대규모 제거`는 파일을 남기더라도 독자가 복원하던 핵심 질문, canonical
owner 계약 또는 상태·결정 section 묶음을 실질적으로 없애는 효과입니다. 정보가 중복인지,
Git에서 복원 가능한지와 무관하게 실제 제거 효과의 범위로 판정합니다.

문서 전체 삭제는 다음 조건 중 하나가 source로 확인될 때만 후보가 됩니다.

- 문서가 소유하던 독자 목적과 canonical 책임이 사라졌습니다.
- 다른 문서가 그 책임과 모든 고유 정보를 완전히 이어받아 원본이 중복 owner가 됩니다.
- 문서 전체가 현재 source와 양립할 수 없고 부분 보완이나 재검토 상태로는 독자를 안전하게
  안내할 수 없습니다.

Git에서 복원할 수 있다는 사실, 문서가 오래됐다는 사실과 탐색 비용만으로는 삭제 후보가
되지 않습니다. 문서 전체 삭제나 이에 준하는 대규모 제거는 후보가 되더라도
[100 작업 실행 워크플로우의 문서 삭제 권한](workflow/100-work-execution-workflow.md#문서-삭제-권한)과
[150 문서화 워크플로우의 문서 삭제 admission](workflow/150-documentation-workflow.md#문서-삭제-admission)을
모두 통과해야 합니다.

## 새 문서와 분리 기준

다음을 모두 만족할 때만 새 문서를 만듭니다.

- 기존 문서에 명확한 owner가 없습니다.
- 독자 질문·행동, authoritative source, 갱신 주기 또는 보존 기간이 기존 책임과 다릅니다.
- 기존 문서에 넣으면 단일 목적이 깨집니다.
- 반복해서 참조할 가치가 있습니다.
- 관련 router에서 자연스럽게 찾을 수 있습니다.

한 파일이 길다는 이유만으로 분리하거나, 일회성 경위·기존 문장의 반복·미확정 추천을 위해 영구 문서를 만들지 않습니다.
현재 단계의 기존 owner가 같은 독자 질문을 수용할 수 있거나 선행 결과가 아직 닫히지 않아
새 문서의 내용이 달라질 수 있으면 새 문서를 만들지 않습니다.

## 번호와 이동

일반 문서의 구조 번호와 work item 번호는 서로 다른 계약입니다.

### 구조 번호

- 번호 범위는 파일이 직접 속한 디렉터리입니다.
- `000`은 해당 디렉터리의 router입니다.
- direct-directory router가 현재 번호 그룹을 안내하지만 스스로 옳음을 증명하는
  oracle은 아닙니다. 새 numbered document·책임 group을 만들거나 기존 topology를
  변경하기 전에는 편집 전 directory inventory, 실제 책임과 router map을 함께 고정하고
  아래 순서 계약에 다시 대조합니다.
- 서로 다른 활성 책임 group에는 가장 작은 hundred block부터 `100`, `200`, `300`
  순서로 빈 block 없이 배정하고, router에 `번호대 → 책임` group map을 명시합니다.
  첫 활성 group이 `200`부터 시작하거나 활성 group 사이의 hundred block이 비어 있으면
  과거 삭제·이동의 흔적을 새 group 뒤에 이어 붙이지 않고 현재 책임 순서로 재번호합니다.
- 한 group은 `x00`부터 `x90`까지 최대 10개 문서를 10 단위로 정렬합니다. `x00`은
  그 group의 첫 문서이고 `x10`~`x90`은 독자의 읽기 순서입니다. 한 group이 10개를
  넘으면 다음 hundred block을 같은 책임의 overflow로 사용하지 않고, 책임을
  분리하거나 하위 디렉터리로 재구성한 뒤 새 group을 배정합니다.
- `200`과 같은 hundred boundary는 앞선 활성 group이 있고 router group map에 선언된
  새 책임의 시작일 때만 새 group입니다. group map이 없거나 순서 계약·actual sibling과
  다르면 번호를 판정할 수 없는 구조 결함입니다.
- 활성 group 내부의 사용하지 않은 10 단위 번호는 결함이 아닙니다. 사용하지 않은
  hundred block이 활성 group보다 앞에 있는 것은 같은 의미의 빈 번호가 아닙니다.
- 책임이나 읽기 순서가 바뀌면 재번호할 수 있지만, 파일 이동과 모든 inbound link를
  같은 작업에서 갱신합니다.
- 새 numbered document의 path는 편집 전 inventory와 group map을 대조한 뒤 선택합니다.
  그 결과 새 group map entry, owner 분리, 재번호나 rename이 필요하면 line 수와 무관한
  topology 변경으로 분류하고, path를 만들기 전에 before/after topology와 move·link
  범위를 먼저 감사합니다.
- `AGENTS.md`, root·하위 `README.md`, `.agents/**`, work item template처럼 이름이
  외부 계약이나 도구 진입점인 파일에는 구조 번호를 강제하지 않습니다.

### 번호가 있는 문서의 표시 이름

- Markdown link 대상 파일 이름이 `NNN-*.md` 또는 `NNN-index.md`이면 표시 이름에도
  해당 세 자리 번호와 문서 책임을 함께 씁니다. 독자가 link를 열지 않고도 어느 단계의
  어느 문서인지 구분할 수 있어야 합니다.
- 서로 다른 directory에 같은 번호가 있을 수 있으므로 번호만 표시하지 않습니다.
  `Application 100 DB role`, `GitOps 200 private repository 연결`처럼 domain·작업 의미를
  필요한 만큼 함께 표시합니다.
- `AGENTS.md`, `README.md`, workflow YAML처럼 번호가 없는 고정명 artifact에는 표시를
  맞추기 위해 임의 번호를 만들지 않습니다.
- 이 규칙은 새 numbered document link와 현재 작업에서 target·anchor·표시 이름 중 하나를
  실질적으로 수정하는 numbered document link부터 적용합니다. 건드리지 않은 기존 corpus는
  다음에 그 link를 실질적으로 수정할 때 함께 맞추며, 이 규칙을 도입했다는 사실만으로
  repository 전체를 기계적으로 다시 쓰지 않습니다.

### 구조 파일 이름

- 번호 뒤 이름은 현재 문서의 canonical 책임과 독자 질문을 표현합니다. 이미 존재한다는
  이유만으로 과거 system, delivery 방식이나 폐기된 범위 이름을 유지하지 않습니다.
- 새 문서를 분리하거나 같은 directory의 topology를 변경할 때는 기존 sibling의 filename,
  제목, 현재 목적과 router 책임을 함께 대조합니다. 이름과 현재 책임이 다르면 그 path를
  새 문서의 기준으로 복제하지 않고 rename 대상과 모든 inbound link를 먼저 확정합니다.
- 필요한 rename 권한이나 전체 link 범위가 없으면 잘못된 기존 이름을 전제로 새 path를
  만들지 않고 구조 작업을 미완료로 남깁니다.

### Work item 번호

Work item 번호는 현재 유형·생성 연도 디렉터리의 읽기 순서입니다. `001`부터 빈자리
없이 증가하며 본문·`-design`·`-history`가 번호와 slug를 공유합니다. 문서를
삭제·병합하거나 순서를 바꾸면 현재 문서를 다시 번호 붙이고 모든 inbound link를
같은 작업에서 갱신합니다. 과거 번호와 경로는 별도 발급 원장이 아니라 Git 이력으로
복원합니다. 상세 규칙은
[100 작업 문서 생명주기](work-items/100-work-item-lifecycle.md)가 소유합니다.

이동·삭제·rename 시에는 어느 번호 체계든 제목, router, inbound link, 대체 owner와 실제
directory topology를 같은 작업에서 갱신합니다.
